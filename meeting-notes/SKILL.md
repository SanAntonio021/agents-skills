# 会议纪要

## 作用

这份 skill 把原始转写和用户补充整理成便于理解、继续讨论或推进工作的会议纪要。会议不一定产生任务，先判断它是在讨论问题，还是在分配工作。

## 触发

下面这些情况优先进入这份 skill：

- 用户上传或引用一份或多份会议转写文件
- 用户说“根据语音转文字整理会议纪要”“做会议纪要”“提取行动项”“把会议记录整理一下”
- 用户要整理技术交流、方案讨论、访谈或咨询对话
- 同一场会议被拆成多个分片文件
- 目标是形成讨论记录、行动纪要或最终定稿

## 先判断怎么写

按下面的证据顺序判断会议用途和读者：

1. 用户明确说明的用途和读者。
2. 转写中实际讨论的内容，以及是否出现明确决定、负责人和时间。
3. 文件名和项目背景只用于理解上下文，不能据此推断纪要用途。即使文件位于申报书目录，也不能自动写成服务于申报书的材料。

根据内容选择类型：

- **讨论型**：重点是交换看法、比较方案、解释技术问题或找出还没想清楚的地方。
- **行动型**：已经形成决定，并明确了任务、负责人或时间。
- **混合型**：前面以讨论为主，末尾只有少量明确任务。

默认面向“懂一些技术、但没有参加这次会议”的读者。保留必要专业术语；较生僻的术语第一次出现时，用一句短话解释，不把技术内容改写成纯科普。

## 流程

1. 读取同一场会议的全部转写文件，并视为一份完整会议材料。
2. 判断会议用途、读者和纪要类型，再选择输出结构。
3. 按“发言人 + 议题”拆分内容，合并反复出现的同一观点。一个事实只完整写一次，其他位置只做简短引用。
4. 讨论型纪要保留不同意见和没说透的问题；行动型纪要识别用户本人相关的任务、待办和决定；混合型纪要先写讨论，再单列确实已经明确的任务。
5. 第一版完成后暂停，请用户补充笔记、备注或纠错。
6. 只有能明确对应到原始转写或用户补充的信息，才能并入最终稿。
7. 默认输出 `.md` 纪要；用户明确要求 Word 时，再导出 `.docx`。

## 输出结构

讨论型纪要默认使用：

1. 这次在讨论什么
2. 已经基本明确的几点
3. 现在还没说透的几点
4. 后面怎么继续讨论

行动型纪要默认使用：

1. 用户需要做的事
2. 会议已经确定的事项
3. 各项任务、负责人和时间
4. 还需要确认的事项

混合型纪要以讨论型结构为主，在末尾增加“已经明确的任务”。如果某一节没有实际内容，省略该节，不用空话补齐模板。

具体写法见 [references/workflow.md](references/workflow.md)。

## 用词

- 标题和小标题直接说明在谈什么，例如“为什么要换方案”“两种方案差在哪”“还缺哪些数据”。
- 不用“核心判断”“关键展开”这类看不出具体内容的标签，也少用“差异化价值”“产品化叙事”等咨询式说法，除非它们是会议原话且确有必要。
- 用自然、准确的技术中文。读者能理解常用术语，但不能假定读者知道会议背景。
- 删除口头重复、寒暄和同义反复；不同发言人对同一问题有实质差别时，分别保留差别。

## 边界

- 不做沟通风格、行为表现或团队心理分析。
- 不把推测性的“可能任务”写成既定行动项。
- 不因为项目目录、旧材料或会议涉及申报内容，就自行认定纪要服务于申报书。
- 不把讨论型会议硬整理成“结论 + 责任人 + 截止时间”。
- 不把同一场会议的分片转写拆成多份互不关联的摘要。
- 用户没有补充笔记时，要明确记录“无补充”，再输出最终版。

## 维护

- 始终把“原始转写 + 用户补充”作为唯一事实来源。
- 当输出模板、纪要口径或导出要求变化时，优先更新这里。
