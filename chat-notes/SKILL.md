# 对话收尾与经验整理

## 何时执行

只在用户显式调用 `$chat-notes`，或明确要求按本技能收尾时执行。

开始前先确认：

- 当前是哪个项目；
- 本轮做了什么；
- 应读取哪些材料；
- 用户是否限制为只读、局部修改、暂不清理、暂不提交或暂不发布。

五项工作按依赖关系执行。某项缺少材料、需要确认或暂时受阻时，只停该项，其他已授权工作继续。

用户限制、计划模式和宿主权限约束优先于默认动作；只讨论、只审查、指定文件范围、暂不清理、暂不提交或暂不发布时，按限制执行。未受限制时，调用本技能包含本任务过程材料的可恢复清理，以及本轮已确认、可隔离成果的提交推送；已获准的技能修改还包括检查、发布和运行副本复查，按第 5 项完成。未经授权，不扩大到父工作区、其他项目、外部链接目标或整个资料库。技能行为修改必须有明确建议并获得确认；已有准确授权时不再重复询问。

不要在收尾时另建总结、综合记录或核验报告。没有新事实时，仍要检查相关文档的职责和引用；内容准确就保持原样。

## 五项工作

### 1. 项目 Markdown

**先看什么**

- 完整阅读本轮涉及的 README、AGENTS、SKILL.md 和接续入口。
- 对关联专题，只读受影响内容和必要引用。
- 核对当前成果、状态、限制、待办、重复、错放内容和失效引用。
- 不扫描或改写无关历史文件。

**怎么做**

Markdown 的结构、引用和历史处理按[维护规范](references/markdown-maintenance.md)执行。事实保护、重复判断、修改强度和停笔条件按 [common-quality.md](../writing-router/references/common-quality.md) 执行。

先判断需要哪种处理：

- **不修改**：内容准确，章节各有用途，引用清楚。长文也可以保持原样。
- **局部修改**：只更新过时状态、参数或用法。
- **合并**：同一事项分散在多处，或内容放错文件。
- **重构**：历史记录、混合职责或重复内容妨碍阅读和接续。

需要重构时，先按维护规范建立内容清单和唯一落点，再开始移动。已有合适目录或文档时优先复用。没有合适位置且详细内容确有后续用途时，才新建专题。

保留有效参数、条件差异、失败结果、恢复依据、用户修改和无关工作。已解决且不再有用的调试流水可以合并或删除，但不要把它复制成新的历史总账。

**完成标准**

- 重读修改后的入口和受影响段落。
- 当前状态、待办、职责和引用一致。
- 迁移出去的内容只有一个权威落点。
- 必要参数、证据、失败结果和恢复信息仍能找到。
- 缺少原机或外部材料时保留来源和未核验状态。

### 2. 飞书与实验文档

**先看什么**

从项目入口定位用户指定的主稿、当前步骤和批次。先核对原始材料及真实执行状态，再区分计划、实测、离线回放和推测。

**怎么做**

- 同一批次的结果写回对应步骤、表格或单元格，不在末尾重复追加。
- 不同批次分别记录。
- 条件、动作、结果和证据放在一起。
- 保留接线、参数与单位、测量点、次数、判据、图片、原始数据和下一步。
- 图片和附件放在对应结果之后，结论与证据保持相邻。
- 参数名与单位分开；一个单元格只放一个参数。
- 人填／AI 回填标记沿用原表。
- 未知值留空，不推测补齐。
- 保留有效的差结果和失败记录。
- 未开始的实验仍写为计划。
- 软件通过、设备接入或文件传输成功，不能写成硬件采集或通信性能通过。
- 不把 AI 写作规则、调试流水或无信息量的“无异常”写进实验正文。

没有新结果或结构问题时保持原样。如果图片或附件仍需实验电脑补交，明确列出所需内容。不要把本机无法访问的实验室路径当作已读证据。

只有已经证明采集无效，并且用户同意移出正文时，才可以把内容移到已有归档位置。归档时必须保留原因。

**完成标准**

用实际记录工具重读，核对步骤顺序、批次、条件、数值、单位、附件、引用和结论范围。新结果要有材料支持；原有有效结果不能被覆盖；未执行步骤不能被升级为已完成。

### 3. 经验与技能缺口

**先看什么**

先读相关规则和实际过程，核对适用条件、执行动作及结果。不要因为文件里已经有某句话，就直接认定执行没有问题，也不要预先归为执行遗漏。

**怎么做**

先判断原因：

- 规则清楚、适用，但没有执行：属于执行遗漏。沿用现有规则，不追加同义提醒。
- 缺少触发条件、判断方法、操作步骤或完成标准，或条款分散、歧义：属于技能缺口。可以提出具体改进。
- 两类原因可以并存；证据不足时说明原因尚未确定，不断言单一根因。

有后续用途的内容按以下位置整理：

- 项目参数、路径、版本和当前状态放入对应项目记录。
- 一次性的试错和普通发布过程不写成长期规则，除非它仍影响使用、恢复或判断。
- 可跨场景复用的方法放入对应技能。通用流程留在入口，较长细节复用已有参考；已有清楚且适用的方法只引用，不重复新增。
- 设备、站点或平台特例放入技能中的相应说明，只保留差异和有效例外，并引用通用方法；尚未证明跨场景适用的做法不提升为通用要求。

先按第 1 项确定归属，选择不修改、局部修改或合并；确有新内容且现有位置无法承接时才新增。技能行为建议标为“建议修改”，写清目标技能及链接、现有缺口、拟增加或删除的内容、验证场景。用户确认前只提出建议，不修改、不提交、不发布。含义不变的引用修正和去重可以直接做；涉及技能源码时按 [skill-creator](../skill-creator/SKILL.md) 检查，获批行为修改先独立试跑，再进入第 5 项。确认一项不扩展为确认其他项。

**完成标准**

- 原因判断能指向具体规则和实际过程。
- 建议只覆盖已确认的缺口。
- 项目事实没有写成通用规则。
- 通用流程没有复制到每个特例。
- 特例没有扩大适用范围。
- 有效差异和例外没有因去重丢失。
- 已修改和未验证部分分开报告。

### 4. 过程文件清理

**先看什么**

只盘点本任务及明确属于本任务的过程目录和散落文件。先核对成果、草稿、对比版本、原始输入、源码、测试、实验数据、编辑源、验证证据、依赖和正在使用的文件。

**怎么做**

先按对象分类：

- 用户过程资料、草稿、被替代稿、预览、截图和实验中间材料，使用可恢复清理。
- 本次工具创建且可重建的临时 clone、缓存、锁目录和比较目录，核对绝对路径、用途、依赖和进程占用后直接删除。
- 正式成果及复现依赖必须先归位，并更新所有真实引用。

移动或删除前再确认：

- 文件确实属于本任务；
- 是否仍被入口或正式成果引用；
- 是否有恢复依据；
- 是否还有进程正在占用。

对工具临时目录，还要核对只读属性、锁文件和 worktree 状态，确认临时 clone／worktree 没有用户改动。只释放本任务创建的锁和句柄；删除前解除目标树内阻止删除的只读属性。不要强关用户正在使用的应用。

不要只凭文件名、目录名、修改时间或版本号判断删除。无法确定用途或落点时，保留相关文件并说明待确认项。

跨目录范围未确定时，先列出成果、依赖、目标位置、旧位置和拟改动范围。确认后按 [project-organizer](../project-organizer/SKILL.md) 处理；不要借收尾搬动整个工程、申报包、原始数据或其他项目。

用户资料没有可恢复入口时保留原文件。永久删除必须针对准确文件取得明确许可。不要把全部过程材料搬到新归档目录来代替清理，也不要把临时材料写入正式正文。正式成果仍依赖待清理目录，或引用检查失败时，保留相关文件。

每个对象按选定方式处理一次。不要用盲目循环重试代替清理前准备；准备条件不满足时保留对象并记录原因。临时移动后失败时，先恢复原路径。

**完成标准**

- 目标原路径已消失；
- 用户资料有回收或恢复入口；
- 工具临时目录已确认可以重建；
- 正式成果和相关引用仍可打开；
- 失败或只完成一部分时如实报告，不把手动处理算作已完成。

正常情况只报告清理结果；出现残留、恢复失败或正式文件受影响时，再说明原因和后续动作。

### 5. 提交、发布与运行时同步

**先看什么**

分别检查项目成果、技能源码和运行副本。确认哪些改动已经批准，哪些仍在草稿中，哪些与本次任务无关。

**怎么做**

项目成果：

- 已经完成的提交、推送或复查不重复执行。
- 内容已确认、可以隔离且允许提交时，先核对远端，再精确暂存并提交。
- 推送后读回远端提交，确认包含本次成果。
- 不整库暂存，不修改无关改动，不强制重置或强推。
- 内容未定稿、项目没有 Git、没有远端或存在无法安全处理的冲突时，只暂停提交和推送。

技能修改：

- 按 [skill-creator](../skill-creator/SKILL.md) 完成必要检查和验证。
- 按[技能发布操作](references/skill-edit-followup.md)和 [agent-rules](../agent-rules/SKILL.md) 使用受支持的同步入口。
- 精确提交并推送本项目实际修改的技能文件。
- 使用相同提交、完整技能集合和必要参数完成后台同步。
- 再用完全相同的参数执行 `-VerifyOnly`。

不要手工修改数据库或运行副本，也不用前台点击代替受支持流程。

固定 CLI 因数据库 schema 不兼容而无法写入时，按顺序处理：先在 CC Switch 桌面版界面中编辑已启用的预设并保存，由它写入应用规则文件；界面入口也不可用时，停止发布并报告卡点，保留源码改动、提交与备份，等待支持该 schema 的 CLI 或人工处理。不以“先改库再回读一致”作为替代方案。

**完成标准**

- 项目提交已推送并能从远端读回。
- 技能源码、CC Switch、Codex 和 Claude 的文件集合及 SHA-256 一致。
- 来源登记有效，启用的应用正确。
- 同步和复查都返回 `runtime_active`。

只完成源码推送时，要明确报告“运行副本尚未生效”。发布失败时，保留准确提交、完整目标集合、失败阶段和恢复依据，并继续其他独立的已授权工作。

## 结果汇报

保留五项标题和顺序。每项先写用户需要知道的结论，再补必要依据；没有内容时直接写“无”，不解释检查过程。完整文件清单、哈希、逐步校验和排错流水留在已有记录中，不复制到默认汇报。

1. **修改的 Markdown**：实际修改的文件链接和改法；没有修改时写“无”。
2. **成果**：最终文件或回填位置，以及提交、推送、运行同步的实际状态。正常时合成一条状态链；失败时只指出断点。
3. **经验整理**：实际更新了记录或技能就写改了什么；只有建议时直接写“技能建议：对象和要解决的问题”；两者都没有时写“无”。
4. **清场**：是否完成、是否有残留、是否需要用户处理。正常时不逐项列文件或恢复位置。
5. **待办**：尚未完成或需要用户决定的事项及下一步；没有时写“无”。

异常项只写发生了什么、影响什么、下一步；不展开完整排查过程。
