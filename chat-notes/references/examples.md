# chat-notes 例子

## 例子 1：判断经验该写到哪里

用户说：
```text
把刚才关于项目私有经验和跨项目方法的讨论整理一下，不要直接改文件。
```

应该做：
- 从当前对话提取经验
- 区分项目私有和跨项目通用
- 分流判断：涉及跨项目方法 → 有可能做 skill → 走完整流程
- 查本地和外部类似 skill
- 给出四类结论之一和简短审查稿

## 例子 2：对话结束收尾

用户说：
```text
这轮先到这里，整理一下，把没用的中间文件也清一下。
```

应该做：
- 沉淀有价值经验
- 更新项目 README/AGENTS/CLAUDE 或标准文件
- 先按用途列出当前交付物、当前可编辑版本、来源证据和现役 QA 的保留集，再列出可归档候选与待判断项
- 给用户完整清场预览：候选数量/字节数、归档前 SHA-256 清单、归档位置和逐项恢复方式；此时不移动文件
- 用户看完完整汇报后再次批准，才用路径固化的任务级命令移到 `archive/cleanup-YYYYMMDD/data/<原相对路径>`
- 对每个已移动文件复核源离开、目标存在和 SHA-256；汇总复核保留集、引用和空目录，并给出验收 JSON
- 不平铺文件、不覆盖已有归档项、不改 `.gitignore`，不进入回收站也不硬删

## 例子 3：多版本非代码项目收尾

用户说：
```text
这个调研目录里文档太乱，收尾整理一下。
```

应该做：
- 建立或更新 `README.md` 和 `AGENTS.md`
- 把成文说明命名为 `doc-*`
- 把台账索引命名为 `record-*`
- 把最终成果命名为 `output-*`
- 保留当前成果、最新可编辑 Office 文件、支撑结论的原始来源和现役 QA 证据
- 只有确认已被当前成果替代的旧 Office/PDF、候选图片、旧提示词、过程脚本和旧 QA 截图才作为归档候选；不因 `v1`、`qa` 或 `_reference` 前缀自动移动
- 将批准的候选按其原项目相对路径归档，并用归档前后 SHA-256 清单与恢复命令保证可复原

## 例子 4：正式改完 skill 后推送

用户说：
```text
这个 skill 已经按审查稿改完了，能安全推送就推上去。
```

应该做：
- 按 `skill-creator` 对照检查
- 补齐缺口
- 找对真正源码仓库
- 检查 git 和 remote
- 只提交本次相关改动
- push 后调用 `ccswitch-skill-sync` helper，只更新该提交实际修改的 Skill
- 只有源码、CC Switch、Claude、Codex 四层文件集合和 SHA-256 完全一致才报生效
- 自动更新或验收失败时只报“源码已推送，运行时未生效”，不直接改运行时

## 例子 5：分流后直接写项目记忆

用户说：
```text
帮我把这次排查 Nginx 反向代理到 3000 端口的步骤记下来，下次同一个项目能查。
```

应该做：
- 从对话提取经验（Nginx 反向代理配置步骤）
- 分流判断：这是针对当前项目的一次性配置记录，不是跨项目可复用的工作流 → 不值得做 skill
- 跳过本地和外部 skill 搜索
- 结论：写在当前项目里
- 输出简短审查稿，说明写到哪个文件、写什么内容

## 例子 6：区分规则缺口和没有执行

情况一：现有 skill 只要求测试输出使用临时目录，但没有说明测试所读取的冻结文件和阶段状态也要隔离。按原文仍可能做错，属于`规则不完整`，可以建议修改现有 skill。

情况二：现有 skill 已明确要求审查稿不要列出排除项，agent 仍列了排除项。属于`规则明确但没有执行`，结论应为`这次不改`，不能重复增加同义规则。

情况一的审查稿写结论、一句理由、准备修改的内容和一个确认问题。情况二没有实际改动，只写`这次不改`和一句理由，不硬加`准备改`或确认问题。两种情况都不展开内部判断过程。

## 例子 7：单个缓存文件也走完整核验

用户在完整清场预览后说：

```text
同意归档那个单独的 render-cache.bin。
```

应该做：
- 即使只有一个文件，也建立保留集清单、归档前清单、归档后清单和 `archive-acceptance.json`
- 在移动前记录其原相对路径、归档相对路径、用途、Git 状态、字节数、SHA-256 与拒绝覆盖的恢复命令
- 逐项核验该缓存文件从源路径离开、归档目标存在且 SHA-256 不变，再复核保留集
- 任何清单遗漏、哈希不一致或回收站路径出现时停止，不把单文件当作可跳过核验的例外
