# Markdown 文档维护规范

## 适用范围

本规范用于整理、拆分、合并和持续维护 Markdown 文档。它处理文档之间如何分工，不替代 README、AGENTS、SKILL、实验记录、技术文档和版本记录自身的内容要求。

开始前先确认：

- 当前项目是什么；
- 哪些文档属于本轮范围；
- 各文档面向谁；
- 谁会在什么情况下更新这些内容。

不同项目的目录和文档类型可以不同。不要把某个项目的文档结构套到其他项目。

## 推导文档结构

### 1. 盘点现有内容

完整阅读受影响入口和必要引用，把内容按实际段落或章节拆开。对每块内容记录：

| 字段 | 要回答的问题 |
|---|---|
| 内容块 | 这段在说什么 |
| 权威落点 | 以后修改这项事实时应只改哪里 |
| 维护者 | 谁最常维护这部分 |
| 更新触发 | 什么事件会导致它变化 |
| 读者 | 谁需要读取它 |
| 生命周期 | 当前状态、长期设计、批次记录、恢复材料还是历史记录 |

清单只用于判断，不作为收尾报告写入项目。

### 2. 按维护方式分组

- 先看现有目录和文档能否承接内容。
- 把经常由同一事件、同一证据一起更新的内容放在一起。
- 每项事实只能有一个权威落点。其他文档需要时只写摘要并链接。
- 不要按部门名、学科名或固定栏目强行分类。
- 不要为了整齐创建空目录。

### 3. 拆到单一职责

一份详细文档只承担一个主要维护任务。

如果一份文档同时包含多个独立内容，例如：

- 系统方案；
- 器件选型；
- 代码操作；
- 仿真结果；
- 实验记录；
- 交付和验收；

并且这些内容会因不同事件分别更新，就应继续拆分。

禁止建立“项目设计与验证记录”“综合技术记录”“项目总记录”等跨主题兜底文档。它们只是把原来的长文换了文件名。

篇幅不是判断标准。内容准确、职责单一的长文可以保留；短但承担多个独立维护任务的文件也应拆分。

### 4. 验证目标结构

从当前项目选取 3–5 个实际可能发生的变更，检查每项内容的权威落点：

- 修改当前方案时改哪里；
- 新增一次实验时改哪里；
- 更新分析结果时改哪里；
- 修改交付物时改哪里；
- 项目特有场景可换成其他真实更新事件。

如果同一项信息出现多个同等权威落点，结构还没有拆清。

## 内容归位

- README 等项目入口保留用途、入口、当前状态、关键限制、待办和专题链接。
- 专题文档保存详细方法、参数、条件、结果和证据。
- 实验记录按实际批次和步骤维护，不把计划和实测混在一起。
- 历史记录保留当时的条件、结果和结论，不改写成当前状态。
- 配置、待办、参数和并列事实可用列表或表格；背景、判断和方法可用段落。结构服从内容，不为形式强行统一。

## 处理重复

按“事实 + 章节作用 + 证据”判断是否重复：

- 同一事实、同一作用、没有新证据：合并或删除。
- 入口摘要与专题详情承担不同作用：可以同时存在，但入口要压缩并链接专题。
- 不同实验批次或不同条件有真实差异：分别保留。
- 为了解决重复而更换术语、削弱限制或改变结论强度：不允许。

日期可以用来组织实验批次、版本和汇报索引，但不要按日期或文件年龄批量删除历史。

## 历史与删除

- 仍影响当前使用、兼容、排错、恢复或责任判断的内容，必须保留在可查找的位置。
- 已解决且没有后续用途的普通试错和调试流水，可以合并或删除。
- 没有明确承接位置、唯一证据或恢复依据的内容，先保留并标为待核实。
- 不要新建一份冗余历史文件来替代真正的归位。

## 验收

修改后重新读取入口、专题和受影响引用，并检查：

1. 读者能找到当前入口、使用方法、状态、限制和下一步。
2. 参数、条件、批次、结果、版本差异、证据和未验证事项仍可定位。
3. 规则、配置、回退、恢复和证据入口没有因精简丢失。
4. 每项事实只有一个权威落点，迁出内容有明确归属。
5. 所有本地引用指向存在的文件或目录。
6. 数字、版本、因果关系、适用范围和结论强度没有变化。
7. 详细文档按维护任务拆分，没有跨主题兜底文件。
8. 单主题长文没有仅因篇幅被拆分。

修改后只剩同义替换、句式变化或个人偏好时停止，不设固定字数或压缩比例。

缺少原始材料、外部证据或目标文件不可访问时，保留来源和未核验状态。路径存在不能代替内容核验。
