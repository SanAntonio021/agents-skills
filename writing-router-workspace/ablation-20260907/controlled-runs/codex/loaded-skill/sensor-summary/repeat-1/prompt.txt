# 中文正式写作总路由

## 目标

先确定文稿类型、本轮改动边界和协作方式，再加载一个主文体技能。不要把所有写作规则一次性塞进上下文，也不要用同一套“去 AI 味”规则处理所有正式文稿。

## 写作上下文

开始正文工作前，在任务内部记录以下字段；当前任务未换文稿或阶段时沿用。普通交付不展示这段记录。评测提示包含 `TRACE_WRITING_CONTEXT=1` 时，才在文末输出同名 JSON 对象。

| 字段 | 允许值 |
|---|---|
| `document_type` | `project`、`technical`、`research_report`、`meeting_notes`、`paper`、`general` |
| `mode` | 使用下表中与文稿类型对应的值 |
| `edit_scope` | `draft`、`structural`、`bounded`、`in_place`、`audit_only` |
| `language` | `zh`、`en`、`mixed` |
| `loaded_refs` | 本轮实际读取过的规则和样稿路径；不得登记“准备读取”或凭规则名称猜测 |

`edit_scope` 的含义：

- `draft`：从材料起草正文。
- `structural`：允许调整章节、段落职责和信息顺序。
- `bounded`：只改用户指定章节、段落或问题。
- `in_place`：保留结构和作者声音，只做必要的原位修改。
- `audit_only`：只审不改，按共同质量规则在对话中分点报告问题。

## 两级路由

| `document_type` | `mode` | 主技能 |
|---|---|---|
| `project` | `proposal`、`expert_reply`、`final_audit` | [project-writing](../project-writing/SKILL.md) |
| `technical` | `technical_scheme`、`technical_exchange`、`system_description`、`test_result_analysis` | [technical-writing](../technical-writing/SKILL.md) |
| `research_report` | `evidence_report`、`decision_report`、`final_audit` | [research-report](../research-report/SKILL.md) |
| `meeting_notes` | `discussion`、`action`、`mixed` | [meeting-notes](../meeting-notes/SKILL.md) |
| `paper` | `zh_paper`、`en_paper`、`final_audit` | [ieee-manuscript-edit](../ieee-manuscript-edit/SKILL.md) |
| `general` | `general_edit` | 本技能的通用编辑流程 |

判断顺序：

1. 用户明确说出的文稿类型、用途和读者。
2. 原文件的栏目、模板和内容职责。
3. 仍无法区分且会改变产物时，只问一个最关键的问题；不影响实质结果时按最窄范围继续。

会前方案讨论稿、技术交流材料或待讨论问题清单，目标是区分已有条件、会上决定和另行工作时，使用 `document_type=technical`、`mode=technical_exchange`。会议已经结束，任务是整理实际发言、结论和行动项时，使用 `meeting_notes`。

正式文稿进入对应文体技能；普通中文直接在本技能完成，不递归路由。

## 规则优先级

正文中的冲突按以下顺序处理：

1. 用户要求、权威源材料、指定模板和受保护事实；
2. 当前文体与 `mode` 的规则；
3. [共同质量规则](../writing-router/references/common-quality.md)；
4. 已批准的个人样稿。

个人样稿只用于句子密度、信息顺序和语气。样稿不能覆盖事实、模板、术语、证据边界或当前任务的文体规则。

摘要与结论、申报表规定栏目、会议行动项可以为不同章节功能复述同一论点。复述必须服务于新的章节功能，不能整段复制，也不能改变事实、适用范围或完成状态。

## 最小加载规则

1. 确定文体后，先实际读取上表对应主技能的 `SKILL.md`，再按该入口读取本轮需要的参考文件。路由表只用于选择，不能代替文体规则；只读共同质量规则不算完成正式文稿的加载。`general_edit` 不加载另一个写作入口。
2. 五类正式文稿的主技能都读取 [共同质量规则](../writing-router/references/common-quality.md)。中文正文首次起草、续写、局部修改或审查前，同时读取 [AI 气味目录](../writing-router/references/ai-smell-catalog.md)，逐批执行共同质量规则的“中文正文展示前检查”；混合稿仅对中文部分执行。英文仍在完整草稿、结构重写、终稿审校或 `audit_only` 时读取气味目录。
3. 个人样稿入口固定为 `D:\BaiduSyncdisk\.agents\writing-profile\index.md`。只有入口和对应样稿都标为 `approved` 时才读取；一次只读当前文体的样稿。未读取的文件不能写入 `loaded_refs`。
4. 中文正文工作开始时按 `style-vocab` 读取适用词表，在逐批检查中结合语境使用；完整正式文稿交付前继续运行正式词表审计。同一任务文体、规则和材料未变时沿用实际已读内容；无法确认已读内容或内容已变时补读必要文件。若当前文体技能已经完成共同质量与 AI 气味审校，向 `style-vocab` 传递这一状态，不再重复通用改写。
5. 中文论文不加载英文写作细则；英文论文不加载中文写作细则。`final_audit` 只加载当前稿件语言对应的细则和终稿规则。

## 通用流程

1. 锁定当前主稿、来源、模板、交付范围和受保护片段。
2. 建立写作上下文后、处理正文前，读取[文稿协作](references/collaborative-writing.md)，将实际路径记入 `loaded_refs`，再选择主技能。先识别会议整理、运行日志和明确整篇处理等例外；其余 `draft/structural` 默认分批确认，`bounded` 按实际改动判断，`in_place` 直接编辑，`audit_only` 保持只读。同一任务已读且处理方式未变时沿用。
3. 材料不足时只写材料能支持的部分，明确列出阻塞正文成立的缺项，不用常识或套话补篇幅。
4. 按当前文体、模式和协作方式起草、重构、局部修改或审查。协作起草先讨论结构和思路，中文正文每批先检查再展示；确认后写回当前主稿，并直接衔接经过检查的后续正文。
5. 用共同质量规则检查事实漂移、段落职责、信息推进、全文重复和停笔条件。中文在每次正文展示前结合气味目录检查本批及必要上下文，不等完整稿；英文沿用当前文体的检查时机。
6. 完整正式稿再做术语与个人用词检查。默认只交付本轮请求的正文，不附修改理由或检查记录；用户要求解释时才说明，仍与正文分开。确有无法自行解决的事实疑点时，先提出具体疑点，不交付掩盖它的改稿。
7. 实际写入工作区内的 `.md` 或 `.tex` 时，读取 [文稿版本保护](references/document-version-protection.md)。只读审查和聊天内改句不触发。
8. 需要 Word 时，正文先按当前协作方式完成本轮内容处理与审校，再按 [Markdown 到 DOCX 交接契约](references/markdown-docx-contract.md) 交给 `docx`。飞书主稿直接回读，不额外维护本地副本；交付流程不再自行运行第二遍通用风格改写。
   恢复交付或复用检查结果时，由 Word 工具核对主稿、模板、图片和 Word 版本；变化后的材料重新检查，保留用户手工修改。

## 普通中文编辑

已有普通中文的 `general_edit` 默认 `in_place`：以原文为底稿，先定位具体问题，再只替换必要片段；没有具体问题就原样交付，不从头另写一版。新建文档使用 `draft`，用户要求重搭结构时使用 `structural`，均按文稿协作处理。只看问题时使用 `audit_only`，不顺手改稿。

处理中文文稿前读取 [共同质量规则](references/common-quality.md)、[AI 气味目录](references/ai-smell-catalog.md)及 `style-vocab` 适用词表，每次展示正文前检查；普通讨论回复不因此进入文稿检查。先保护事实、数字、单位、公式、引用、因果、比较、否定和完成状态；优先删无信息句、合并重复，再修句式。关键词命中只能帮助定位，不能单独判错。不注入虚构细节、第一人称、情绪或幽默，不把专业术语当 AI 词替换。

默认给本轮请求范围内的修改文本；只有事实缺口或实质取舍需要决定时再附简短说明。继续改写不能带来明确收益时停止。

## 私有样稿

仅在用户要求维护样稿时更新，不在业务交付后自动追问。运行时只读取 `approved` 样稿；候选与批准内容分开，用户已明确的替换范围和选择可复用。样稿只提供表达参考，事实必须重新取证。

## `audit_only` 审查输出

按 [共同质量规则](references/common-quality.md) 直接在对话中分点列出问题，每点以加粗关键词开头，保持用户指定的审查范围。

整段无理由重复、跨节事实矛盾、虚构数据或把“计划/设计/测试”升级成更高完成状态，直接判 `fail`。`audit_only` 不顺手改正文。

# 文稿协作

把内容取舍放在起草过程中解决，减少整篇生成后的返工。先确定当前主稿和本轮处理方式，再按以下流程推进；文体规则负责怎么写，本说明负责何时讨论、确认和写入。

## 选择处理方式

沿用当前任务已确定的 `document_type`、`mode`、`edit_scope`、`language` 和 `loaded_refs`。直接调用文体技能时补齐这些字段，实际读取本说明后将其路径记入 `loaded_refs`；同一任务已读且处理方式未变时沿用，不重复加载。

先保留只审不改等明确限制，再识别直接处理的任务：会议转写整理、执行期运行日志、普通润色与纠错，以及用户明确要求直接给出整篇的任务。纯导入和格式转换交给对应文件或平台技能。已有模板或材料齐全，本身不改变协作方式。

其他正文任务按修改范围处理：

| `edit_scope` | 处理方式 |
|---|---|
| `draft` | 先讨论结构和思路，再分批确认正文 |
| `structural` | 讨论受影响的结构及正文，分批确认改动 |
| `bounded` | 补写方案、改变论点或调整结构时分批确认；局部润色、纠错直接处理 |
| `in_place` | 保留结构和含义，按请求直接修改 |
| `audit_only` | 给出位置、问题和依据，保持只读 |

运行日志沿用 `lab-notebook` 的连续记录流程；整理成新的正式报告时，再按正文任务判断。“整理成文档”表示要形成文档，先进入这里选择处理方式，不据此自行补齐全文。

## 结构和思路

先读取已有材料、文稿和模板，给出便于浏览的总体结构，并简述各部分要回答什么、内容如何衔接。与用户讨论需要调整的部分，不在提纲下提前展开完整正文。

结构可以暂定，先从能够明确的部分开始。正文讨论暴露结构问题时，指出受影响的章节和段落，商量调整后再继续。只调整相关内容，保留其余已确认部分。

## 正文循环

中文正文按“起草或修改 → 展示前检查 → 展示 → 用户确认 → 原样写入并回读”推进。首次处理时按[共同质量规则](common-quality.md)的“中文正文展示前检查”读取并执行所需规则；同一任务未变时沿用。直接处理任务在交付或写入前检查，不增加确认轮次；`audit_only` 只报告问题，不生成替换稿。英文沿用当前文体的检查时机。

1. 展示本批拟写入的实际正文，覆盖当前讨论的内容。中文本批正文及必要上下文须先完成检查，包括标题、图表说明和聊天中待确认的段落。每批可以是一段或相邻几段，按内容难度和用户反馈调整，不预设固定段数。
2. 用户提出修改时，先检查修改后的中文正文，再在对话中给出。确认对象是这份实际文字，结构或内容要点的认可不代替正文认可；不能用上批的检查代替本次检查。
3. 用户只反馈部分段落时，修改指出的问题，并主动询问未提及段落是否需要修改。写入范围以明确认可的段落为准，一次回复可以认可多段。
4. 回读当前主稿，原样写入已认可的正文，核对实际写入内容。若同一位置已有用户的新改动，先展示与待写版本的差别，再确定替换内容；其余内容保持原样。确认后发现文字问题时，先展示具体修改让用户确认，不在写入时悄悄重写。
5. 写入成功后，简短说明已写入哪部分，并在同一次回复中直接给出后续正文；中文后续正文也须先检查。仍有待确认段落时主动询问，不只停在确认总结上。

例如，用户说“第二段太长”，就修改第二段并询问其他段落；说“其他都没问题，第二段再改一下”，可以写入其他段落，再讨论第二段；说“这几段都可以，继续”，就写入本批并给出后续正文。写入受阻时说明实际状态，保留已确认文字，不宣称保存成功。

讨论结构、思路或其他取舍时，也在每项确认后主动提出下一项真正未决问题。已有决定直接沿用，所需信息充分后进入正文或完成当前任务。

## 主稿与交付

主稿使用用户当前选定的文档，可以是本地 Markdown，也可以直接是飞书文档。目标尚未明确时，先确认要写回哪份文档；直接修改飞书无需额外维护本地主稿。

本地文件按[文稿版本保护](document-version-protection.md)处理；飞书的读取、局部写回和核验交给对应平台技能。平台上的分段写入只是执行方式，仍按上面的正文确认范围操作。普通问答只在对话中回答，不自动建立主稿。

转换 Word 等交付版本时，使用当前主稿中本轮已确认或按直接处理流程完成的正文。既有内容、图片、公式和用户手工修改随主稿回读，格式阶段不新增论点、步骤或结论；Word 按[交接说明](markdown-docx-contract.md)处理。

## 全篇收尾

各段完成后，当前助手通读全文，检查结构衔接、重复、术语和事实一致性，并完成当前文体要求的质量与用词检查。只展示需要调整的地方，用户确认后写入；没有问题即可完成，不要求用户再审一遍完整稿。

独立读者检查按用户要求或明显理解风险使用：由不了解聊天背景的助手只读成稿，检查缺失前提、歧义和矛盾，再把发现的问题带回讨论。常规任务不自动增加这一轮。

# 共同质量规则

这份文件只规定各类写作都必须满足的质量底线。具体结构和语气由当前文体技能决定。

## 1. 优先级

发生冲突时按以下顺序处理：

1. 用户要求、权威源材料、指定模板和受保护事实；
2. 当前文体与模式；
3. 本文件；
4. 已批准的个人样稿。

样稿只能影响句子密度、信息顺序和语气，不能改写事实、模板、术语或证据边界。

## 2. 事实与关系保护

编辑前建立受保护项清单，至少检查：

- 数字、单位、公式、变量定义和计算关系；
- 人名、机构、设备、版本、时间、地点和专有名词；
- 引用、引文、来源归属和论点—证据关系；
- 因果、比较对象、否定范围、条件、概率和结论强度；
- `拟开展`、`已设计`、`已实现`、`已测试`、`实测`、`计算得到` 等状态；
- 模板规定栏目、用户要求原样保留的句子、代码和受保护片段。

任何修改都不得让这些项目漂移。无法判断时保留原文并标 `review_required`；不得凭常识补齐。

## 3. 材料充足度

先判断材料能支撑到哪一层：

- 足够：可以完成用户指定范围。
- 局部足够：只写已被材料支持的部分，并指出阻塞其他部分成立的具体缺项。
- 不足：不扩写正文，列出最少的必要材料。

“写得完整”不能成为补造背景、数据、结论、行动项或完成状态的理由。材料不足时，少写比用常识和套话撑篇幅更好。

## 4. 段落功能与信息推进

每段只设一个主要功能，例如背景、问题、方法、事实、结果、判断、限制、决定或行动。允许同段出现支撑主功能的条件和证据，但不要把定义、事实、判断和建议混成一段。

一句话应对当前段落有用：交代材料中的事实、证据、条件、限制、决定，或完成当前任务所需的解释与推理。“推进信息”是相对同段其他句子而言，不是要求增加材料之外的内容；摘要可以压缩复述已有结论。只预告将要讨论什么、评价前文很重要、换说法重复结论或泛泛拔高的句子应删除。

段落长度由内容决定，不追求统一。并列项数量由事实决定，不强凑两项、三项或四项。

### 中文正文展示前检查

这项检查只处理中文文稿正文，包括待确认的段落、标题和图表说明；不扩展到普通讨论回复。首次起草、续写、局部修改或审查前，读取本文件、[AI 气味目录](ai-smell-catalog.md)及 [style-vocab 技能正文](../../style-vocab/SKILL.md)，再按文体读取适用词表，实际路径记入 `loaded_refs`。同一任务规则和材料未变时沿用；上下文已缺失或无法确认读过时补读，不靠登记名称代替读取。

先选择本批的实际操作。局部润色以原文为底稿，先定位具体问题，再只替换必要片段，不从头另写一版；找不到影响理解、事实或信息密度的问题时，原样交付。未涉及的原句及时间、条件、状态表述保持原样；加标题、分段或列表只改变用户要求的形式。摘要先选取回答当前问题的原有事实和结论，再压缩合并。新起草或用户明确要求重写时，按材料组织新句子，仍执行下面的事实核对。

保留事实不等于每段重述事实。摘要只带入理解本句结论所必需的信息：删去某项状态后，会不会让读者误认结论已得到更广的验证？会就保留具体限制；不会就不为完整性附加核对过程或未完成事项。单项比较只回答该项比较，不顺带讨论整体可用性；涉及整体可用性时，不能隐去影响它的未验证状态。局部润色仍保留原稿明确的对象状态，不把摘要取舍当成删除正文事实的许可。

每次展示正文前，当前助手检查本批及判断所需的前文、已确认段落和材料：

1. 先核对数字、公式、术语、完成状态和成立条件，再看表达；不因追求简短删去限制或补造事实。

   从改稿反查用户材料：逐字核对出现的人名、机构名、型号和编号，并核对其对应的发言、动作或数据。只与助手上一轮改稿比较，可能沿用先前的错字或错配；用户明确更正的内容优先，不能凭常见写法纠正专名。

   对照材料检查实际增删：新增的时间、条件、动作、建议和结论各依据哪句话？合理推断不能写成已确认安排。润色和摘要只处理既有信息，不补出执行安排或增减条件；不要把材料中的时间、范围或先后顺序重新解释成另一项要求。明确要求提出建议时，将建议与已有事实分开，不能伪装成材料原有结论。

2. 对疑似多余的句子试删：删后，当前读者理解对象、方法、证据或结论所需的信息是否损失？没有损失就删除，不换成另一句解释；有损失就保留必要信息。专业读者已知且不参与后续论证的常识可删；首次定义、变量含义和推理必需的前提仍应保留。

   审查中发现缺少依据的推断，删去该推断即可，不补一段声明来替它收尾。已有的限制直接用材料中的事实表达；不再附加助手自行推导的“本段仅供……”“不能形成最终结论”等免责或定位说明。材料本身明确的风险、否定和适用范围仍须保留。

3. 对否定或转折找到它实际回应的观点：该观点是否在材料、前文或读者任务中存在？没有真实对象，且删去不改变适用范围时直接陈述结论。真实反例、比较、风险和适用条件不能按句式删除；无法判断时保留，并只询问影响当前正文的具体疑点。
4. 与前文比较同一论点是否增加了条件、证据或新的章节功能。没有增加就合并或删除本批重复句；不顺手修改已确认的旧段。术语重复不等于论点重复。
5. 对照原文回看改后的实际正文，确认信息关系未变后再展示。局部润色中，每处改动都应对应先前定位的问题；只有同义替换或“听起来更正式”的改动撤回。已经清楚自然的文字保持原样；不凑压缩比例、不为句式变化继续改写。

用户修改或要求重写后，再检查本批；完整稿仍需全文通读和正式词表审计。逐段检查不要求新建临时文件、运行扫描脚本、调用独立审稿助手或输出检查报告。检查在内部完成；用户只要正文时，直接交付本轮正文后结束，不展示检查清单、加载记录或改写理由。`audit_only` 使用上述判断，但只报告问题。已加载技能、词表无命中或自称完成检查，均不能代替对实际正文的判断。

## 5. 全文重复

按“论点 + 章节功能 + 证据”判断重复：

- 同一论点、同一功能、没有新证据：`review_required`，通常合并或删除。
- 同一论点用于摘要与正文、结论与论证、申报表不同规定栏目：可以保留，但应压缩并适配新功能。
- 整段无模板理由的逐字或近逐字复制：`fail`。
- 复述导致数字、范围、因果或完成状态变化：`fail`。

不要为了避重而循环更换同一术语。术语稳定优先于表面词汇多样。

## 6. `audit_only` 审查输出

只审不改时，默认直接在对话中分点列出需要处理或核实的问题，重要问题在前。每点以加粗关键词开头，紧接位置、问题、原因和必要的修改建议；同一问题集中说明。没有问题时简短说明。

判断应对应原文、来源或数据，并结合章节作用，区分已确认问题和待核实事项。用户明确要求表格时按要求整理。

以下情况直接 `fail`：虚构数据或引用、跨节事实矛盾、整段无理由重复、改变公式含义、把计划或设计升级成实现或实测、把个人观点写成组织结论。

## 7. 修改强度

按 `edit_scope` 控制：

- `in_place`：只修明确问题，不重排结构。
- `bounded`：不越过用户指定范围；上下文只用于判断关系。
- `structural`：可以移动和合并，但先做内容清单，防止漏掉受保护项。
- `draft`：只使用已提供或已核验材料。
- `audit_only`：不产生替换稿。

优先顺序是删除无信息内容、合并重复、补回缺失主语或逻辑关系、调整信息顺序，最后才是换词和改句式。

## 8. 个人样稿

私有入口为 `D:\BaiduSyncdisk\.agents\writing-profile\index.md`。只在入口和对应文体样稿都标为 `approved` 时读取。一次只加载当前文体样稿，并把实际路径写入 `loaded_refs`。

样稿中的事实、名称、数字和句子不得复制到新文稿。没有获批样稿时照常执行文体规则，不猜测用户偏好，也不读取其他类型样稿。

## 9. 停笔条件

同时满足以下条件就停止：

- 用户要求的范围已经完成；
- 受保护事实和关系未漂移；
- 每段功能清楚并推进信息；
- 没有未处理的 `fail`，`review_required` 已保留给人工判断或得到处理；
- 继续改写只能产生同义替换、节奏扰动或个人偏好变化，不能带来明确的信息或理解收益。

# AI 写作气味目录

气味是复核线索，不是禁词表。只有“成立条件”满足且不属于“文体例外”时才处理。每个实例只使用 `resolved`、`review_required`、`fail` 三种状态：

- `resolved`：已删除、合并或改写，且事实关系未变。
- `review_required`：是否成立或如何处理需要结合作者意图、模板或证据判断。
- `fail`：会造成事实、证据、状态或整段重复问题，当前稿不能交付。

## S01 无信息开场或收尾

- 可观察现象：先宣布“下面将介绍”，或最后只说意义重大、前景广阔、希望有帮助。
- 成立条件：整句没有增加对象、事实、范围、结论或必要导航。
- 文体例外：长文导语确实说明范围；摘要首句交代研究对象；交付说明写清文件和限制。
- `blocking_when`：整段仅由元话语组成。
- 处理：删除；确需导航时改成具体范围或结论。

中文正文还要检查常识铺垫：若当前读者已知，且后文推理并不依赖这段解释，可删除。首次出现的变量定义、计算条件、非专业读者需要的概念解释不属于无信息内容。用删后是否损失理解来判断，不按句子是否“基础”判断。

## S02 结论换说法重复

- 可观察现象：相邻句、段或章节反复表达同一判断，只更换词语。
- 成立条件：论点、章节功能和证据都没有变化。
- 文体例外：摘要、结论、申报表规定栏目或会议行动项承担不同功能的必要复述。
- `blocking_when`：整段逐字或近逐字复制，且模板没有要求。
- 处理：保留信息最完整的一处；必要复述压缩并适配新功能。

## S03 空洞拔高

- 可观察现象：把普通事实写成“重要支撑、坚实基础、深远意义、战略价值”，却没有对象和证据。
- 成立条件：删掉评价后事实不受影响，且材料没有给出评价依据。
- 文体例外：申报栏目明确要求写价值，并已有场景、指标或受益对象支撑。
- `blocking_when`：拔高改变结论强度或把局部结果写成普遍价值。
- 处理：写出具体影响及依据；没有依据就删。

## S04 强凑并列

- 可观察现象：为整齐而固定列两项、三项、四项，项目之间层级不同或有空项。
- 成立条件：并列由句式需要而非事实分类产生。
- 文体例外：模板规定栏目；确有同层级参数、步骤或比较项。
- `blocking_when`：强凑项目引入材料没有的内容。
- 处理：按真实层级合并、拆开或减少项目，不补齐空项。

## S05 过渡词堆叠

- 可观察现象：此外、同时、进一步、因此、综上连续出现，却没有真实递进、并列或因果。
- 成立条件：连接词删去后逻辑不变，或连接词声称的关系与内容不符。
- 文体例外：复杂推导中连接词确实标明逻辑步骤。
- `blocking_when`：错误连接词改变因果或证据关系。
- 处理：先恢复真实逻辑；能直接相接就删去连接词。

## S06 主体和动作消失

- 可观察现象：抽象名词、名词化短语和“开展……的推进”堆在一起，读者看不出谁做什么。
- 成立条件：句子无法回答主体、动作、对象或结果中的关键一项。
- 文体例外：标题、参数表、术语定义以及确需无主句的客观描述。
- `blocking_when`：主体缺失掩盖责任人、实验对象或数据来源。
- 处理：补回具体主体和动词；拆开不同动作。

## S07 伪转折或伪深刻

- 可观察现象：用“不是 A，而是 B”“看似 A，实则 B”“不仅是 A，更是 B”制造反转。
- 成立条件：A 从未被提出，删掉 A 后信息不损失。
- 文体例外：纠正文献误解、比较旧方案与新方案、限定概念边界。
- `blocking_when`：假转折歪曲已有观点或掩盖真实比较条件。
- 处理：直接陈述 B；真实比较则写清对象和条件。

中文正文中的“并不限于……”“这不意味着……”即使没有完整转折句，也按相同方法检查：先找它回应的真实观点，再判断删除会不会改变结论范围。无端设立反驳对象、删后又没有信息损失时直接删去，不换说法补回来。

例如，某段只介绍设备在仓库的部署方式，材料没有比较其他场所，也不需要说明适用范围，“应用并不限于仓库”可以删除；若材料明确区分室内外适用性，则不能删去该范围信息。“未测室外条件，结果不能直接用于室外部署”属于证据限制，须保留。例子只说明判断方法，不迁移其中的事实。

## S08 状态说过头

- 可观察现象：把计划写成完成，把设计写成实现，把仿真写成实测，把一次测试写成普遍结论。
- 成立条件：动词、时态、范围或结论强度高于证据。
- 文体例外：无。
- `blocking_when`：一旦成立即 `fail`。
- 处理：恢复材料中的准确状态、条件和范围；缺证据时不得保留升级后的说法。

## S09 同义词轮换

- 可观察现象：同一对象被轮流称作系统、平台、装置、载体，或为避重不断更换术语。
- 成立条件：换词没有区分概念，反而增加指代成本。
- 文体例外：不同词确实对应不同层级或部件。
- `blocking_when`：换词导致对象混淆、引用错位或参数归属错误。
- 处理：固定术语；重复术语本身不是问题。

## S10 句式和段落机械对称

- 可观察现象：连续句子长度、起法、并列数和段尾完全一致，内容被迫套进同一模具。
- 成立条件：结构整齐没有帮助比较、步骤或扫描，且造成冗余或信息错位。
- 文体例外：参数表、逐条答复、测试步骤、严格平行的比较项和模板字段。
- `blocking_when`：为了对称补造事实、删掉限制或改变层级。
- 处理：按信息关系决定句长和段落，不为“变化节奏”随机打乱清楚结构。

## 复核顺序

1. 先检查 S08 和所有事实保护项。
2. 再检查 S02 的全文重复。
3. 检查段落是否有功能和信息推进。
4. 最后处理句式层气味。

不要统计关键词命中数来代表质量。评测只统计人工复核后仍未解决的实例；原稿已经干净时，目标是保持为零。

# 文风词表与术语

## 数据位置

词表数据位于 `D:\BaiduSyncdisk\.agents\vocab\`：

- 路由入口：`目录.md`
- 中文文风：`中文/通用.md` 和对应文稿类型表
- 英文文风：`英文/通用.md` 和对应文稿类型表
- 全局术语：`术语.md`
- 候选、弃用项、非字面匹配和变更记录：`维护.md`

文风表固定为 `不建议 | 建议 | 例外` 三列，术语表固定为 `中文 | 英文` 两列。普通写作不读取 `维护.md`。

## 适用范围

本技能约束论文、申报书、技术文档、调研报告、会议纪要、审稿回复、正式函件和对外说明的正文，也处理经写作路由进入的通用中文文稿。正文包括聊天中待确认的段落、标题和图表说明，不以是否已写入文件区分。

普通对话、代码、注释、提交说明、引用原文、参考文献、文件路径、URL、LaTeX 命令和引用键不受词表约束。

## 自动交付检查

中文正文首次起草、续写、局部修改或审查前，按下方“加载”读取适用词表；同任务文体和规则未变时沿用。每批展示前由当前助手结合句子语境和例外检查，按[共同质量规则](../writing-router/references/common-quality.md)处理，不机械替换命中词。内容变化或无法确认已读内容时补读，不逐轮重复读取；英文仍沿用原有交付检查时机。

逐段检查不要求将聊天文本落为临时文件，也不要求每段运行扫描脚本。普通问答不触发正文检查；用户要求只审不改时只报告问题。

生成、重写或实质性修改完整正式文稿时，在首次提交完整稿给用户审阅前运行本技能。用户修改正文后，进入定稿、内容冻结或格式交付前重新检查当前文件；用户不需要再次提出“去 AI 味”或“检查用词”。

完整中文正式文稿先由 `writing-router` 或当前文体技能按共同质量规则检查通用 AI 写作模式，再由本技能运行个人词表审计；局部段落按前述语境检查处理。审计结果为 `clean`，或所有命中均已结合例外逐项处理并留有内部记录后，才算词表审计完成，不要求在交付正文时宣布结果。临时关键词列表和人工扫读不能代替完整稿的正式审计；`clean` 只代表没有词表命中，不代表正文没有空话、重复或不必要的防御性表述。

## 加载

先判断语言和文稿类型，再按 `目录.md` 读取最少文件：

- 中文申报书、调研报告、论文、审稿回复：`中文/通用.md` + 对应类型表。
- 其他中文文稿：只读 `中文/通用.md`。
- 英文论文、审稿回复：`英文/通用.md` + 对应类型表。
- 其他英文正式文稿：只读 `英文/通用.md`。

同一“不建议”在两张已加载文风表中同时出现时，任务类型表优先。需要统一术语时再读全局 `术语.md`；项目目录内存在 `术语.md` 时，项目表优先。

## 收录

触发语包括“以后别用 X，用 Y”“这个词太 AI”“记住这个用词”“收录术语”。

1. 先判断是否值得长期收录。用户明确要求以后统一采用，或该表达能够脱离当前句子形成适用范围和例外清楚的稳定规则，才进入正式表；同一技术对象需要固定中英文名称时，按术语处理。仅因某一句的主谓、动宾、并列或修饰关系不顺，或专业术语只是在当前句中使用不当，不写入词表，只修改当前文稿。
2. 判断它属于通用文风、某类文稿文风，还是中英文术语。
3. 用户已经明确给出“不建议、建议、例外”或“中文、英文”并要求收录时，查重和查冲突后直接写入对应正式表。
4. 只有候选、尚未确认的替换或互相冲突的写法写入 `维护.md` 的“待确认”；用户明确不采用的写法写入“不采用”。
5. 通用规则只进入通用表；任务规则只进入对应类型表，不重复抄写。
6. 普通字面词不登记匹配规则。需要覆盖词形变化、多个变体或非字面结构时，在 `维护.md` 的“检查补充”增加 `条目 | 匹配`，其中“条目”必须与正式文风表的“不建议”完全一致。
7. 术语只记录中文和英文。全局一致的术语写入全局 `术语.md`；只适用于当前项目的术语写入项目 `术语.md`。来源、领域和维护过程不进入日常术语表；必要说明写入 `维护.md` 的“变更记录”。
8. 用户确认替换规则后，检查当前指定文稿中语义相同的既有用法，包括标题、正文、表格、图引和图题，只修改确实适用的内容，不做全局盲替换。旧用法出现在图片内部时，将图片及对应文字列入图文核对事项，不以正文替换冒充图片已经修改。
9. 写入后重读目标表，确认列数、重复项、冲突和匹配规则对应关系。

不确定规则属于通用还是某类文稿，且这一选择会改变后续加载范围时，只问这一项。

## 盘点

用户要求盘点时才读取 `维护.md` 的“待确认”和目标文稿：

1. 只扫用户指定文件或当前交付稿，不扩展到整个磁盘。
2. 跳过代码、URL、路径、LaTeX、引用键、引用原文和参考文献。
3. 排除已在正式表和“不采用”中的条目。
4. 每轮只提交少量高价值候选，用户确认后再迁入正式表。

## 检查

优先检查 Markdown 或 LaTeX 源稿；DOCX 先由 `docx` 提取可审文本。使用：

```text
python -X utf8 ../ieee-manuscript-edit/scripts/audit_writing_memory.py \
  --file <稿件> \
  --vocab-root D:\BaiduSyncdisk\.agents\vocab \
  --language zh|en \
  --document-kind general|proposal|research-report|paper|review-response|letter|other \
  --output-format json|markdown
```

状态含义：

- `clean`，退出码 0：没有命中。
- `review_required`，退出码 1：有命中，需要结合句子和“例外”判断。
- `error`，退出码 2：稿件、词表或规则无效。

命中不等于必须修改。逐条核对例外，只改确认不合适的句子，不做全局盲替换；修改后复扫，最多三轮。专业术语不进入禁用词检查，另行用全局与项目 `术语.md` 核对一致性。

## 验收

- 文风表只有三列，术语表只有两列。
- 任务表覆盖通用表时，加载结果以任务表为准。
- 正式规则、待确认、不采用和检查补充各有唯一位置。
- “检查补充”的每个条目都能对应一条正式文风规则，匹配表达式有效。
- 检查报告给出命中位置、建议和例外，不自动改稿。
- 代码、URL、路径、LaTeX、引用键、引用原文和参考文献不产生命中。

# 调研报告

审计脚本仅依赖 Python 3.11+ 标准库；联网取证需同时使用 `web-access`。

## 入口

从 [writing-router](../writing-router/SKILL.md) 接收：

- `document_type=research_report`
- `mode=evidence_report|decision_report|final_audit`
- `edit_scope`、`language`、`loaded_refs`

建立或沿用写作上下文后、处理正文前，读取[文稿协作](../writing-router/references/collaborative-writing.md)，按其中的范围和例外选择处理方式，并将实际路径记入 `loaded_refs`。直接调用本技能时同样执行；本轮已读且处理方式未变时沿用。

读取 [共同质量规则](../writing-router/references/common-quality.md)。中文正文首次起草、续写、局部修改或审查前，同时读取 [AI 气味目录](../writing-router/references/ai-smell-catalog.md)，按共同质量规则的“中文正文展示前检查”加载适用词表并逐批检查；同任务未变时沿用。英文仍在完整草稿、结构重写、终稿审校和 `audit_only` 时读取气味目录。

再按 [工作模式](references/modes.md) 读取最少参考文件。私有样稿入口为 `D:\BaiduSyncdisk\.agents\writing-profile\index.md`；只有 `research_report` 样稿获批时才加载。

局部润色和从现有正文提取摘要时，先沿用原文的事实与结论范围，不因题目含“采购”“选型”就增加决策建议。`mode` 规定文体能容纳什么，不扩大本轮改动授权；没有要求新增建议时，不补采购、验证或暂缓安排。材料中已核实的未完成状态属于对象事实，按其对判断的影响保留，不当作编写者的资料缺口移出正文。

提取摘要时，先在原文中定位要概括的结论句，按共同质量规则选择必要信息，不把单项满足改写成综合推荐。对象状态是否入摘要取决于它是否限制这句结论，不按状态清单逐项补齐。区分材料中的单项比较与产品的实测验证：按报价比较交期，不等于断言产品已经可用，不能把未验收自动接成该交期结论的转折。若摘要确实声称产品可用，则必须有相应验证依据。用户只要摘要时只交付摘要。

## 正式报告与内部台账

正式报告面向读者，只写已闭合的问题。内部台账记录检索过程、来源冲突、缺失字段和待取证事项。两类工件分开保存。

写正文前建立“读者问题—来源—论点—章节功能”关系：

| 项目 | 要求 |
|---|---|
| 读者问题 | 报告必须回答什么 |
| 来源 | 真实、可回查，含版本、地区和时间 |
| 论点 | 来源事实或由多条事实支持的判断 |
| 章节功能 | 范围、事实、比较、判断或建议 |

资料不足时不把未闭合问题写进正式报告，也不静默缩小用户要求。交付内部台账，指出缺哪条证据。

## `evidence_report`

正文只承担三类职责：

1. 定义与研究范围；
2. 有真实引用支撑的来源事实；
3. 基于已写事实形成的综合判断。

不生成行动建议。原稿中的建议转入内部映射表，除非用户将模式改为 `decision_report`。摘要最后写，只概括对象、主要发现和结论，不展示检索过程、资料缺口或内部编号。

详细内容边界见 [报告内容契约](references/report-contract.md)。

## `decision_report`

先完成与证据型报告相同的事实和判断，再根据用户需要写建议。建议必须：

- 明确针对哪个决策对象；
- 能回指前文事实和判断；
- 写清适用条件、代价、风险或触发条件；
- 区分“建议采用”“建议验证”“暂缓决定”等不同强度；
- 不把建议写成已经批准、已经实施或已经取得效果。

建议可以单列，也可以放在对应判断后，但不要与来源事实混在同一段。具体规则见 [决策报告](references/decision-report.md)。

## `final_audit`

按共同质量规则分点报告问题，核对：

- 每个关键数字、参数和结论能否回到真实来源；
- 来源事实、作者判断和建议是否分开；
- 摘要是否只是拼接各节首句；
- 同一结论是否跨节换说法重复；
- 报告模式是否与建议内容一致；
- 是否残留内部来源号、待补状态或虚构元数据；
- 结论和建议是否超过证据适用范围。

跨节事实矛盾、虚构数据或引用、整段无理由重复、状态升级直接判 `fail`。

## 写法

- 标题写具体对象或结论，不用“核心洞察”“关键抓手”等空标签。
- 一个段落只承担范围、事实、判断或建议中的一个主要功能。
- 定义只解释到读者能理解后文，避免在每个章节重复。
- 表格用于参数、来源和同条件比较；推理写成段落。
- 引用紧跟所支撑的句子。转载同一原始资料不算多条独立证据。
- 计算结果引用输入和方法，不写成来源直接发布的数据。

## 审计脚本

用于完整报告审计或用户明确要求的脚本检查。聊天内局部润色、改列表和提取一句摘要按共同质量规则直接核对，不为这些操作启动完整报告审计。Markdown 或纯文本文件可运行：

```text
python scripts/audit_report.py report.md --mode evidence-report --json
python scripts/audit_report.py report.md --mode decision-report --json
python scripts/audit_report.py research-ledger.md --mode internal-ledger --json
```

脚本只提供候选问题。关键词命中、行动词或句式整齐都需结合当前模式人工判断。

## 文件边界

正文按当前协作方式写回主稿，飞书主稿交给对应平台技能局部更新。实际写入本地 `.md` 或 `.tex` 前执行 [文稿版本保护](../writing-router/references/document-version-protection.md)。Word 交付按 [Markdown 到 DOCX 交接契约](../writing-router/references/markdown-docx-contract.md) 使用本轮按协作方式处理并审校的正文，再交给 `docx`；导出阶段不重新改写内容。

## 完成条件

- 用户要求回答的问题已经闭合，或明确留在内部台账；
- 关键事实和数字可回查；
- 事实、判断和建议的身份清楚；
- `evidence_report` 没有行动建议，`decision_report` 的建议有证据和适用条件；
- 没有内部编号、无理由重复或虚假完成状态；
- `loaded_refs` 与实际读取一致。

# 工作模式

`mode` 决定报告承担什么职责，`edit_scope` 决定本轮能改多大范围。两者不能混用。

模式表示允许的内容类型，不要求每个片段凑齐这些类型。对已有段落做局部润色、改列表或提取摘要时，沿用现有内容职责；除非用户要求提出或修改建议，否则 `decision_report` 也不新增建议。不要仅凭“采购”“选型”等主题词，把事实比较片段升级成新的决策稿。

## 模式

| `mode` | 适用情况 | 正文可包含 |
|---|---|---|
| `evidence_report` | 读者要了解事实、比较和研究结论 | 范围、来源事实、综合判断 |
| `decision_report` | 读者要据此选择方案或安排验证 | 范围、来源事实、综合判断、证据支持的建议 |
| `final_audit` | 已有完整报告，准备冻结或交付 | 审计结果；只有用户要求修改时才改正文 |

## 与 `edit_scope` 的组合

- `draft`：从已闭合证据生成新稿。
- `structural`：先做内容清单和旧段落映射，再重排。
- `bounded`：只处理指定章节。
- `in_place`：保持章节，只压缩重复、修复混写和表达问题。
- `audit_only`：保持只读，按共同质量规则在对话中分点报告位置、问题、原因和必要的修改建议。

只有主题、读者或研究问题而没有闭合证据时，不生成正式报告。先建立 [内部调研台账](research-ledger.md)，持续取样转 `baseline-research`。

## 最小参考文件

| 任务 | 读取 |
|---|---|
| `evidence_report` | [report-contract.md](report-contract.md)、[research-ledger.md](research-ledger.md) |
| `decision_report` | 上述两份 + [decision-report.md](decision-report.md) |
| 结构重写 | 再读 [restructure-existing.md](restructure-existing.md) |
| `final_audit` | 只读与当前报告模式对应的文件 |

## 读者测试

报告接近完成时，用正文回答四个问题：

1. 报告研究什么对象和范围？
2. 最可靠的发现是什么？
3. 哪些是来源事实，哪些是作者判断？
4. 若为决策报告，每项建议依据什么、在什么条件下成立？

必须靠口头补充才能回答时，先补证据或重写正文，不用更长摘要掩盖问题。

# 报告内容契约

## 作用

本契约约束 `evidence_report` 的内容职责，也是 `decision_report` 的事实与证据底线。它不是章节模板；章节数量、顺序和名称由读者问题及已闭合证据决定。

`decision_report` 还需读取 [decision-report.md](decision-report.md)。该文件只替代本契约中“正式报告不得写建议或行动内容”的限制；内部编号、未闭合证据、来源真实性、事实与判断分离和完成状态等要求继续有效。

先区分两份工件：

- 正式报告回答已经完成调研的问题；
- 内部调研台账记录取证过程、未闭合问题、来源冲突和后续任务。

两者不能拼在同一份交付稿中，也不能把台账里的状态语句改得更委婉后放进报告。

区分编写者未完成的取证与调研对象的真实状态：缺少来源、引用待补属于内部台账；有材料支持的未验收、未测试或未批准属于来源事实。这类状态只在它实际限制的判断处保留，不作每段的固定收尾。局部润色保留原稿的对象状态；摘要按自身结论选择必要限制，不复述无关的核对过程或未完成事项。不能将未完成改成已完成或新的执行条件，也不能添加无依据的免责说明。

## 正式报告的三类内容

| 类型 | 回答的问题 | 可以包含 | 不应包含 |
|---|---|---|---|
| 研究范围与必要定义 | 讨论什么 | 对象、地区、时间、资料截止日、必要术语 | 未完成事项、缺失字段、冗长名词解释 |
| 来源事实 | 已核验材料实际说明什么 | 原始数据、公开参数、政策原文、访谈原意、正式引用 | 作者没有来源的推断、内部编号 |
| 综合判断 | 已闭合事实合在一起意味着什么 | 比较、归纳、因果分析、结论 | 新出现的事实、数字、行动指令、免责语句 |

正式报告不设“证据范围与待核实事项”“资料缺口”“引用待补”“后续调研”等章节，也不在摘要、正文、脚注、参考资料说明或附录中呈现它们。

## 内部台账的职责

内部台账可以使用 D/F/J/R/U、S-01、S01 等工作标记，记录：

- 尚未闭合的问题及原因；
- 来源冲突、缺失字段和检索范围；
- 引文元数据补全情况；
- 原稿中无依据数字、行动句和删除理由；
- 下一轮取证任务及完成状态。

台账格式与闭合条件见 [内部调研台账](research-ledger.md)。它不是报告正文、附录或参考资料。

## 研究闭合门

开始正式起草前，逐项核验每一个用户要求回答的问题：

1. 有直接支持结论的真实来源；
2. 事实、时间、地区、产品版本和统计定义一致；
3. 引文信息足以形成真实、可回查的正式引用；
4. 来源冲突已解决，或该问题已由用户明确从报告范围排除。

任一条件不满足时，问题留在内部台账，继续调研。不要用“待补充”“还需要资料”“现有材料只能说明”“尚不能判断”这类句子让未闭合的问题进入正式报告。

也不要静默缩小用户已经要求的研究范围。需要改变范围时，先由用户确认，再据此修改正式报告的研究范围。

## 段落规则

一个段落只承担一种主要任务。段落可以包含多条同类事实，也可以在同一判断段中比较多条已经写明来源的发现，但不要在一句术语解释后立刻接市场结论，再以行动要求收尾。术语定义只放在“范围与术语”或独立背景节，并在全文完成一次即可；主体发现段不重复“X 是……”的定义，而应直接进入对象、事实、比较或判断。

推荐顺序：

1. 在范围节给出读者理解结论所需的最少定义；
2. 在主体节写来源事实和正式引用；
3. 另起段落写基于这些事实的判断。

原稿中的建议、下一步、参数冻结安排和后续验证计划只在重构映射表中记录处理结果。除非相应事实已经独立闭合，否则不能改写成“结论成立所需的证据条件”放进正式稿。

## 章节选择

先列读者问题，再选择模块。读者问题是内部分析工具，不是正式标题。

| 已闭合的读者问题 | 可选模块 | 使用条件 |
|---|---|---|
| 报告研究什么 | 范围与术语 | 对象容易混淆，或定义会改变结论 |
| 当前发生了什么 | 现状与进展 | 有可核验事实和时间线 |
| 有哪些产品或参与者 | 产品或参与者比较 | 比较项使用同一时间、地区和产品定义 |
| 需求有多大 | 需求与规模 | 有定义、分母、时间和来源一致的数据 |
| 技术方案如何比较 | 技术条件与方案比较 | 比较标准来自实际使用条件 |
| 已有事实支持什么结论 | 综合判断 | 所有支撑事实和引用已经在正文展开 |

没有闭合证据的问题不能通过添加“公开数据缺口”“待确认项”或“判断条件”成为报告章节。先进入内部台账和补证据流程。

### 从读者问题到正式标题

正式标题应说明研究对象、分析方面或已经得到的结论。除非用户明确要求问答体，不把内部问题原样搬进目录。

标题只在读者问题、证据类型或分析对象发生切换时设置。一个标题下只有一段短说明、少量零散参数或一张表，而相邻内容仍围绕同一对象和同类证据时，优先并入相邻章节；不要为了目录整齐另设薄标题。标题数由论证结构决定，不按篇幅或固定模板凑齐。

优先使用：

- 研究范围与术语；
- 公开试验进展；
- 终端产品参数；
- 业务状态判断；
- 市场规模测算。

避免使用：

- 这份报告要帮助项目团队判断什么；
- 当前应如何推进；
- 还缺什么证据；
- 核心洞察；
- 战略启示。

目的陈述直接写研究动作和判定对象，例如“评估业务开放状态”“比较候选终端的安装条件与功耗”。不描述报告在“帮助谁想明白什么”。

## 信息顺序

默认按读者理解结论的过程排序：

1. 本报告研究什么；
2. 最可靠的发现是什么；
3. 每条发现由哪些来源支持；
4. 这些事实支持什么结论。

技术教学内容只有在读者不理解它就无法判断发现时才进入正文。较长原理说明放入独立背景节或附录，不穿插在每个产品和市场段落中。

## 摘要契约

摘要最后写。它包含研究对象、最可信的两至五项发现和报告结论；这些是内容检查项，不是固定句序、段落数或可见标签。

正式摘要围绕一条判断链写成一个或少数几个自然段。先从最重要的发现或结论切入，再用事实和推理关系组织后文。可以用一句自然的范围交代作开头，但不能把“研究对象、主要发现、证据限制、当前含义”逐项变成四字标签或同构段落。只有用户明确要求结构化摘要时，才使用可见分项；即使使用分项，每项也必须是完整判断，不得只是章节标题的改写。

摘要不承担以下任务：

- 逐个解释轨道、频段、器件、政策主体等名词；
- 罗列报告目录；
- 引入正文没有证据的新数字；
- 交代待核实、待补充、未公开、未列明、引用待补或检索过程；
- 用“前景广阔”“空间巨大”等套话代替发现；
- 写行动指令或条件性建议。

摘要和正文都避免连续否定（如“不是没有”“并非不存在”“不能不”）以及没有证据作用的弱化限定语（如“在一定程度上”“相对而言”“某种意义上”“不排除”）。如果结论存在可量化的不确定性，写出条件、区间、样本或来源；不能用模糊缓冲词替代证据。

## 证据和引用

先建立内部来源清单和来源—断言台账，再写正文。每条来源只记录实际获得的信息：题名、发布主体或作者、日期、文号、DOI、URL、访问日期、本地文件位置及内部键；每项关键事实或判断都记录其来源实际支持的对象、时间、地区、版本和数值范围。不得根据文件名、机构惯例或上下文猜测缺失字段。

S-01、S01 等是内部证据编号，只能留在来源清单、台账或重构映射表中。正式稿不得沿用它们充当引用。应按用户指定格式生成脚注、尾注或编号参考文献；未指定时可用顺序编码，但文内编号必须与文末真实来源逐项对应。

来源元数据不能满足正式引用规范时，先在内部台账补齐。不要虚构作者、发布机构、题名、文号、日期、DOI 或 URL，也不要把不完整条目伪装成已经核验的正式参考文献。

每处引用放在它实际支持的句子或紧邻段落。综合判断回指已经展开的事实、章节或正式引用。计算结果引用输入与计算方法，不冒充来源直接发布的数字。“尚未公布”“尚不能说明”等句式只提示复核：若有具体对象和来源、且确实限制当前判断，保留必要内容；没有信息作用的防御性模板句删除。编写过程中的资料缺口留在内部台账，不把它包装成对象事实。

## 自然中文

先写清主语和动作，再补条件。标题直接说内容。需要强调时补数据或来源。

不要把内部完整性清单搬进正文。用户列出的研究对象、主要发现和结论只是语义覆盖要求，不能直接变成三四个可见字段，更不应变成句首四字标签。

摘要应围绕事实和结论组织，而不是按清单逐段排列。短报告通常用一个摘要段；材料较多时，按自然的因果或对比关系分成两段。

优先：

- “两县行业应用试点已完成现场演练。[1]”
- “三款候选终端的重量和功耗采用同一测试条件后进行比较。”
- “样机参数对应工程验证用途。”

避免：

- “政策端释放积极信号，产业化进程有望全面提速。”
- “多维度洞察行业演进逻辑，构建端到端能力闭环。”
- “在市场规模方面，整体呈现蓬勃发展的良好态势。”
- “资料没有 A，也没有 B，因此不能 C，无法 D。”

也删除只说明材料或来源作用、没有新增对象、时间、数据或适用条件的句子，例如“这些材料共同构成……基础”“为……提供依据”“作为外部参照”。直接写来源实际列出的事实，或删除该句。

# 内部调研台账

## 作用

内部调研台账记录尚未闭合的问题和取证过程。它服务于研究者，不是正式报告的章节、附录、脚注或交付说明。

正式报告只引用状态为已闭合的记录。台账中的任何状态、内部编号或任务文字都不得复制到正式稿。

## 最小字段

每个需要继续处理的问题至少记录：

| 字段 | 说明 |
|---|---|
| ledger_id | 内部唯一编号，例如 U-01 |
| reader_question | 关联的读者问题或报告结论 |
| status | 已闭合、待取证、来源冲突、引文待补、范围待确认 |
| current_evidence | 已获得的来源、摘录、数据或原稿位置 |
| gap_or_conflict | 未闭合原因、冲突点或缺失字段 |
| next_research_action | 下一项可执行的取证动作 |
| citation_status | 是否已具备正式引用所需的真实元数据 |
| formal_report_disposition | 不进入正式稿、待闭合后进入、或经用户确认排除 |
| owner_and_date | 责任人和最近更新时间 |

来源可另建明细表，保留题名、发布主体或作者、日期、文号、DOI、URL、访问日期、本地文件位置和内部来源键。

## 来源—断言台账

除问题台账外，为进入正式稿的每一项关键内容建立内部对应关系。它用于核验“这句话凭什么成立”，不作为正式报告的附录。

| 字段 | 说明 |
|---|---|
| claim_id | 内部断言编号；可对应一条来源事实或一条综合判断 |
| claim_text | 准备写入正式稿的最小事实或判断，不写行动要求 |
| claim_type | 来源事实或综合判断 |
| source_key | 实际来源记录的内部键；正式稿不得直接使用 |
| support_scope | 来源实际支持的对象、时间、地区、版本、数值或原意 |
| evidence_level | 一手、可追溯转引、访谈记录或其他已定义等级 |
| conflict_or_limit | 与其他来源的冲突及其处理状态；未闭合时不进入正式稿 |
| formal_citation | 闭合后采用的脚注、尾注或 `[n]` 编号 |
| formal_location | 正式稿中的章节和段落位置 |

一条来源事实必须能回到至少一个实际来源；一条综合判断必须回指已经展开的来源事实。来源仅支持局部条件时，不得扩展成更大范围的结论。同一问题存在相反材料时，先在台账保留各自的适用条件和冲突处理，再决定是否能形成正式判断。

## 闭合条件

一条记录只有同时满足以下条件，才能进入正式报告：

1. 它回答了用户已定义的一个问题；
2. 有真实来源直接支持相邻的事实或结论；
3. 时间、地区、产品版本、统计定义和单位可比；
4. 来源冲突已解决；
5. 引文信息可按选定规范生成并回查。

“获得一份资料”“找到一个网页”“名称和日期已记录”不等于研究闭合。

## 与正式稿的分工

| 内容 | 正式报告 | 内部调研台账 |
|---|---|---|
| 已核验事实 | 写入正文并正式引用 | 保留来源摘录和核验记录 |
| 无依据数字 | 不写 | 记录删除理由和取证任务 |
| 缺失字段 | 不写 | 记录来源、字段和检索状态 |
| 来源冲突 | 不写成免责语句 | 记录冲突、判定依据和处理状态 |
| S-01、D/F/J/R/U | 不写 | 可作为工作键 |
| 行动或后续安排 | 不写 | 可记录内部任务 |

## 转入与关闭

重构已有报告时，每个转入台账的内容在 restructure-map.md 中保留 ledger_id 和理由。正式新稿只保留已闭合内容。

若用户要求的核心问题仍处于待取证、来源冲突或引文待补状态，报告不能标为完成。继续调研，或由用户明确调整研究范围；不要通过添加“待补充”“尚不能说明”“结论还需要资料”等句子绕过闭合门。
