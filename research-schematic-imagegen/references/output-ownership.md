# 输出文件所有权与非破坏性整理

科研图目录常同时保存历史定稿、其他课题图和本轮候选图。目录名称是 `final` 不表示其中所有文件都由当前任务管理，也不授权代理整理既有资产。

## 所有权判定

- 任务开始前已存在的文件视为用户资产。
- 当前任务新生成、复制或编辑出的文件才属于本轮可管理集合。
- 用户明确点名要求替换、移动、重命名或归档的既有文件，才进入本轮可管理集合。
- 无法确认来源时按既有用户资产处理。

未经用户明确授权，不得对既有用户资产执行：

- 删除
- 移动或归档
- 重命名
- 覆盖
- 改写内容或元数据

## 开始任务前

写入任务过程目录中的 `prompt/`、`working/` 或项目根目录成果前，先只读列出目标目录已有文件。至少记录路径、大小和修改时间；高风险整理任务再记录哈希。

发现目标文件已存在时，不自动覆盖。使用新文件名或请求用户确认。

## 原始图与处理版

生成接口、宿主工具或网页实际提供的自然尺寸结果先作为来源文件保存。目标尺寸是生成约束，不是自动后处理授权；返回尺寸不符时，只记录偏差并保留原图。只有用户明确同意后，才能另存裁切、缩放、拉伸、补边、扩图或合成后的处理版。

- `original`：未经裁切、缩放、拉伸、补边、扩图或合成的实际返回文件。能够取得服务器文件字节时，副本必须与来源逐字节一致。
- `processed`：经用户明确授权后产生的派生版本。不得覆盖原图，也不得在记录或回复中称为原始生成图。
- 浏览器自然尺寸像素导出是重新编码结果，不属于服务器原始文件；仍须保留其未再处理的导出版，并在 `record.md` 中写清来源类型。

原图和处理版同时交付时，manifest 使用对象条目记录角色和各自尺寸。旧的纯文件名数组继续兼容：

```json
{
  "files": [
    {
      "name": "scene-original.png",
      "role": "original",
      "width": 1672,
      "height": 941
    },
    {
      "name": "scene-processed.png",
      "role": "processed",
      "width": 2048,
      "height": 1152
    }
  ]
}
```

## 最终交付

“用户要求 N 张图”约束本轮交付清单，不约束一个已存在目录中的历史文件总数。

优先顺序：

1. 保留本轮 manifest 供图片校验；来源、可编辑源与导出路径映射、生成请求和实际检查结果复用已有制作记录，仅缺少承载位置时使用 `过程文件/<任务主题>/record.md`。
2. 选定或无需确认且检查通过后，自动非覆盖复制到项目根目录，复核哈希，再用 `verify-output.js --dir <project-root> --manifest <过程文件/任务主题/manifest.json>` 只验证清单中的文件。
3. 目录存在其他 PNG 时，将其报告为 `extra_files`，不移动、不删除，也不把它们视为本轮失败。
4. 默认不新建成果层级，直接交付根目录文件链接；只有用户明确要求其他位置时才按其指定位置交付。
5. 用户明确要求清理既有目录时，先列出拟移动文件和目标路径，得到确认后再执行。

manifest 示例：

```json
{
  "files": [
    "fig1_final.png",
    "fig2_final.png"
  ]
}
```

统一尺寸的旧清单可以继续使用字符串条目和全局 `--width/--height`。对象条目中的逐文件尺寸优先于全局尺寸，适合原图与处理版尺寸不同的交付。

### 多图项目与续做的版本选择

多张图、多个候选或跨对话续做时，复用已有清单记录当前采用路径；本轮 manifest 已足够时不另建项目级清单。已有项目清单的 `path` 仍相对项目根目录，指向实际交付文件，历史记录继续保留。可编辑源的路径记录在现有制作记录中，PNG 导出使用原有 manifest 校验；脚本不负责验证 PPT／SVG 的可编辑性。

- 每张图明确一个当前采用路径；历史 `status=confirmed` 只表示真实的用户确认，不能因智能体检查通过就补写。
- 复用现有图号、图题、路径、哈希、尺寸和引用信息；已有授权且无需用户选图时，依据任务及实际检查更新当前路径即可，不要求新增确认字段或状态机。
- 图题准确对应当前正文的技术含义即可，复用已确定名称，不要求与章节标题逐字一致。
- 不按文件名中的 `v2`、`v3`、`确认版`，不按修改时间，也不按文件位于 `final/` 就判断哪一版更新。
- 用户选定新版本，或无需选图的已授权任务检查通过后，先非覆盖保存文件，再更新所复用清单与哈希，继续已授权的文稿引用或插图。不要把历史版本的确认状态复制给未获用户确认的新版本；新交付可直接使用原有不含状态的 manifest。
- 清单缺失或冲突时，读取当前文件、任务授权、既有选图决定及实际检查记录，能够确定则继续；仍有两个实质不同且无法判断的候选时只询问版本选择。用户手工修改过的源文件先重新读取，再在副本上检查和导出。

历史用户确认条目示例（原格式继续保留，不作为新交付的必填模板）：

```json
{
  "number": 17,
  "title": "实时波束解算与控制技术",
  "status": "confirmed",
  "path": "图17_实时波束解算与控制技术_v03.png",
  "sha256": "<64位SHA-256>",
  "width": 1536,
  "height": 1024,
  "markdown_references": [
    {
      "document": "课题4.md",
      "display_number": 17
    }
  ]
}
```

验证示例：

```powershell
node <skill-dir>/scripts/verify-output.js `
  --dir <project-root> `
  --manifest <manifest.json> `
  --expected-count 2 `
  --json
```

## 过程材料保留与清理

普通任务结束时保留全部过程材料，不自动删除缓存、失败尝试或旧候选。只有用户手动触发 ChatNote 或明确要求清理时，才进入可恢复清理流程；不因目录名为“过程文件”就整目录删除，保留原件、可编辑源和必要依赖。

## 允许归档的范围

可直接移入 `working/` 或本轮归档区的内容仅限：

- 本轮生成的过程候选图
- 本轮生成后被用户明确否定的版本
- 本轮创建且已被新版本替代的临时遮罩、裁剪和诊断图

历史定稿、其他课题图、来源不明文件不属于“过程版本”。

## 冲突处理

如果目录总数与用户要求不一致：

1. 不做任何文件移动。
2. 验证本轮 manifest。
3. 报告额外文件名称及其“非本轮管理”状态。
4. 只有用户明确要求目录清理时，才提出可逆的移动方案。

如果已经误移动既有文件，立即停止后续整理，保留路径映射和哈希；先向用户说明，再经用户确认执行原位恢复。
