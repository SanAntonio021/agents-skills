# Skill 升级候选审查

当本轮对话可能补强一个或多个现有 skill 时读取本文件。这里是内部检查表，目标是先判断“值不值得升级、升级什么”，再把结论改写成用户容易理解的几句话。不要把本文件的栏目名原样堆到用户回复中。

## 候选门槛

一个 skill 只有同时满足以下条件才进入候选：

1. 本轮对话提供了可指认的证据，例如用户纠正、已验证的新流程、反复出现的失败模式或稳定输出需求。
2. 经验属于该 skill 的职责，且换到同类任务仍有用；不要把所有经验都写回 `chat-notes`。
3. 逐字检查现有 skill 后，能够指出没有规则或规则不完整的具体位置。规则已经明确但本轮没执行，不构成升级理由。
4. 能说清准备提取什么，以及提取后要改变哪个判断、步骤或交付物。
5. 能选出合适落点，不把细节全部塞进 `SKILL.md`。

单次严重失败、安全边界缺失或用户明确指出稳定需求时，可以成为候选，但仍要满足职责和缺口检查。候选之间按影响和证据强度排序，通常保留 1～3 个；证据不足的目标不靠“低优先级”混进清单。

## 落点选择

| 内容性质 | 推荐落点 | 判断方式 |
| --- | --- | --- |
| 会改变触发、分流、顺序、权限或停止条件 | `SKILL.md` | 每次使用该 skill 都需要知道 |
| 较长的领域知识、检查表、案例或条件化流程 | `references/<topic>.md` | 只在特定模式下读取 |
| 会复制或改造成用户交付物的固定骨架 | `assets/` 中的模板 | 模板本身属于输出材料，不当作指令加载 |
| 稳定但需要模型阅读后填写的格式或样例 | `references/` 中的模板说明 | 重点是指导模型，不是直接复制文件 |
| 重复、确定、容易手工出错的转换或检查 | `scripts/` | 脚本能提高一致性，并可独立验证 |
| 防止本轮问题复发的真实场景 | `evals/` | 能观察候选规则是否改变行为 |

一个候选可以有多个落点，例如在 `SKILL.md` 增加分流入口，在 `references/` 保存详细检查表，并在 `evals/` 增加回归场景。每个落点都要对应具体内容，不能只写“完善规则”“补充模板”。

## 每个候选内部要回答

- **目标 skill**：名称和源码目录。
- **为什么值得升级**：本轮证据及其可复用价值。
- **现有缺口**：没有规则，还是规则不完整；具体缺少对象、边界、顺序或检查方法中的哪一项。
- **需要补强**：升级后应改变什么行为或结果。
- **拟提取内容**：从本轮提取的判断规则、检查表字段、参考知识、模板栏目、脚本能力或回归场景。写清内容轮廓，不写成可直接应用的补丁。
- **建议落点**：精确到 `SKILL.md`、`references/<topic>.md`、`assets/<template>`、`scripts/<helper>` 或 `evals/evals.json`；新建文件时说明现有文件为什么不能承载。
- **外部借鉴**：只有实际影响候选时才写来源、指标、可吸收内容和明确不吸收的边界。

这些问题必须在内部有答案，但用户通常只需要知道三件事：为什么要改、准备做什么、现在是否需要他批准。把上述答案合并进自然短句；只有用户要求详细依据时才展开字段、源码路径或外部对比。

## 审查与执行边界

审查阶段不给 Git diff、整段替换文本、完整 `SKILL.md` 或可直接落盘的新文件。内部准备的内容要具体到足以确认修改范围，用户稿则用普通聊天的方式说明原因和准备做的事。用户批准某个候选后，才按批准的目标和落点调用 `skill-creator` 正式编辑；批准一个候选不等于批准清单中的其他候选。

高 stars、高安装量只说明值得检查，不证明适合本地。外部 skill 可以贡献判断标准、字段、模板结构或测试场景；自动监听、遥测、自动写入、自动安装、自动提交等机制除非用户单独授权，否则只列为不吸收边界。
