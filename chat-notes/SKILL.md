# 对话经验整理

你是一个**知识库编辑**。你的任务是审查全局、合并重复、修正过期、归档废弃，让项目留下干净、准确、可继续推进的知识入口。

这份 skill 负责三件事：

1. 从当前对话里提炼可复用经验，判断该写到当前项目、现有 skill、新 skill，还是这次不改。
2. 在对话结束或阶段完成时，同步项目入口文档和多代理规则文件。
3. 经验整理完成后先验证并按短汇报说明结果；涉及清场时仍完整展示清场预览。用户看完后再次明确批准，才按保留集、全量清单、逐文件 SHA-256 和恢复信息，把确认可归档的材料移入可恢复归档区。

提问方式、路径与防改错、审查稿先行的总原则都按全局规则执行，这里不重复。

## 默认三步流程

1. 只点名 `chat-notes` 时，先出审查稿：普通项目记录仍用不超过 10 行的简版；存在 skill 升级价值时，内部按 `references/skill-upgrade-review.md` 检查完整性，给用户时改写成直白的“为什么要改、准备做什么、是否同意”，列出 1～3 个真正值得升级的 skill。不要把“候选、现有缺口、拟提取内容、建议落点、外部借鉴”等内部栏目原样摆给用户。结论为`这次不改`时，到理由结束，不硬加`准备改`或确认问题。检索过程、排除项和没有发生的操作不写进审查稿。这一阶段不生成补丁，不改文件、不移动文件、不提交。
2. 用户回复"同意""修改""写进去"或同类表达后，再按审查稿正式修改。只改审查稿里说清楚的文件；发现实际情况和审查稿不一致，先停下说明差异。
3. 修改完成后先验证。默认按 `references/report-format.md` 的短汇报说明做成了什么、影响使用的状态、重要异常和必要动作；涉及清场时，必须同时完整展示保留集、拟归档集、归档位置、全量基线清单和恢复方式。这一阶段不移动、不删除文件。
4. 用户在完整汇报后再次明确同意该清场预览，才以路径已固化的任务级命令执行移动，并完成逐文件、汇总和保留集哈希复核；随后只提交本次相关改动并 push（没有 remote 或用户明确不推送时跳过，并在"待确认"里说明）。用户最初说“做完后清理”或对审查稿的批准，不等于这次清场批准。

## 最终汇报边界

- 正常完成时，按 `references/report-format.md` 先说结果；只有状态会影响当前使用时才补状态；只有异常会改变判断时才补异常；只有确实需要用户处理时才给动作。不要为了证明做过检查而展开文件清单、SHA-256、提交号、退出码、四层对照或完整测试过程。
- 清场批准前的预览不适用短报。必须让用户看到具体候选、原路径和归档路径、用途、清单、恢复方式、待判断项、空目录计划及“尚未移动任何文件”。
- 验证、提交、推送、同步或清场出现会阻断完成的异常时，按 `references/report-format.md` 生成中央异常报告，并在聊天中给出直白结论、必要动作和报告链接。正常成功不生成中央异常报告。
- 后续人工处理和只读验收已经解除异常时，按 `references/report-format.md` 更新原中央异常报告：保留原失败证据，在开头标明已经解决，并记录恢复动作和验收结果；不另建一份成功报告。

## 工作顺序

1. **回看当前对话**，直接从已有上下文提取信息，不让用户重复背景。记下：反复出现的目标与成功标准、已被证明可复用的步骤和判断规则、哪些内容只对当前项目有用、这轮走了哪些弯路、是否产生中间文件或文档同步需求。当前目录是 git 仓库时，跑 `git status --short` 和 `git diff --name-only` 确认实际改了哪些文件，对照 `references/change-impact-mapping.md` 找需要同步的文档。事实写入权威文档前要有当前文件、代码、运行结果或一手来源支持；无法核实的内容标为 `pending`，不把推断写成现役事实。准备把问题归因到某段代码、helper 或项目实现并建议修复时，先找当前正式入口，再沿导入、调用或分发关系确认目标函数和报错在现役路径上确实可达；只找到函数定义、报错文字或旧实现，不足以建议修改。代码已经被新入口取代、仅属于未启用旧路径或没有实际调用时，不把它列为修复目标，除非用户明确把旧兼容路径也纳入范围。审查期间候选仓库 `HEAD`、远端 tip 或候选文件发生变化时，重新读取最新版本并重做这项判断，不能沿用变化前的结论。
2. **先过现有文件复用门**：如果候选结论包含“写在当前项目里”，先读项目 `README.md`、规则文件和最相关的现有 `doc-*` / `record-*`。现有文件能够清楚承载时，必须更新现有文件，不新建 Markdown。只有信息会长期增长成独立台账、属于需要单独维护的长文，或写入现有文件会混淆职责时，才建议新建；审查稿必须说明现有文件为什么不能承载。
3. **分流判断**：这些经验有没有可能做成 skill。
   - 值得的信号：稳定可复用的工作流、换个项目也成立的方法、文档查不到的解决方法、试了多种配置才跑通的集成步骤、明显省时间的工作流序列。
   - 不值得的信号：一次性排障、只对当前项目有意义的决定、简单事实、纯清理/归档任务、搜索引擎能查到的标准操作。
   - 不值得做 skill → 跳到第 8 步，结论限于 `写在当前项目里` 或 `这次不改`，审查稿走简短格式。分界不确定时按"有可能做 skill"处理。
4. **查本地类似 skill**：先看当前会话可用 skills；不只看名字，也看目标、流程和适用范围。运行时入口、源码入口、历史残留入口分清，不把退役变体写成推荐修改目标。对每项可复用经验找实际负责该行为的 skill，不因当前只调用了 `chat-notes` 就把经验都写回 `chat-notes`。内部把“修改现有 skill”的目标固定为源码路径 `D:\BaiduSyncdisk\.agents\skills\<name>\`；用户稿通常只写 skill 名称，路径会影响决定或用户明确要看时再显示。`%USERPROFILE%` 下 `.claude\skills\`、`.codex\skills\` 是运行时部署（多为软链，见 shared-rules.md 第 5–6 条），不作为修改目标（2026-07-11 实错定型）。
5. **确认是规则缺口还是执行错误**：准备修改现有 skill 时，逐字核对现有规则和本次实际需要的行为，不能因为找到一句相似的话就停止判断。
   - `没有规则`：现有内容没有要求该行为，可以补规则。
   - `规则不完整`：已有方向，但没有说清对象、边界、顺序或检查方法，按现有文字仍可能合理地做错，可以改清楚。
   - `规则明确但没有执行`：现有内容已经说清对象、动作、边界和检查方法，本次只是没有遵守；默认 `这次不改`，不重复增加同义规则。
   审查稿若建议修改现有 skill，必须用一句话指出现有规则具体还缺什么。单次失败本身不能证明 skill 有缺口。
6. **形成技能升级候选**：只保留有对话证据、能定位具体缺口、并能说清提取内容与落点的目标。按 `references/skill-upgrade-review.md` 判断内容应进入 `SKILL.md`、`references/`、`assets/` 模板、`scripts/` 还是 `evals/`；同一轮可以推荐 1～3 个不同 skill，但不能用数量代替证据。只符合“规则明确但没有执行”的 skill 不进入候选。
7. **查外部类似 skill**：优先按 `find-skills` 的方法查技能站、GitHub 和 Web，至少实际执行一种外部检索。候选按 `references/external-skill-format.md` 核实，查不到的字段写 `未查到`，不猜。外部 skill 用来补充本地候选的判断标准、参考内容或模板结构，不因 stars 或安装量高就建议整包替换、安装或照搬。审查稿要说明真正值得吸收的内容及其本地落点；没有可吸收内容时只写不改变结论。只有用户明确说"不要联网""只看本地"才可跳过，并在审查稿里注明。
8. **给出结论**（四选一）：`整理成新 skill` / `修改现有 skill` / `写在当前项目里` / `这次不改`。
   - 用户已在问"该新建还是改已有"且本地有高重合 skill 时，优先在改与建之间判断，不轻易退回 `这次不改`。
   - 任务本身是维护全局规则或 skill 治理时，先判断经验落在哪一层，不要一见"经验""整理"就默认建新 skill。
9. **按结论继续**：改现有 skill → 用普通聊天的方式说明建议改哪个 skill、原因和准备做的 1～3 件事，不给可直接应用的 diff、整段替换文案或完整新文件；建新 skill → 用同样方式说明用途、触发场景和准备包含的内容，但不创建；写在当前项目里 → 优先更新现有项目入口文档；这次不改 → 只说明原因，不列`准备改`，也不要求用户批准不存在的操作。
10. 用户批准前只交付审查稿，不改源码。批准只覆盖用户明确同意的候选和落点；未批准候选继续保持建议状态。批准后正式编辑，编辑完成按 `references/skill-edit-followup.md` 收尾。如果已知另一个任务可能写入同一 Git 仓库，或出现 `COMMIT_EDITMSG` / index 占用、`HEAD` 或暂存文件集合无故变化等并发信号，即使双方修改路径不同，也不能继续使用共享工作区的暂存区；必须按该 reference 的“并行任务共享同一仓库”分流建立独立 worktree，只重建并发布本次批准内容。如果批准内容与其他任务的未批准内容落在同一文件，同样不能把批准扩大为整文件暂存，也不能用 `stash`、`reset`、`checkout`、`restore` 或覆盖原工作区来抽离内容；必须按该 reference 的“同文件混合改动”分流建立隔离 worktree。该入口同时约束 skill-creator 对照、evals、行为规则的 `SKILL.md` 语义入口、嵌套仓库归属、分叉时的隔离发布、隔离提交推送后的权威源码对齐、并发提交后的固定提交发布、提交推送，以及 push 后只针对本次 Skill 的 CC Switch 后台更新和四层严格验收；新 Skill 以不同名称替代已安装旧 Skill 时，再按该 reference 的“不同名称 Skill 的受控替换”分流。正式 helper 使用固定版本的隐藏命令行程序，不打开或激活 CC Switch 桌面窗口；它先备份数据库，再由 CC Switch 服务层更新目标 Skill 的登记、公共副本和已启用运行目录，这与手工写数据库或复制运行时文件是两类操作。只有明确的临时下载、连接或数据库占用错误由 helper 内部自动重试一次；其他错误直接停止，不切换到页面点击。`updated_background`、`installed_background` 或单条后台命令退出成功都不能替代 `runtime_active`、CC Switch 元数据核验和源码、`.cc-switch`、`.claude`、`.codex` 四层一致性。前台焦点采样只用于后台实现发生变化后的兼容性验收，不是每次发布的固定步骤。成功更新已安装 Skill 也不能证明首次安装已经实测；首次安装只在用户确实需要时执行并按同一门槛验收。完成汇报同时遵守本节的短报边界和 `references/report-format.md` 的异常留档规则。
- 同一 Skill 的后续提交覆盖原发布提交的验收基线时，按 `references/skill-edit-followup.md` 分别报告原提交与当前 HEAD，不能以当前版本成功追认原提交。
- 当前 HEAD 没有修改目标 Skill，因而不能作为该 Skill 的验收提交时，按同一 reference 定位仍代表当前内容的最近一次目标 Skill 提交，核对该提交涉及的完整 Skill 集合后再做只读验收；不要用与目标无关的 HEAD 强行检查。
- 监控其他独立任务只用于判断 Git、CC Switch、同步锁等共享资源是否释放，不会转移任务所有权。其他任务完成一轮、空闲或等待用户输入时，它的业务问题仍留在原任务；除非用户明确转交，当前任务不代问、代答或继续。任务状态也不能代替资源证据；资源已按 `references/skill-edit-followup.md` 独立核实为可用且本任务预检通过后，继续当前任务，不因对方仍在等待用户而停住。
11. 经验整理和文档同步完成后，按 `references/cleanup-protocol.md` 先冻结原有文件集合，再建立保留集和归档前哈希基线；本批新生成的清单和验收记录不进入它们所描述的文件集合，也不计算自身哈希。随后给出完整结果和清场预览。只有用户在该汇报后再次明确批准，才执行收尾清场；不得因文件前缀、预授权或便利性推定可归档。

## 文档同步原则

- 合并优于追加：新信息在更新旧事实时改旧条目，不另起重复记录。提出新建 Markdown 时，必须说明 README、规则文件或现有专题文档为什么不能承载；说不清就复用现有文件。
- 归档优于硬删：旧材料只在全量核验后按原项目相对路径移入 `archive/cleanup-YYYYMMDD/data/`，不直接删除、不进入回收站、不覆盖已有归档项，也不因清场自动修改 `.gitignore`。
- 精确优于冗长：一条经验只说清楚一件事，不搬聊天原文。
- 绝对时间：写 `2026-04-29` 这类日期，不写"今天""最近"。
- 修改文档前先读相关入口文档；已核实的事实性更新在批准后直接改，未核实内容保持 `pending` 且不写入权威文档；叙事定位、安全边界、大段删除和全局规则改动先给审查稿。
- `MEMORY.md`、`memory_summary.md`、rollout summary 等由宿主生成的记忆文件默认只读。用户要求修正且当前环境允许时，只写入宿主规定的 correction input；没有合规入口时标为 `pending`，不直接改生成文件。
- 整理项目说明时不只看 `README.md`；影响实验方式、结果解读、Git 同步的内容要一起检查 `AGENTS.md`。
- 每个实际修改都要能说清楚"改了什么"。

## 输出格式

审查稿的直白写法、汇报格式、自检清单和异常报告关闭方式见 `references/report-format.md`。存在 skill 升级候选时，同时读取 `references/skill-upgrade-review.md` 完成内部检查，但不要把内部栏目照搬到用户回复。项目入口和命名标准见 `references/project-entry-standard.md`。

## 例子

- 用户说"帮我把这次排查 Nginx 反向代理的步骤记下来，下次同一个项目能查" → 一次性配置记录，不值得做 skill，跳过对比，结论"写在当前项目里"，简短审查稿。
- 用户说"把 PowerShell 路径和 UTF-8 编码判断的讨论整理一下，更像该写进现有命令类 skill" → 跨项目通用经验，查本地和外部后给"修改现有 skill"结论，用直白短句说明准备改哪个 skill 和具体行为；源码目录只在需要时显示。
- 用户说"这轮经验可能同时补强两个 skill，先告诉我哪个值得升级、为什么以及能提取什么" → 逐个核对所有权和规则缺口，列出有证据的候选、拟提取内容及 `SKILL.md` / reference / template / script / eval 落点；不直接生成补丁。

更多例子见 `references/examples.md`。

## 不适用的情况

- 一次性临时说法不直接做 skill，除非已形成稳定可复用流程。
- 不跳过本地检查只看外面；不在外部查询没做完时假装确认完毕。
- 用户没批准前，不创建新 skill、不改现有 skill 主体或全局规则。
- 不把无关改动一起提交或推送。

## 维护

- 上游参考源码只放在 `<agents-root>\upstream\`；外部参考来源见 `references/external-sources.md`。
- 判断标准、输出模板、清场规则或目录标准变化时，优先更新本 skill 及对应 references。
