# 钢人论证

## 目标

帮助用户在重要选择前看清自己方案真正成立的条件，也把可信替代方案放在最有利的位置检验。目标是得出更可靠的判断，不是凑成正反各半的辩论，也不是拖延已经足够清楚的执行。

## 自动触发

仅当下面三项同时成立时自动触发：

1. 用户已经表达一个初步立场、方案、偏好或倾向。不能从一句裸露的“比较 A 和 B”擅自猜出立场。
2. 存在能够在当前场景落地的可信替代立场或反对意见。它必须有真实机制、收益或证据基础，不能用明显荒谬的选项充数。
3. 取舍会实质改变路线、时间或资金投入、主要风险、验收口径，或用户能否接受结果。低风险口味选择不触发。

用户显式调用 `/steelman` 或 `$steelman` 时，直接进入本流程；若缺少可信替代方案，说明无法诚实地做完整钢人比较，不要凭空编造反方。

## 不触发与路由

- 只求一个事实、定义、出处或数据时，先查证，不把查证包装成论战。
- 用户只是发散想法、尚无初步立场或关键替代方案时，按普通 brainstorming 或 `ask-first` 的需求确认处理。
- 方案、范围和验收已经确定，用户要求直接实现、修改、测试或交付时，转入相应执行流程。
- 核心问题是实验设计、偏倚、统计或证据质量时，使用 `rigor-check`。
- 核心问题是某个技术/申报指标能否成立、应怎样收紧口径时，使用 `target-feasibility`。
- 核心问题是现有文稿是否还要修改、有哪些实质问题时，使用 `paper-review`。

当这些专属任务和竞争性选择同时出现时，先让专属技能判断其事实或审查结论；只有仍需要在可信路线间取舍时，再做钢人论证。

## 工作方法

### 1. 先还原决策，而不是复述立场

先写清用户真正要达成的结果、当前倾向、替代路线和真正的决策边界。把“支持用户”与“支持问题本身”分开：用户的初步立场是待检验输入，不是预设结论。

### 2. 按影响度查证

优先查会改变结论的事实，不为显得全面堆背景。

- 低影响事实可暂按用户材料采用，并标出来源范围。
- 中高影响、可公开核验的事实应先查用户材料、原始数据、官方资料或一手来源。
- 若关键事实尚未核验，不把它写成结论依据；说明缺口、它可能把判断推向哪边，以及最低成本验证方式。

每个关键点用以下标签之一表达，避免把不同性质的话混在一起：

- `事实`：已有来源、记录或直接观察支持的内容。
- `判断`：基于事实作出的推断，说明其成立条件。
- `价值取舍`：用户或利益相关方对速度、稳妥、成本、控制权等的优先级，不能伪装成客观事实。
- `待验证假设`：尚无足够证据、但可能改变结论的前提。

### 3. 对双方都做钢人处理

先把当前立场写成最强版本：它在什么条件下有效、能避免什么代价、哪些证据真正支持它。再把替代路线或反对意见也写成最强版本：它解决了什么真实问题、在哪些条件下更优、哪些证据支持它。

证据不对称时直接说明。某一方只有营销说法、单次经验或未经核验的假设，并不会因为写了“反方”就获得与另一方同等分量。不要为了看起来中立而制造五五开，也不要把明显较弱的反方写成稻草人。

### 4. 找出会改变答案的地方

明确最小的决策分界：哪些事实、约束或价值排序一旦变化，结论会翻转；哪些信息即使补齐也不会改变答案。把能自行查证的事实留给智能体处理，把只能由用户决定的优先级和边界留给用户。

每轮最多问一个问题。只有该问题的答案可能改变判断、路线或验证顺序时才提问；否则不问。不要把多个问题藏进一个长句，也不要用“还需要了解什么”代替直接判断。

## 首轮输出

首轮固定使用以下五个标题，按人话写，不要先堆抽象框架：

```text
你真正要解决的事
[决策对象、当前倾向和替代路线]

支持这个想法的最强理由
[强版本理由；标出事实、判断、价值取舍和待验证假设]

另一条路或反对意见的最强理由
[强版本理由；如证据明显更弱或更强，直接说明]

真正会改变答案的地方
[决策分界、关键证据缺口和最低成本验证]

现在最值得先回答的问题
[只有一个会改变结论的问题；若信息已足够，写“无需再问”，并给出直接判断]
```

前四部分不夹带新的问题。最后一部分只有在确实需要用户回答时才出现一个问句；已有足够信息时直接作出判断，不为了遵守模板硬问。

## 用户回答后

吸收用户的新信息，必要时自行核验事实，再用下面结构收束。除非出现新的、会改变结论的缺口，否则不要继续追问。

```text
我的判断
[选择哪条路，或在什么条件下暂不选择]

为什么
- 事实：...
- 判断：...
- 价值取舍：...
- 待验证假设：...

接下来怎么做
[一个可执行的下一步；必要时先做最低成本验证]
```

如果判断已经足以开始执行，把执行工作交回相应专业技能或流程；不要在未被要求时把钢人论证扩写成完整方案、代码或文件修改。
