# 对话经验整理与清场

调用本技能（包括仅发 `$chat-notes`）或要求按本技能收尾，即包含对当前任务过程文件的可恢复清理授权，不再另行询问；仅提及、讨论或审查技能本身不触发清理。明确“只讨论”“不改文件”“不删除”“只更新某文件”或限定目录、计划模式及宿主权限优先。项目明确配置“资料库归入须确认”时，必须按下方流程确认具体搬动和关联清理范围，不能用一般清场授权替代。

上游来源登记用于追溯历史吸收内容；其中旧的再次审批要求不作为当前执行流程，现行授权与清场方式以本文件为准。

按顺序完成：**识别项目与当前成果 → 整理经验及已授权记录、必要发布 → 正式内容归位、更新引用并验证 → 实际清场 → 核验成果并给出文件链接**。经验写入和清理分别判断；没有新经验、经验修改待确认或发布失败，不阻塞独立可执行的清场。

## 整理经验

从本轮对话和实际改动中找出下次仍有用的新信息，核实事实并检查相关现有说明，分清规则缺失还是执行时遗漏。能改变下次判断或行动的新信息才值得记录。

优先更新已有文件：项目事实留在项目说明，跨项目方法归负责该行为的已有 Skill。涉及 PPT/演示文稿时，页面结构与项目参数写入项目说明；制作方法、用户编辑保护、兼容性检查、重绘验证和交付要求归 `pptx` / `ppt-master` 等现有 Skill，不在本技能重复维护。按内容选择正文、参考、模板、脚本或测试；只有确实无法归入现有文件时才新建。

收尾默认维护当前有效状态。按实际用途判断记录方式，文件名包含“记录”“日志”或“台账”不构成按日期追加的理由。配置、部署、接入和核验说明通常更新原状态；只有任务明确需要按时间追溯时才追加历史记录。日期可注明核验时间，不为每次收尾新增日期章节。

写入新结论前，找到同一事项的原有结论、待办和限制，替换或合并失效、重复或已被覆盖的内容；已完成待办和不再影响使用的失败经过不并排保留。只整理本次涉及事项，不扫描无关记录；没有新增事实且原说明准确时不修改，不默认增加待办，也不汇集其他项目或技能的问题。

历史信息仅在复现、恢复、解释重要决定或满足明确追溯要求时保留；实验中的有效结果（包括差结果）及必要原始证据不因精简而删除。普通操作、验证、发布和清场经过、重复哈希及已解决报错不累积写入长期说明；影响后续使用的结论简要写入，必要证据优先引用已有位置，不重复抄录，也不将冗余内容整体搬到新建历史文件。

已有清晰规则直接沿用；只有规则冲突、重复或结构妨碍执行时才删改合并。按实际变化检查受影响的用法、配置、接口、名称路径、架构图和上下游说明。

发布中的普通命令错误直接修正；云盘或并发 Git 问题按[发布说明](references/skill-edit-followup.md)读取局部排错资料。

本地依据不足，或外部方案会影响技能改进选择时，通过 `web-access` 查上游并比较可复用部分，保留来源并遵守许可要求；安装或替换需有对应授权。

经验整理后，向用户说明每项经验的去向：已写入的项目记录、建议补入的现有 Skill，或无需吸收及理由。已有规则覆盖时说明是执行遗漏，不重复加规则。需要升级 Skill 且尚未获准时，展示目标、原因和拟改内容并请求确认；等待确认只暂停该技能修改，独立记录整理和清场继续。已有授权时直接修改；修改后用 `skill-creator` 检查，并按[发布说明](references/skill-edit-followup.md)提交、推送和双端同步，除非明确限定只改本地。

## 资料库归入

项目已有 README、AGENTS 或当前任务指定资料库时，读取其真实位置、分类和登记约定；未配置时不猜目录、不新建资料库，也不改变普通收尾流程。材料正文已确认不等于已授权跨目录搬动或清理。

先形成可审阅清单：采用的成果及必要依赖、当前位置、目标位置、版本与提交状态、登记更新、旧位置和过程文件的清理范围，以及恢复方式。资料库要求确认且当前授权尚未覆盖该清单时，展示具体内容并等待确认；在此之前可继续盘点和独立记录工作，保护拟归入材料及依赖，不先清掉与本次归入耦合的文件。已有准确授权则直接沿用，不重复提问。

确认后，跨目录归入交给 `project-organizer`；依次完成归位、登记和引用更新、实际可用性检查，再执行已确认的可恢复清理。采用[资料库登记衔接](../project-organizer/references/material-library.md)区分文件位置、引用内容和核实状态，复用既有编号与登记，不为每次收尾另建一套表。确认稿、实际提交版和证据已核实分别记录；未知项标待核实，不因归档完成自动升级。

只整理经验、只登记或只审查的请求不触发搬动。保留完整申报包、实验工程及原始证据；其他项目和整个资料库不因本次收尾纳入清场。

## 清场

普通任务交付后保留过程材料，由用户显式调用本技能或明确要求清理后再清场；仅修改本技能或讨论存放规则不触发清理。优先盘点本任务的 `过程文件/任务主题/` 及可确定属于本任务的散落产物；目录名本身不代表其中内容可删。文件归属和正式位置遵循已加载的共享全局规则，不强制根目录、`输出/` 或 `final/`。其他任务目录和历史项目不自动纳入；用户明确扩大清理范围时按指定范围处理。

先依据任务上下文、项目说明和实际文件关系确认当前项目及成果，盘点本任务及其续做累积的过程文件。不能直接把父工作区、聚合仓库、其他项目或符号链接指向的外部目录纳入清理。逐项核对生成记录、用户决定、版本替代关系和真实依赖，不能只凭文件名、目录名、修改时间或最高版本号判断。

在大工作区内收尾时，按事情或主题归并本次新建内容及其必要依赖，包含散落在工作区根目录的成果，不限于过程目录。优先复用已有同主题目录；没有合适目录且成果属于独立主题时，新建名称明确的主题子目录。同一主题跨对话复用目录，一次对话涉及多个独立主题则分别归位，不按对话日期或会话编号统一打包。不自动搬动历史散落文件；已有正式资料就地引用，避免搬动共享依赖。普通主题子目录不自动视为新工作区，不因此另建 README、AGENTS；只更新受影响的现有项目说明。归属不明、同名冲突或正在使用的文件原地保留，继续处理确定项。

集中归并在本技能收尾时执行；开始任务时已有明确归属的直接使用已有目录，不强制每次开聊建文件夹。任务中的临时材料仍遵循既有过程目录约定。

- **保留当前成果**：已确认的当前或最终版本，以及用户明确指定的对比版本。尚无确认终稿时保留当前工作稿并标明“待确认”；当前版本无法唯一确定时，保留候选并列为待定，不能清到无稿可用，也不能擅自把旧稿指定为对比版本。
- **保留原件与必要依赖**：用户原始输入、引用资料、正式源码和测试、可编辑源文件、成果图片及运行依赖，保护用户手工改动、正在使用的文件和恢复未完成事项所需的材料。
- **先归位并验证正式内容**：采用的成果、当前工作稿、必要编辑源及依赖若仍在过程目录或散落在所属主题目录之外，先按上述范围无覆盖迁入正式位置，更新入口、相对路径、清单及实际引用，再检查打开、重绘或构建结果。必要事实并入已有项目记录；不把全部日志或临时恢复清单另建为永久成果。归位与验证通过后才移除旧路径；失败则保留相关文件并报告清场未完成。不能以“仍有用”为由把正式内容永久留在过程目录。
- **清除已证实无用途的过程产物**：被替代的旧稿、无用候选稿和失败稿，以及测试副本、预览、临时截图、转换文件、临时脚本、缓存和重复报告。曾确认但已被替代的版本，仅在明确用于对比时保留。不以“以后可能复核”笼统保留整批材料。
- 仅用于过程检查的截图、PDF、日志或检查副本，不因被过程记录引用就永久保留。清除前判断检查结论是否影响后续使用：必要结论更新到相应记录，普通成功经过在对话中报告，不逐次追加到项目说明。修正失效引用，必要时区分历史检查结果与仍可复用的依据；不能为了删除唯一必要证据而删掉正式成果的证据引用。
- **实际执行可恢复清理**：核对实际绝对路径和恢复依据，用实际执行账户及对应文件或目录类型验证系统回收站或已有项目恢复机制；不能沿用另一账户或仅文件探测的结果推断目录可回收。每项核验完成前保留相称的回退依据，清理后检查恢复记录及内容，不能只看命令成功或原路径消失。核验失败先还原受影响项，再修正清理方式。不能把整批中间文件搬到项目中新建的归档目录冒充清场，不自建外部垃圾目录或安装清理工具。
- **失败后自动补救并继续**：清理报错或核验失败时，主动诊断，在原授权和权限范围内修正、恢复并重试，同时完成其他确定项；无需用户再说“重新清理”。同一原因反复出现时先改变有问题的条件，不盲目重复相同操作，不以“已记录异常”代替补救或作为结束条件。已移除的文件不再列为待删除；无法补救的损失单独处理，不阻塞剩余清理。
- **只暂停确实需要外部条件的项**：归属、用途或版本无法自行查明的原地保留；完成可行补救后仍需用户决定、无法取得所需权限或恢复条件的，才暂停对应项。继续其他可执行工作，不强关应用、不绕过权限。确无可恢复手段时，仅针对确切清单询问永久删除许可；未获答复不删，不重新询问整次清场是否获准。

## 核验与交付

检查本次维护的相关段落能否直接说明当前状态及确实尚需处理的事项，消除新旧结论冲突、过期待办和重复叙述；同时确认必要追溯信息及证据引用仍完整。按用途判断是否清楚、足够，不设字数上限或固定章节。

清场后实际检查本任务过程目录已清空（无用途的空目录可一并移除）、正式成果及依赖完整可用、引用有效，且其他任务内容未受影响。正式入口不得再依赖已清理的过程路径。结束前处理完仍可自动补救或清理的事项，不把记录、重试建议或“部分完成”状态当作停止理由。只有剩余项确实依赖用户决定或不可获得的外部条件时才带阻碍交付；已发生且无法补救的文件损失须准确告知，不能写成成功，也不能与尚未清理的文件混为一谈。没有待清理项也要说明盘点结果。

回复固定按以下四项反馈，通常每项一句话；即使无事项也不省略，仅有阻碍或必要说明时展开：

- **成果：** 最终文件链接及状态；未定稿标“待确认”，无文件则明确说明。
- **经验整理：** 明确已写入的项目记录、已修改的 Skill，以及待确认的技能建议；没有值得吸收的新内容写“无需更新”并简述理由。待确认建议必须展示具体拟改内容并请求确认，不能仅以“已整理经验”概括。涉及技能发布时，区分源码修改、已发布和运行时已同步，不把单步成功写成全部完成。
- **清场：** 明确标注“无需清场／已完成清场／部分完成／未执行”，附简短依据。
- **待办：** 尚未完成的事项及阻碍；没有则写“无”。

未检查不能写“无需清场”；没有实际清理操作不能写“已完成清场”。已检查且没有待清理项用“无需清场”，全部清理并核验通过用“已完成清场”，仍有待定或受阻项且已完成部分清理用“部分完成”，未检查或未执行应做的清理用“未执行”并说明原因。

复用已有 README 或交付索引，不为每次收尾新建总结、清场报告或额外的 final 副本。

用户要求整理目录或命名时，遵循项目现有习惯和依赖关系，调整后修复引用；涉及多目录合并或迁移时使用 `project-organizer`。

已解决的普通权限、路径、回收或重试故障不写入项目正文、不新建事故记录、不列为待办，最终只报告清理结果和仍有的影响。先完成可执行补救，确有尚未解决且需要后续处理的阻碍或损失时，才在本次获准维护的现有记录中简要保留状态、影响和恢复依据；记录不替代继续执行，问题解决后更新原状态。只审阅时在回复中说明。
