# 对话收尾与经验整理

普通对话不自动触发本技能。用户显式调用 `$chat-notes`，或明确要求“按 chat-notes 收尾”时，才执行完整收尾。一次调用不是五选一的模式：必须检查下面五条轨道；每条轨道独立判断、独立执行、独立返回状态。某一条无需处理、待确认或受阻，不影响其他轨道继续。

用户的当前限制优先于默认动作。以下限制直接覆盖本技能的默认授权：只讨论、只审查、只改指定文件或目录、不清理、不提交、不推送、不发布、计划模式和宿主权限限制。没有这些限制时，显式调用本技能包含对当前任务过程文件进行可恢复清理的授权；不扩大到父工作区、其他项目、外部链接目标或整个资料库。

统一使用这些状态：**无需更新 / 追加 / 整合 / 重构 / 建议修改 / 已修改 / 待确认 / 受阻**。状态描述当前轨道的实际结果，不能用一条轨道的“已完成”代替其他轨道的核验。

## 统一收尾检查表

按以下顺序逐项检查，并为每项保留一个状态和必要依据：

1. **项目 Markdown**：找出本轮实际受影响的入口、README、AGENTS、配置说明或项目实验记录，按下方三级维护。
2. **飞书或实验文档**：把实验步骤、条件、实测结果和证据放回用户指定的飞书主文档或实验记录；不把给 AI 的写作规则写进实验正文。
3. **经验与技能缺口**：区分项目事实、一次性执行遗漏和跨项目可复用方法；已有规则覆盖时说明执行遗漏，不追加同义规则。
4. **过程文件清理**：盘点本轮及明确属于本轮的过程文件，归位并核对依赖后清理确定无用项。
5. **提交、发布与同步**：分别核验项目 Markdown 的提交推送、Skill 源码的提交推送、CC Switch/Claude/Codex 运行时同步；没有对应改动时记录“无需更新”，不能用项目提交代替 Skill 发布。

每项先核实实际文件、当前版本、用户限制和引用，再决定动作。没有新增事实时，不制造日期章节、总结文件、重复报告或新的待办。

## 固定落点

- **项目事实**：写入已有项目 `README.md`、`AGENTS.md` 或项目实验记录；按文件职责选择唯一落点。
- **实验步骤和结果**：写入飞书主文档或项目实验记录。操作、参数、测量点、结果和证据紧跟对应步骤；不把计划值写成实测值。
- **跨项目通用方法**：进入负责该行为的已有 Skill 的修改建议；未获用户确认前不改 Skill 源码。
- **临时材料**：只进入清理检查，不写入正式正文。必要的最终成果、编辑源、原始资料、实验数据和可复现依赖按项目现有结构保留。

资料库已有明确归入流程时，先按该流程列出成果、依赖、目标位置、旧位置、登记和清理范围；需要确认的跨目录搬动先停在“待确认”，继续其他独立轨道。不能因为正文已确认就猜测资料库目标或清理范围。

项目已有 README、AGENTS 或指定资料库时，读取其真实分类和登记约定，不猜目录、不新建重复资料库。跨目录归入在用户确认清单后交给 `project-organizer`，依次完成归位、登记、引用更新和可用性检查；未知项标“待确认”，不因归档完成自动升级。只整理经验或只审查时不触发搬动；完整申报包、实验工程、原始数据和其他项目不因本次收尾纳入清场。

## 项目 Markdown

只检查本轮涉及的主 Markdown，不扫描整个仓库，也不批量改写无关历史文件。判断维护级别后，再在对应范围内读、改、回读：

### 增量同步

只有一个新事实、一个入口或一个参数变化时，合并到已有段落或表格，不追加重复标题，不创建日期流水。修改后核对附近的当前状态、待办和引用。状态通常为“追加”或“无需更新”。

### 受影响文件整合

本轮改动了多个位置，或发现重复、顺序颠倒、失效结论、分散表格时，读取整份受影响主文件，统一结构后再写入。合并相同批次和相同结论，区分计划、实测、失败结果和历史依据，保留有效差结果、参数、运行编号和证据引用。状态为“整合”或“已修改”。

### 完整入口重构

文件是项目入口或实验接续文档，或用户提出“全文、完整、精简、重构、还有类似问题”时，检查整份受影响 Markdown：

- 当前接续内容是否位于前面；
- 标题层级和章节顺序是否清楚；
- 相同批次或相同结论是否重复；
- 计划、实测结果、失败结果和历史依据是否混在一起；
- 本地路径、归档路径和外部链接是否有效；
- 有效参数、异常、运行编号和证据是否保留；
- 是否可删除过程流水、重复附件说明和无信息量文字。

只有已有归档能够完整承接且链接有效时，才从主入口压缩详细记录；不为了变短而丢失可解释结果、失败证据或恢复入口。状态为“重构”或“已修改”。

## 飞书与实验文档

实验主文档只记录实验相关内容。执行记录按实际步骤组织，保留接线、参数和单位、测量点、每点采集次数、判断标准、下一步、结果图片、原始数据和可定位引用。参数名称与单位分开，一格只放一个参数；人填写项和 AI 回填项按用户确定的标记和表格格式保留，空值留空，不用占位话代替。

继续已有批次时，定位对应章节、步骤和原表，优先补行或更新单元格；不同批次分别记录，沿用同类表格结构。图片、原始文件和配置附件放在对应结果之后，写明实验电脑需要提供的文件内容；不把本地不可访问的实验室路径当成本机证据。

删除重复或没有信息量的解释时，保留能改变操作、结果解释或追溯的内容。没有异常时不添加“无异常”等防御性句子；发现有问题的批次时，不因结果不好就删除，只有能证明是未通电、通道选错等无效采集且用户同意其不进入正文时才移入已有归档并保留原因。

写入后重新读取目标文档，核对步骤顺序、批次、数值、单位、附件和引用。实验尚未开始的章节保持计划状态，不把空白当作已完成，也不重写本轮未涉及的后续测试。

## 经验与技能缺口

先判断本轮内容属于哪一种：

- 已存在且清楚的规则没有被执行：记录为执行遗漏，不追加同义规则；
- 只影响本项目的参数、路径、版本或实验事实：写入项目记录；
- 可跨项目复用且现有 Skill 确有缺口：提出技能建议；
- 一次性试错、普通发布经过或已解决报错：不写入长期说明，除非仍影响恢复或判断。

技能建议必须分别写清：

1. **目标技能**：名称和文件链接；
2. **现有问题**：现有流程在哪个触发、分类、授权或验证点不清楚；
3. **具体改法**：准备增加、删除或替换的规则和对应验证场景。

提出建议时状态为“建议修改”，不修改 Skill 源码，不提交、不发布。只有用户确认具体建议后，才调用 `skill-creator` 修改源码，补充隔离行为试跑，按 `agent-rules` 的定向发布流程提交、推送和同步；源码、评测、发布回执和运行时生效分别核对。确认一个建议不等于确认其他建议。

## 过程文件清理

只有显式调用本技能或明确要求清理时，才进行清场；“只讨论”“不删除”或指定范围优先。先确认当前项目、最终成果、工作稿、用户原始输入、必要编辑源、验证材料和真实依赖，再处理本轮及明确属于本轮的 `过程文件/任务主题/` 和散落产物。

- 保留已确认的当前或最终版本、用户指定的对比版本、原始输入、正式源码、测试、实验数据、编辑源、成果图片和必要依赖；没有确认终稿时保留当前工作稿并标明“待确认”。
- 先归位、更新入口和引用、检查打开或构建结果，再清除旧路径；归位或引用验证失败时保留相关文件并报告“受阻”。
- 清除已证实无用途的被替代稿、测试副本、预览、临时截图、转换文件、缓存、临时脚本和重复报告。不能只凭最高版本号、目录名或修改时间判断，也不能把全部过程材料搬到新归档目录冒充清场。
- 每项清理都要核对绝对路径、恢复依据和实际清理回执；不能只看命令成功或原路径消失。核验失败先恢复，再修正清理方式。系统没有可恢复机制时，只针对准确文件请求永久删除许可，未获许可不删。
- 一项清理受阻不影响其他确定项；不强关应用、不扩大范围、不把“已记录”当作已清理。已发生且无法补救的损失单独说明，不能伪装成成功。

清场状态只能写“无需清场 / 已完成清场 / 部分完成 / 未执行”，并附实际依据；未检查不能写“无需清场”，没有执行不能写“已完成清场”。

## 提交、发布与运行时同步

只提交本轮已确认且可隔离的改动，保留其他未提交内容，不使用强制重置、整库暂存、覆盖用户文件或手工改运行数据库。项目 Markdown 的提交推送与 Skill 的提交推送分开判断。

在 Git 项目中，显式调用本技能默认授权提交并推送本次已确认、可隔离的成果；用户明确只留本地、未定稿、无远端或冲突无法安全处理时暂停该轨道并说明。提交前只暂存本轮改动，核对远端，推送后读回准确提交，不混入无关工作、不强推。

Skill 发布时：确认源码仓库、准确提交和本次实际修改的完整 Skill 集合；按 `D:/BaiduSyncdisk/.agents/automation/ccswitch-skill-sync/README.md` 的受支持入口执行，使用完全相同的提交、集合和范围参数运行同步及 `-VerifyOnly`。只有两次退出码为 `0`、返回 `runtime_active`，且源码、CC Switch、Claude、Codex 文件集合和 SHA-256 一致，才报告运行时已同步。同步失败保留准确提交、目标集合、失败阶段和恢复依据，不手工覆盖运行副本、不改用前台点击。

用户明确“不发布”“只改本地”时，提交、推送和同步状态为“无需更新”或“待确认”，不擅自执行。源码提交不等于运行时生效，单条命令退出 `0` 也不等于完整同步通过。

## 核验与反馈

收尾前核对受影响 Markdown、实验文档、技能源码、评测、清场结果、提交回执和运行时状态；不同证据层级分开报告，不把计划、模拟、文档读回或源码检查说成实测硬件结果。

最终固定按以下五项反馈，即使某项无需处理也不能省略：

1. **修改的 Markdown**：列出本轮实际修改的 Markdown 链接；没有修改写“无”。只读检查或引用的文件不列为修改。
2. **成果**：给出最终文件链接及状态；未定稿标“待确认”。Skill 改动分别写源码修改、行为检查、提交推送、运行时同步完成到哪一步。
3. **经验整理**：写入了哪些项目记录、已修改哪些 Skill、哪些建议仍待确认；没有新经验写“无需更新”并说明理由。
4. **清场**：写“无需清场 / 已完成清场 / 部分完成 / 未执行”及依据。
5. **待办**：只列确实未完成、待用户决定或受阻的事项；没有则写“无”。

复用已有 README、实验记录或交付索引，不为一次收尾新建总结、清场报告或额外 final 副本。普通收尾过程和已解决故障留在对话中，不追加长期流水。
