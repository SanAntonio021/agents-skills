# 常见指标论证模式

## 时延类

推荐模式：

1. 明确写出包含和排除范围。
2. 拆成发送端处理、传播过程、接收端处理。
3. 对每一项给出定量值。
4. 对总时延求和。
5. 明确说明这些值是实测还是工程估算。

推荐句式：

`该时延指标可按发送端处理时延、传播时延和接收端处理时延三部分进行分解论证。`

## 视频速率类

推荐模式：

1. 区分单路业务速率和多路聚合回传速率。
2. 明确压缩方式。
3. 需要时给出短对照表。

推荐对照维度：

- 无压缩
- 轻压缩
- 重压缩

## 存储吞吐类

推荐模式：

1. 如果讨论顺序吞吐，保留 `GB/s`。
2. 明确指标对象是顺序读写。
3. 若需要提随机读写，只放在理由中说明，不要与主指标混写。
4. 用 SSD 和 NIC 官方页面支撑论证。

## 申报表性能指标与考核目标分工

处理工程申报表、重点方向推荐表等多列并行字段时，先划清字段职责，再写正文。不要先把内容写满，再回头删重复。

推荐分工：

1. `产品关键性能指标` 写装备本身能做到什么。优先放系统构成、装备形态、工作频段、速率、时延、建链时间、业务接口、组网能力、中继能力、环境适应性等可承诺能力。
2. `应用考核目标` 写项目结束如何证明做到了。优先放台套数、交付或应用数量、试验工况、场景验证、可靠性考核和已有依据支撑的测试报告。
3. 性能指标尽量定量化。可采用 `支持≥X类`、`完成≥X跳`、`速率≥X`、`时延≤X`、`建链≤X分钟` 等形式，但必须先说明指标对象。
4. 考核目标可以保留台套数、连续运行时间、工作温度、外场或场景验证等验收指标，但不重复列出性能指标中的通信方式数量、中继跳数、探测单元数量等能力清单。

去重检查：

- 性能指标中避免写 `项目期内形成`、`交付`、`通过测试`、`形成报告`、`应用验证`。
- 考核目标中避免重复展开 `融合通信`、`中继扩展`、`探测协同` 等已在性能指标中定义的能力。
- 没有来源或用户确认的成果材料，不主动补写为验收输出。

## 成立强度判断

在理由中可使用以下判断：

- `mature`：现成器件或公开工程结果已直接覆盖
- `conditional`：在明确限定架构或口径下成立
- `high-risk`：支撑不足或余量过小
