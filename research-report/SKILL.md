# 调研报告

审计脚本仅依赖 Python 3.11+ 标准库；联网取证需同时使用 `web-access`。

## 入口

从 [writing-router](../writing-router/SKILL.md) 接收：

- `document_type=research_report`
- `mode=evidence_report|decision_report|final_audit`
- `edit_scope`、`language`、`loaded_refs`

建立或沿用写作上下文后、处理正文前，读取[文稿协作](../writing-router/references/collaborative-writing.md)，按其中的范围和例外选择处理方式，并将实际路径记入 `loaded_refs`。直接调用本技能时同样执行；本轮已读且处理方式未变时沿用。

读取 [共同质量规则](../writing-router/references/common-quality.md)。完整草稿、结构重写、终稿审校和 `audit_only` 再读取 [AI 气味目录](../writing-router/references/ai-smell-catalog.md)。

再按 [工作模式](references/modes.md) 读取最少参考文件。私有样稿入口为 `D:\BaiduSyncdisk\.agents\writing-profile\index.md`；只有 `research_report` 样稿获批时才加载。

## 从调研到报告

1. 先读取任务、已有材料和当前主稿，沿用已确定的读者、研究问题、比较范围和交付形式。资料齐全时直接分析写作；缺什么就定向补什么。仅无法自行查明、会实质改变方向或结论的问题才询问。
2. 联网取证使用 `web-access`，核对实际页面、题名、日期、原文位置及支持内容。URL 本身不等于结论的依据；静态页面缺失或跳转异常时使用该技能的浏览器能力继续核实。用户明确不联网时只用已提供材料。
3. 比较口径已明确就继续扩展；仅字段、单位或来源类型尚不明确时用少量真实样本校准，样本无实质歧义就继续，不设固定样本审批、任务池或设计单。
4. 学术检索及 Zotero 任务文献管理交给 `paper-search`，下载复用其条目和分类上下文。持续产品库交给 `product-research-workbook`；普通参数或采购渠道比较表按需用 `xlsx`，不强制长期编号和双工作簿。仅请求这些专业操作时按原范围交付，不自动增加报告。
5. 对齐时间、地区、版本、指标定义和单位，核对关键结论及相反材料；据此组织事实、比较和判断，按现有文稿协作方式形成报告并完成指定文件交付。续做复用已有来源和判断，不重复取样或审批。

## 正式报告与内部记录

正式报告面向读者，结论由已核实事实支持。检索过程、来源冲突和待核实项按需记入已有研究记录；只有复杂任务确需追踪时才使用[内部调研台账](references/research-ledger.md)，不默认另建多份文件。内部记录不充当报告正文。

写正文前建立“读者问题—来源—论点—章节功能”关系：

| 项目 | 要求 |
|---|---|
| 读者问题 | 报告必须回答什么 |
| 来源 | 真实、可回查，含版本、地区和时间 |
| 论点 | 来源事实或由多条事实支持的判断 |
| 章节功能 | 范围、事实、比较、判断或建议 |

资料不足时继续补齐可查明部分，并完成有依据的分析和已授权交付；不能只交内部台账就结束。仍无法解决的关键缺口在交付说明中如实列出，不把无依据结论写进正文、不静默缩小研究范围，也不把部分成果称为全部完成。影响读者判断的真实适用条件仍在对应正文保留。

## `evidence_report`

正文只承担三类职责：

1. 定义与研究范围；
2. 有真实引用支撑的来源事实；
3. 基于已写事实形成的综合判断。

不生成行动建议。原稿中的建议转入内部映射表，除非用户将模式改为 `decision_report`。摘要最后写，只概括对象、主要发现和结论，不展示检索过程、资料缺口或内部编号。

详细内容边界见 [报告内容契约](references/report-contract.md)。

## `decision_report`

先完成与证据型报告相同的事实和判断，再根据用户需要写建议。建议必须：

- 明确针对哪个决策对象；
- 能回指前文事实和判断；
- 写清适用条件、代价、风险或触发条件；
- 区分“建议采用”“建议验证”“暂缓决定”等不同强度；
- 不把建议写成已经批准、已经实施或已经取得效果。
- 比较各方案时保留相同的决策维度，包括单价、数量、总价及时间条件。某方案因一项条件不满足要求，仍保留它在其他维度的已知事实，使取舍可复核。
- 总时限包含采购、交付、联调、部署或验收等多个环节时，不能用其中一个环节的周期证明全流程满足期限。已知交付期为 3 个月、总时限为 4 个月，只能推出后续环节最多剩 1 个月；后续用时未知时，建议应以能在剩余时间内完成为条件。材料未指定责任方时，不补造分工或合同责任。

建议可以单列，也可以放在对应判断后，但不要与来源事实混在同一段。具体规则见 [决策报告](references/decision-report.md)。

## `final_audit`

按共同质量规则分点报告问题，核对：

- 每个关键数字、参数和结论能否回到真实来源；
- 来源事实、作者判断和建议是否分开；
- 摘要是否只是拼接各节首句；
- 同一结论是否跨节换说法重复；
- 报告模式是否与建议内容一致；
- 是否残留内部来源号、待补状态或虚构元数据；
- 结论和建议是否超过证据适用范围。

跨节事实矛盾、虚构数据或引用、整段无理由重复、状态升级直接判 `fail`。

## 写法

- 标题写具体对象或结论，不用“核心洞察”“关键抓手”等空标签。
- 一个段落只承担范围、事实、判断或建议中的一个主要功能。
- 定义只解释到读者能理解后文，避免在每个章节重复。
- 表格用于参数、来源和同条件比较；推理写成段落。
- 引用紧跟所支撑的句子。转载同一原始资料不算多条独立证据。
- 计算结果引用输入和方法，不写成来源直接发布的数据。来源只报告新增数量时，保留该来源的增量陈述，由多个来源计算出的总量另写为综合计算结果。数量关系只表达一次；已有数量变化足以回答问题时，不重复同一差值，也不额外计算与判断无关的比例或增幅。

## 审计脚本

Markdown 或纯文本可运行：

```text
python scripts/audit_report.py report.md --mode evidence-report --json
python scripts/audit_report.py report.md --mode decision-report --json
python scripts/audit_report.py research-ledger.md --mode internal-ledger --json
```

脚本只提供候选问题。关键词命中、行动词或句式整齐都需结合当前模式人工判断。

## 文件边界

正文按当前协作方式写回主稿，飞书主稿交给对应平台技能局部更新。实际写入本地 `.md` 或 `.tex` 前执行 [文稿版本保护](../writing-router/references/document-version-protection.md)。Word 交付按 [Markdown 到 DOCX 交接契约](../writing-router/references/markdown-docx-contract.md) 使用本轮按协作方式处理并审校的正文，再交给 `docx`；导出阶段不重新改写内容。

PPT 交付使用现有 `pptx` 路由及用户指定模板，按汇报时长和读者需要组织页面，保留图表、来源及结论边界，不把 Word 长段落直接堆进幻灯片。只读审查保持只读；用户只要正文时不额外生成 Word 或 PPT。

## 完成条件

- 已完成用户请求的调研、报告内容和指定文件交付；仍有无法解决的核心问题时明确报告完成范围和缺口，不将登记台账当成完成；
- 关键事实和数字可回查；
- 事实、判断和建议的身份清楚；
- `evidence_report` 没有行动建议，`decision_report` 的建议有证据和适用条件；
- 没有内部编号、无理由重复或虚假完成状态；
- `loaded_refs` 与实际读取一致。
