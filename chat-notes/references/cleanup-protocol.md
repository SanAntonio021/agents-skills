# 可恢复归档与旧文档判断

## 触发与授权

当用户说“整理一下”“收尾”“结束前整理”“把这轮对话沉淀一下”“/neat”，或当前任务已进入阶段结束时，进入**清场准备**。先完成经验整理、验证和完整汇报，再展示保留集、归档候选、归档位置、清单位置和恢复方式。

只有用户在看到该完整清场预览后再次明确批准，才能执行移动。任务开始时的“做完后清理”“顺便清掉”等预授权，以及对审查稿或文档修改的批准，都不能替代这次报告后的清场批准。批准仅覆盖预览中路径、归档位置和空目录列表均已固化的项目；范围、路径或用途发生变化时，重新预览并取得批准。

清场是**可恢复归档**，不是删除授权。不得把它扩展为硬删除、移入回收站、覆盖既有归档、修改 `.gitignore`、修改运行时副本或清理其他批次。

## 先分类，再形成清单

清场前先阅读项目入口和当前结论所依赖的说明，例如 `README`、`record`、`handoff`、交付清单、版本记录和现役 QA 记录。基于用途而非文件名、目录名或前缀，逐项分为以下集合：

- **保留集**：当前交付物、当前可编辑版本、支撑当前结论的必要来源证据、现役 QA/验收证据、用户点名保留的内容，以及仍被有效入口引用的材料。
- **归档候选**：已被新版本替代的过程材料、已失效的候选图/报告、旧提示词、旧脚本、旧 QA 截图、缓存或临时输出。必须能说明它为何不再承担当前交付、可编辑、来源证据或现役 QA 的角色。
- **待判断项**：用途、依赖或版本关系无法从当前资料确定的文件。它们留在原处，不进入本批归档；在报告中写明保留理由或待确认点。

不得仅因 `qa`、`compact`、`_reference`、版本号或日期前缀而移动文件。一个文件同时服务于当前交付和历史过程时，先保留或让用户决定，不能以“看起来重复”推定可归档。

项目中的 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、当前规则文件、运行时副本、已有归档批次和本任务外目录默认不进入候选集。若某项确需处理，必须在预览中单列用途、影响和恢复方式。

## 归档前基线与预览

归档根目录固定为项目内 `archive/cleanup-YYYYMMDD/`。每个归档文件放入：

```text
archive/cleanup-YYYYMMDD/data/<原项目相对路径>
```

这保留原项目目录层级，避免平铺、同名改名和覆盖。开始建立本批预览前，`archive/cleanup-YYYYMMDD/` 不得含有旧批次内容；预览生成本批控制记录后，执行阶段允许这些记录继续留在批次根目录，但 `data/` 下任一归档目标都必须不存在。发现旧批次内容或目标文件已存在即停止，不覆盖、不换名继续。

先在内存中冻结本次盘点的原有文件集合及其字节数、SHA-256 和分类，再向磁盘写清单。本批新生成的 `archive-manifest-before.csv`、`retained-manifest-before.csv`、`archive-manifest-after.csv`、`archive-acceptance.json` 和执行日志都是控制记录，统一放在 `archive/cleanup-YYYYMMDD/` 批次根目录，不进入本批候选集、保留集或任何由它们自身描述的哈希集合。清单不能把自己列为一行，否则写完清单后自身大小和哈希必然变化，形成无法成立的自指校验。

项目中原本已经存在的旧批次清单不是本批新输出：若它们已在冻结的原有文件集合中，仍按实际用途归入保留、归档候选或待判断项，并像普通源文件一样记录归档前哈希。不得用本批同名输出覆盖旧清单。

对本批全部归档候选建立归档前清单 `archive-manifest-before.csv`；对保留集建立 `retained-manifest-before.csv`。清单中的路径都相对于项目根目录，使用 UTF-8。每个归档候选至少记录：

```text
source_relative_path,archive_relative_path,purpose,git_state,bytes,sha256_before,restore_command
```

- `purpose` 说明该文件为何可归档，以及它被哪个当前版本或记录替代。
- `git_state` 记录已跟踪、未跟踪或忽略；Git 状态不是归档依据，只是恢复上下文。
- `restore_command` 使用路径已展开且拒绝覆盖的任务级命令，例如先确认原路径不存在，再从归档路径移回原路径。
- 保留集清单至少记录 `source_relative_path,purpose,bytes,sha256_before`。

清单应覆盖候选集中的每一个文件，汇总候选文件数和总字节数。相对路径与 SHA-256 配对的可核验清单模式可参考 [RFC 8493](https://www.rfc-editor.org/info/rfc8493/) 中的 manifest 原则。

完整清场预览必须给用户看见：

1. 归档批次位置和项目根目录；
2. 保留集的用途、数量、总字节数和清单位置；
3. 归档候选的数量、总字节数、全量归档前清单位置、逐项用途和恢复方式；
4. 待判断项及其未归档理由；
5. 计划移除的空目录及其重建命令；
6. “尚未移动任何文件，等待本次预览后的明确批准”的状态。

预览阶段只读盘点、计算哈希和生成清单；不得移动、复制、删除、进入回收站或改 `.gitignore`。

## 执行与逐文件核验

获得报告后的明确批准后，为当前批次生成一次性的任务级 PowerShell 脚本或命令。它不是可复用的批量清理工具，只含清单中已固化的精确路径，且每一项都遵循以下顺序：

1. 确认源文件存在、目标文件不存在，目标仍位于本批 `archive/cleanup-YYYYMMDD/data/` 下。
2. 创建所需的目标父目录，但不创建或修改任何非本批路径。
3. 用直接移动将文件移至目标，不使用 `Remove-Item`、回收站 API、通配符或批量推导路径。
4. 立即确认源路径已不存在、目标路径存在且字节数相等，再重新计算目标 SHA-256。
5. 只有目标 SHA-256 等于归档前清单中的 `sha256_before` 才记录为通过，并继续下一项。

任一项缺失、已存在、路径越界、字节数不符或哈希不符时，立即停止。不自动删除目标、不自动回滚、不移动下一项，也不把部分完成写成验收通过。保留归档前清单、当前执行日志和已完成项，等待人工判断或用户授权的恢复操作。

移动后写入 `archive-manifest-after.csv`。它必须保留归档前字段，并增加至少：

```text
bytes_after,sha256_after,source_absent,destination_present,verification_status
```

随后写入机器可读的 `archive-acceptance.json`，至少包括：批次时间、项目根目录、归档前/后清单路径、保留集清单路径、候选文件数、候选总字节数、逐文件哈希不一致数、保留集哈希不一致数、空目录处理结果、引用检查结果和总体状态。

只有以下条件全部满足，`overall_status` 才能为 `passed`：

- 归档前、归档后清单的文件数和总字节数一致；
- 每个目标文件的 SHA-256 等于其归档前值，源路径均已离开且目标路径均存在；
- 保留集的当前 SHA-256 与 `retained-manifest-before.csv` 全部一致；
- 已批准的空目录均已重新确认无子项；
- 现役 `README`、`record`、`handoff` 等引用的目标路径均存在，或其后续修改已通过单独验证。

批次根目录中的清单和验收记录只核对是否成功生成、能否解析及其当前 SHA-256；这些控制记录的哈希可以写入最终汇报或独立的批次摘要，但不得回写到文件自身或让某份清单校验自身。

## 空目录与引用

空目录不是默认可删项。预览中必须逐项列出相对路径和重建命令；只有用户对该清单明确批准，且执行时再次确认目录不存在子项，才可移除。把实际移除的目录、确认结果和重建命令写入 `archive-acceptance.json`。未经批准、非空或无法确认的目录保持原样。

文件移动及其哈希验收全部通过后，才检查 `README`、`record`、`handoff` 等现役说明中的引用。若归档使某个现役引用失效，只能在该批归档已经通过验收后，以独立、可验证的文档修改更新为归档副本路径；更新后再确认被引用路径存在。不得为了掩盖失效引用而改写历史归档、删除旧记录或跳过验收。

## 异常、恢复与汇报

如果文件进入回收站、归档清单不完整、发现目标覆盖、哈希不一致，或保留集发生变化，立即把该批标记为未通过。先依据归档前清单和 `restore_command` 把已移动项恢复到预期位置，或在用户明确要求保留部分结果时重新建立基线；在路径、字节数和 SHA-256 全部重新核验前，不交付“清场完成”结论。

成功清场时，用户可见汇报只需说明清场已经完成和归档位置。`archive-acceptance.json` 继续记录验收结论、归档前后文件数和总字节数、逐文件哈希不一致数、保留集复核、空目录处理、未归档候选、引用检查和恢复方式；这些技术细节不默认展开到聊天。

清场出现上述任一阻断性异常时，不交付“清场完成”。按 `report-format.md` 生成中央异常报告，报告链接引用本批 `archive-acceptance.json`、归档前后清单和执行日志；聊天只给异常结论、必要动作和报告链接。批次控制记录仍是原始验收证据，不能以它们替代中央报告。

只清理本次预览中相关的过程材料；发现仍有疑似冗余但未入清单的内容，留待下一次独立预览。默认不打开归档内容正文，除非用于恢复、哈希/路径核验、引用检查或用户明确要求。

## 旧文档判断

- 判断旧文档是清楚还是混乱时，先读文件名、入口引用和前 80 行，避免旧内容污染判断。
- 清楚有用的文件：保留在现役位置，必要时重命名为标准文件并继续维护。
- 混乱、重复、过期或不确定的文件：先确认其价值是否已被当前 README、标准文件或新版本承接；仅承接完成且进入归档候选后，才按本协议归档。
- 需要提炼时，可以继续读完整文件；提炼内容先经用户授权写入正式位置，再将原文件作为候选重新分类。
- README 只做总入口，不塞长台账；台账或索引用 `record-*` 独立保存，并在 README 里链接。
