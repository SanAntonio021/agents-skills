# 技能发布

自建技能的发布说明只在本文件维护：“技能定向发布”写发布步骤、完成标准和失败处理；“CC Switch 后台组件”写发布所依赖的后台组件怎样定位、各技能分别负责什么。上游候选的审核与吸收见[上游维护](skill-upstream-maintenance.md)。

## 技能定向发布

按 [skill-creator](../../skill-creator/SKILL.md)确定具体修改范围及授权后，默认包含同次任务的必要检查、精确提交推送、后台更新和生效核验，不等待另说“更新”或对话收尾；尚在讨论的升级意向不进入发布。按本次实际来源、完整目标技能集合和应用执行，不夹带其他改动。用户明确只讨论、只检查、只改本地、暂不提交或暂不发布时优先遵守限制。

1. **准备源码。** 核对当前文件和修改范围，完成必要验证；仅提交本次相关内容，按所属仓库分别推送并取得准确提交 SHA。
2. **执行发布。** 读取维护目录的 `automation/ccswitch-skill-sync/README.md`，统一使用同目录 `Invoke-LabSkillSync.ps1`。将准确提交传给 `ExpectedRemoteCommit`，该提交实际修改且仍存在的完整技能集合传给 `Skills`，其他范围及本机文件声明按工具说明传入。公开与私有技能采用对应来源，只修改授权范围内的技能和应用状态。已有成功回执且同参数只读核验确认当前仍一致时，不重复写入。
3. **核验更新结果。** 发布后用完全相同的提交、技能集合和其他参数追加 `-VerifyOnly`。确认两次退出码均为 0、状态均为 `runtime_active`，且目标提交与 CC Switch、Claude、Codex 已启用副本的完整文件集合、SHA-256 和启用矩阵均通过后，使用“已更新完成”汇报。官方桌面后端用官方查询和外部发布回执核对仓库、提交和原来源，不读取数据库结构；ZIP 安装保留官方 `local:` 来源，不伪装为 Git 来源。后端与来源语义以回执契约版本为准。
4. **核验管理界面。** 本次交付涉及界面显示时，优先使用受支持的刷新机制；需要前台操作时先告知，再代为刷新并读回技能名称、来源和启用状态。刷新不得改变应用启用状态或强制重启客户端。界面仍显示旧缓存时，分别报告运行时与界面的实际结果。
5. **完成云端分发。** 云端同步已纳入本次授权时，上传后读回目标快照，核对配置与技能内容；本机生效和云端更新分别报告。

仓库里有其他任务的内容时，只提交本次差异，不整理、不取消对方的暂存，也不等对方先提交。本次文件没有对方改动、本地分支也未与远端分叉时，用 `git commit -- <本次路径>` 精确提交。同一文件含对方的暂存或未提交改动，或本地分支已与远端分叉时，改用隔离提交；本次差异无法与对方内容分开时暂停提交并说明。隔离提交依次做：

1. **提交。** `git fetch` 后从远端目标分支建立临时 worktree，只把本次差异应用进去并核对 diff 不含其他内容，校验后提交。主工作区的工作副本保留本次改动，内容与该提交一致。
2. **本地分支带上该提交。** 本地分支包含远端最新提交（`git merge-base --is-ancestor origin/<分支> HEAD`）、本次路径上也没有对方暂存的内容时，推送前在主工作区执行 `git reset -q <提交号> -- <本次路径>`，把这些路径的索引设为提交里的版本，再执行 `git merge --ff-only <提交号>`。两步都不改写工作副本，对方的未提交改动原样保留。快进被拒绝说明本地分支刚有了新提交：用 `git reset -q HEAD -- <本次路径>` 还原索引，在临时 worktree 里把提交变基到本地分支的最新提交后重做。条件不满足时跳过这一步，主工作区保留本次改动的未提交状态。
3. **推送。** 按提交号推送（`git push origin <提交号>:refs/heads/<分支>`）并读回远端。推送被拒绝而远端已含该提交，是其他任务连带推送了它，不算失败。
4. **核对并清理。** 本地分支带上了该提交的，核对本地分支与远端一致、没有多出暂存项、`git diff -- <本次路径>` 里只剩对方的改动。最后删除临时 worktree 和临时分支。

几个任务同时发布时：目标技能目录里还有其他任务未提交的文件，按工具说明逐个声明（`-ExpectedWorktreeExceptions`），不替对方提交或还原。返回退出码 11（`operation_busy`）是另一轮同步占着发布通道，本次没有写入：等它结束后用同样的参数重新运行，不按失败诊断。本次提交之后其他任务又推送了提交，默认检查会因该提交不再是 HEAD 而拒绝（退出码 10，`source_head_or_remote_mismatch`）：按工具说明以历史提交方式只补发本次技能（`-AllowHistoricalCommit -AllowHistoricalSubset`），发布和核验用同一组参数。返回退出码 20（`previous_write_requires_verification`）是发布工具状态目录里留有上一轮写入结果未确认的标记 `uncertain.json`，本次没有写入；在那次写入的结果核实、由发布工具解除标记之前，所有任务的发布都会被拒绝。状态目录 `operations` 下最近一条停在 `recovery_required` 的记录写明了是哪个技能。标记是其他任务留下的：交给那个任务处理，不删除标记、不替对方恢复或回滚，也不反复重试；告诉用户发布在等待，标记消失后用同样的参数重新运行。`-VerifyOnly` 不受这个阻断，也不会解除它。标记是本次任务留下的：先按工具说明核实那次写入的准确结果，再继续。

发布或核验失败、回执缺失或结果无法确认时，明确报告“更新没完成”，说明原因和下一步，保留准确提交、完整参数、回执与差异。超时或断连先用同参数 `-VerifyOnly` 核实实际结果，不直接重跑写入；已满足生效条件时继续剩余交付，否则按现有工具说明恢复或重试。保护用户的新修改；重复失败先诊断，不无限重跑、不重复索取已有授权。通过受支持流程处理备份和恢复，不手工覆盖运行副本、直接修改数据库、回退旧 CLI、改用界面操作或擅自结束客户端。只暂停受阻步骤，恢复后重新核验。

定向更新报 `Installed SSOT has local edits; refusing update` 时，先区分真实用户改动与发布后基线滞后：按该技能记录的旧基线备份并恢复安装目录，再走正常定向更新；不得直接改数据库或覆盖运行副本。更新后以同一提交执行只读复核，并核对源码、CC Switch、Claude、Codex 四层文件哈希一致。结果说明文件是否已更新；来源记录若仍指向 `main`，注明这一点即可，不要用它替代文件核验结论。

固定提交更新报 `Pinned update requires an exact GitHub source path in readme_url`，或普通归档更新因仓库内同名过程副本报 `Remote Skill directory ... is ambiguous` 时，先核对来源仓库、登记分支、`readme_url` 和同名目录，区分路径解析缺口与真实源码冲突。保留原提交及参数，通过受支持流程创建配置备份；直接更新无法解析唯一目录时，用完整键 `<owner>/<repo>:<directory>` 从登记的发布分支重装目标技能，恢复原启用矩阵后执行普通或固定提交更新。不要手工修改数据库或运行副本，也不要把归档回退到的别名分支当成预期来源。最终仍用原提交和完整技能集合执行 `-VerifyOnly`。

## CC Switch 后台组件

维护共用组件的定位或技能引用时，按用户指定位置、当前项目说明或已核实的维护目录读取
`automation/ccswitch-background/README.md`；入口为同目录 `Invoke-CcSwitchBackground.ps1`。
已展开并核验的启动用户主目录下 `.agent-rules/local.md` 存在时可补充“规则维护目录”，缺失不要求创建。
组件无法定位、所选后端身份校验失败或所需能力未通过验收时，只暂停依赖组件的操作，不猜路径、不从 PATH 替换同名程序。具体步骤按共用指南执行。官方桌面的连接、能力验收、保护缺口和恢复说明位于同一维护目录的 `automation/ccswitch-desktop/README.md`；默认选择以本机实际标记为准，不因组件存在而切换，也不自动变更其他电脑。

`agent-rules` 负责共用组件的定位、技能引用和发布边界；Codex 供应商、Common Config、技能启停配置及请求链路
交给 `codex-relay-chain`，Claude 链路交给 `claude-relay-chain`。自建技能发布继续使用
`ccswitch-skill-sync` 的 `Invoke-LabSkillSync.ps1` 统一入口，按本机已选后端执行；官方桌面只要求当前版本的技能发布所需能力通过验收，不以全部业务能力的综合状态阻断已验收能力。其他业务仍保留各自门禁，失败不能退回旧 CLI 写库。源码、CC Switch 保存、运行目录和实际生效分别验收；
测试通过或源码提交不代表已发布。后台失败不转向界面操作或模拟键鼠。
