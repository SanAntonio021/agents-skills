# steelman 路由集成用例

## AF-SM-01: ask-first 转交竞争性判断

**输入**

```text
请使用 ask-first。我在纠结：把“重要方案先做钢人论证”做成独立的自动触发 steelman，还是并入 ask-first。前者会多一个技能，后者可能把需求确认和竞争性判断混在一起；这个取舍会影响以后很多任务的自动路由。请先判断该走哪条思路。
```

**期望路由**

`ask-first` 在完成必要背景读取后，只把这一个竞争性判断转交给 `steelman`。它不应在转交前重复展开目标、交付物、时间和文件格式等常规确认问题。

**应保留的 ask-first 边界**

- 仍由 `ask-first` 保留显式调用入口、一次一个问题和确认后才写入的规则。
- `steelman` 只判断“独立还是融合”；它不应直接创建、修改、提交或同步技能文件。
- 钢人判断结束后，如果用户决定继续实施，`ask-first` 再继续确认实施范围、交付物和成功标准，或在已充分确认时交给执行流程。

**通过标准**

1. 首轮明确点名 `steelman`，不把其当作普通 brainstorming。
2. 不出现与竞争性判断无关的第二个问题。
3. 不取消 ask-first 的确认关口，也不在未获实施授权时写文件。

## SM-AF-02: 不应反向吞掉 ask-first

**输入**

```text
我想做一个链路测试记录工具，但用户、输入数据、桌面还是网页、交付时间和成功标准都没有定。请先帮我问清楚。
```

**期望路由**

选择 `ask-first`。这里没有用户已有立场和可信替代路线；`steelman` 不应因为任务重要或出现“选择”可能性而自动触发。
