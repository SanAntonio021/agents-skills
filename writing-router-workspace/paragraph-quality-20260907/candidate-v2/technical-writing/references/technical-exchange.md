# 技术交流稿写法

## 文稿职责

技术交流稿不是会议纪要，也不是把后续工作提前写成完成状态。它只保留四类信息：

1. 已经掌握、且会影响方案选择的事实；
2. 有真实连接关系或结构差异的方案；
3. 需要参会双方共同作出的选择；
4. 需要在会前或会后完成的计算、回读、设计、加工和测试。

开头直接进入第一项有效信息。若后文已经完整列出讨论项，删除“本次主要讨论……”之类的目录式复述。只对编写者有用、不会改变对方理解或决定的责任声明也不写进正文。

## 区分讨论与另行工作

先判断一件事能否仅凭会议中的现有材料形成结论。

| 类型 | 写法 |
|---|---|
| 已知事实 | 写具体对象、数值、来源或当前状态 |
| 会上决定 | 写清可选项、差异和要确定的事项 |
| 会前或会后工作 | 写执行人、动作、条件和要形成的参数、记录或样件 |

设备配置没有回读、频段需要计算、尺寸需要测量、性能需要仪器测试时，会议不能直接“确认”结果。会议可以决定计算口径、测试条件、接口分工或验收要求，数值本身放入对应的会前或会后工作。

后续动作写在相关技术内容之后，使方案、责任和验证方法连在一起。只有读者确实需要独立的责任总览时才另列表格；表格不得再抄一遍正文。

## 拆分真实方案

不要用一个总称盖住会改变设计或加工的分支。逐项检查：

- 信号路径是否不同；
- 器件数量和封装方式是否不同；
- 本振、供电、控制或机械接口是否不同；
- 必须满足的系统约束是否被误写成可选项。

有差异就分别命名，并在相同条件下比较。名称直接指出差异，例如“上、下变频共壳体”和“上、下变频分别封装”，避免“方案一”“分体模块”等需要回看上下文的称呼。已经确定的共天线、指定接口或固定方向等条件放在共同前提中，不列入讨论问题。

## 句子和术语

让不熟悉上下文的工程人员第一遍就能读懂。每句只承担一个主要判断，明确谁做什么、对象是什么，以及会得到什么结果。

- “需要哪些输入和输出”应改成具体的射频端口、信号频率、带宽、功率、阻抗或连接关系；硬件语境中确实指端口方向时可以保留“输入/输出”。
- “台架”只用于已经定义了仪器和连接关系的测试系统；否则直接写信号源、混频器、频谱仪等实际连接。
- “模块”“平台”“设备”“链路”等词首次出现时要能对应具体对象，后文不换同义词。
- 删除“原则上”“后续再定”“需核对”等没有说明动作、责任人或判断条件的说法。

## 表格

方案比较表先抽出共同指标，再列各方案独有的结构和性能要求，避免每行重复“若选用”“待讨论”等前缀。确定项、候选项和待讨论项用独立字段或简短状态表示。

详细表用于设计和加工，简表用于快速沟通或截图。简表必须脱离正文也能看懂；说明文字能写进列名、单元格或表题时，不在表下另加两行解释。

## 交付前检查

- 每一段是否增加了事实、方案差异、决定、动作或结果；
- 每个讨论项是否能在会上形成明确选择；
- 每个不能在会上完成的事项是否已经移到会前或会后工作；
- 每个方案名称是否能直接对应结构或连接关系；
- 责任和测试是否紧跟相关技术内容，且没有被总表重复；
- 同一指标是否只在一个最合适的位置完整出现。
