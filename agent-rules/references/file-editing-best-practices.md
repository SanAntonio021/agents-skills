# 文件修改注意事项

## 这份说明管什么

这份说明只管当前环境里怎么改文本文件，重点是少出编码问题、少改错范围、少用错工具。

## 默认怎么改

1. 先定位目标文件和实际内容。
2. 手工文本修改默认使用 `apply_patch`。
3. 重命名、移动、批量检查、格式化、验证这类动作使用 `shell_command`。
4. 修改后立刻复读或校验，确认结果与预期一致。

## 当前环境优先用什么

当前这套环境里，优先使用：

- `apply_patch` 做手工编辑
- `shell_command` 跑 PowerShell 命令
- `Get-ChildItem`、`Select-String`、`Get-Content -Raw`、`Test-Path` 做检查

不要继续依赖这类旧语境写法：

- `replace_file_content`
- `multi_replace_file_content`
- `view_file`
- `grep_search`

这些不再是当前维护基线。

## Windows 和 PowerShell 注意事项

- 默认按 PowerShell 语法写命令
- 路径尽量使用绝对路径
- 含空格路径始终加引号
- 修改前先确认目标文件真实存在
- 多步 PowerShell 逻辑如果开始变脆，就写短 `.ps1` 再执行

## 编码怎么处理

处理中文 Markdown 或文本时，默认按 UTF-8 管理。

遇到乱码时按这个顺序处理：

1. 先区分是终端显示乱码，还是文件本身已损坏。
2. PowerShell 读取前先设定：

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

3. 读取时优先使用：

```powershell
Get-Content -Raw -Encoding UTF8 "<path>"
```

4. 如果必须脚本化读写，优先用 `[System.IO.File]` 并显式指定 UTF-8。
5. 写回后立即再读一遍，不靠想当然判断是否修好。

## 改动范围怎么控制

- 只改用户要求的文件和与之直接相关的最小范围
- 不顺手清理无关文件
- 不回滚用户已有改动
- 不使用 `git reset --hard`、`git checkout --` 这类破坏性命令

## 工具怎么分工

- 简单文件读写不要为此启用 Python
- 小规模文本编辑不要用 shell 重定向硬写整文件
- 需要稳定批处理时，优先短脚本或现成 `scripts/`

## 改完后至少检查什么

每次编辑后至少做一项验证：

- 重新读取关键片段
- 搜索旧字符串是否已消失
- 搜索新标题、链接或字段是否已出现
- 运行相关帮助命令、校验脚本或最小检查

## 规则文件没同步上时怎么查

如果你发现两个位置的规则文件不一致，先按这个顺序查：

1. 先确认谁维护源文件、谁生成当前文件。由 CC Switch 等工具管理的普通文件，也不能直接当作手工副本覆盖。
2. 核对两边内容、实际读取路径和文件类型；软链检查目标，普通文件区分生成文件与手工副本。
3. 先查管理工具已有的受支持后台接口或 CLI，再考虑图形界面。“受支持入口”不等于“图形界面”，历史 GUI 案例也不决定当前的默认方式。能力探查先用只读帮助、文档或源码，不用实际同步来试探命令是否可用。
4. 写入前核对工具来源、版本、数据格式兼容性及实际影响范围。帮助中存在命令只说明可以继续核查，不证明该版本能够安全处理当前数据；也不能把 Skill 定向同步已验证，推广成 Prompt 或 WebDAV 恢复已验证。全量恢复尤其要检查是否会覆盖范围外的供应商、认证、技能或其他设置。
5. 授权、兼容性和备份满足后，优先后台执行受支持操作，保存退出状态并回读目标及非目标内容。确实无法后台完成时，先说明原因再使用受支持界面；已有流程明确禁止前台兜底时仍按其要求停止，不因后台失败改用界面或手工写数据库。
6. 只有确认文件不由管理工具生成，且已有相应修改授权时，才考虑修软链、临时复制同步，或只修改源文件。受管理文件仍由管理工具更新，不自行覆盖数据库或生成文件。

不要一上来就直接覆盖文件。

如果只能先复制同步，要明确告诉用户：

- 现在只是内容先对齐
- 这不是自动同步
- 以后源文件再改，这个副本不会自己跟着变

## 维护时注意

- 如果当前工具栈变化，先更新本文件，再更新其他维护文档。
- 本文件只写通用编辑基线，不写单项目特例。
