# 对话经验整理与清场

调用本技能（包括仅发 `$chat-notes`）或要求按本技能收尾，即包含对当前项目无用过程文件的可恢复清理授权，不再等用户另说“请清理”。仅提及、讨论或审查技能本身不触发清理；明确“只讨论”“不改文件”“不删除”“只更新某文件”或限定目录时服从限制，计划模式及宿主权限仍优先。

上游来源登记用于追溯历史吸收内容；其中旧的再次审批要求不作为当前执行流程，现行授权与清场方式以本文件为准。

按顺序完成：**识别项目与当前成果 → 整理经验及已授权记录、必要发布 → 实际清场 → 核验成果并给出文件链接**。没有新经验、某项经验修改待确认或发布失败，都不阻塞独立可执行的清场；经验写入和清理的授权分别判断，不能总结后直接结束。

## 整理经验

从本轮对话和实际改动中找出下次仍有用的新信息，核实事实并检查相关现有说明，分清规则缺失还是执行时遗漏。能改变下次判断或行动的新信息才值得记录。

优先更新已有文件：项目事实留在项目说明，跨项目方法归负责该行为的已有 Skill。按内容选择正文、参考、模板、脚本或测试；只有需要留存的新信息确实无法写入现有文件时，才考虑新建。

已有清晰规则直接沿用；规则冲突或结构妨碍执行时，通过删改、合并解决。按实际变化检查并更新受影响的用法、配置、接口、名称路径、架构图和上下游说明。

本地依据不足，或外部方案会影响技能改进选择时，通过 `web-access` 查上游并比较可复用部分，保留来源并遵守许可要求；安装或替换需有对应授权。

具体改动尚未获准时，简短说明值得改哪里、原因和改法。已有明确授权就完成相应修改；修改 Skill 后使用 `skill-creator` 检查受影响的内容，并按[发布说明](references/skill-edit-followup.md)自动提交、推送和双端同步，除非用户明确限定只改本地。

## 清场

先依据任务上下文、项目说明和实际文件关系确认当前项目及成果，盘点本轮和历史累积的过程文件。不能直接把父工作区、聚合仓库、其他项目或符号链接指向的外部目录纳入清理。逐项核对生成记录、用户决定、版本替代关系和真实依赖，不能只凭文件名、目录名、修改时间或最高版本号判断。

- **保留当前成果**：已确认的当前或最终版本，以及用户明确指定的对比版本。尚无确认终稿时保留当前工作稿并标明“待确认”；当前版本无法唯一确定时，保留候选并列为待定，不能清到无稿可用，也不能擅自把旧稿指定为对比版本。
- **保留原件与必要依赖**：用户原始输入、引用资料、正式源码和测试、可编辑源文件、成果图片及运行依赖，保护用户手工改动、正在使用的文件和恢复未完成事项所需的材料。
- **清除已证实无用途的过程产物**：被替代的旧稿、无用候选稿和失败稿，以及测试副本、预览、临时截图、转换文件、临时脚本、缓存和重复报告。曾确认但已被替代的版本，仅在明确用于对比时保留。不以“以后可能复核”笼统保留整批材料。
- 仅用于过程检查的截图、PDF、日志或检查副本，不因被过程记录引用就永久保留。先把实际检查结果和必要错误摘要并入已有记录，再清除过程文件并修正引用，说明历史检查结果与仍可复用的检查依据。不能为了删除唯一必要证据而删掉正式成果的证据引用。
- **实际执行可恢复清理**：核对实际绝对路径和恢复依据，验证当前平台的系统回收站或已有项目恢复机制后使用，不假定回收功能一定可用。不能把整批中间文件搬到项目中新建的归档目录冒充清场，不自建外部垃圾目录或安装清理工具。
- **只暂停有问题的文件**：归属、用途或版本不明的原地暂留并列为待定；占用、权限或恢复条件不足的列为受阻。先完成其他确定项，再提出影响剩余处理的具体问题，不强关应用。没有可恢复手段时，仅针对确切清单询问永久删除许可；未获答复就保留这些文件，不擅自永久删除。

## 核验与交付

清场后实际检查应清理项已从项目移除、保留成果及依赖完整可用、引用有效。口头列出清理计划不算执行，部分完成不能报告全部清场完成；没有待清理项也要说明盘点结果。

回复固定按以下四项反馈，通常每项一句话；即使无事项也不省略，仅有阻碍或必要说明时展开：

- **成果：** 最终文件链接及状态；未定稿标“待确认”，无文件则明确说明。
- **经验整理：** 已更新的规则或记录；没有新增内容写“无需更新”。涉及技能发布时，区分源码修改、已发布和运行时已同步，不把单步成功写成全部完成。
- **清场：** 明确标注“无需清场／已完成清场／部分完成／未执行”，附简短依据。
- **待办：** 尚未完成的事项及阻碍；没有则写“无”。

未检查不能写“无需清场”；没有实际清理操作不能写“已完成清场”。已检查且没有待清理项用“无需清场”，全部清理并核验通过用“已完成清场”，仍有待定或受阻项且已完成部分清理用“部分完成”，未检查或未执行应做的清理用“未执行”并说明原因。

复用已有 README 或交付索引，不为每次收尾新建总结、清场报告或额外的 final 副本。

用户要求整理目录或命名时，遵循项目现有习惯和依赖关系，调整后修复引用；涉及多目录合并或迁移时使用 `project-organizer`。

需要后续恢复的未完成事项或异常，在本次获准维护的现有记录中简要说明状态、影响和恢复依据，解决后更新原记录。只审阅时在回复中说明。
