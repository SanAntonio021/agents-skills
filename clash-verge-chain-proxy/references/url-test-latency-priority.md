# `url-test` 延迟优先与稳定切换

## 适用范围

用户希望自动使用低延迟节点，同时通过固定测速周期和延迟容差减少无意义切换时，使用本流程。
它适合 Mihomo 原生 `url-test`，不包含外部守护程序、流量繁忙检测、手动锁定或独立控制界面。

先区分两种选择目标：

- `url-test`：在存活候选中选择低延迟项，`tolerance` 用来抑制小幅延迟波动。
- `fallback`：按候选顺序选择第一个可用项，表达业务优先级，不负责选最快。

多层链路通常把两者组合使用：内层 `url-test` 比较同类完整链的延迟，外层 `fallback` 保留 Flower、
普通订阅或裸节点降级等已经确认的业务顺序。

## 配置形态

链式代理必须测试实际使用的完整链。为每个前置节点生成一条独立的“前置 -> 落地”代理，`url-test`
候选放这些链，不用裸前置节点延迟代替到落地节点的真实延迟。

```yaml
proxy-groups:
  - name: <normal to landing latency priority>
    type: url-test
    url: https://www.gstatic.com/generate_204
    interval: 1800
    tolerance: 50
    timeout: 5000
    max-failed-times: 2
    lazy: false
    proxies:
      - <landing via normal node 1>
      - <landing via normal node 2>
```

参数按用户目标确定，不把示例值写成通用常量。采用 `1800 / 50 / 5000 / 2 / false` 时，应解释为：

- 每 1800 秒安排一次定时健康检查。
- 当前节点仍存活时，候选通常至少快 50 ms 才值得切换。
- 单次健康检查最多等待 5000 ms。
- 失败次数超过 `max-failed-times` 配置值后允许提前触发强制健康检查。
- 即使该组暂时未被使用，也继续进行健康检查。

保留已有健康检查 URL，除非有当前环境证据证明它不合适。`generate_204` 只证明通用 HTTPS 链路，
不能代替 ChatGPT、Claude 或其他目标业务的真实请求验收。

## 不能把 30 分钟当成硬冷却

`interval` 只控制定时测试。Mihomo 的通用组字段规定：`max-failed-times` 超过阈值会触发一次强制健康
检查。因此，候选在 30 分钟内再次出现新 history 或发生故障切换，不等于 Clash Verge 另有后台测速器，
也不等于配置没有生效。

判断提前测速来源时按同一时间窗口核对：

1. 从当前运行态 `/proxies` 保存目标组和候选的 `now`、`alive`、`history` 时间戳与 delay。
2. 查服务日志中同一时段的连接错误、健康检查失败和 `using <group>[<proxy>]`。
3. 读取 Clash Verge 的 `verge.yaml`，检查 `enable_auto_delay_detection` 和
   `auto_delay_detection_interval_minutes`。字段为 `null` 时，不直接猜测启用或禁用；结合当前版本源码或
   运行行为确认默认值。
4. 区分用户手动触发的健康检查、Mihomo 定时检查、失败阈值触发的强制检查，以及界面自己的自动延迟
   检测。只有证据指向界面设置时才修改它。

报告中把“定时评估频率”和“实际可能切换的条件”分开写。节点失效、配置重载、手动健康检查和外层
故障转移都可能绕过自然周期；不要承诺 `interval: 1800` 能阻止 30 分钟内的所有切换。

## `tolerance` 的边界

`tolerance` 是延迟切换容差，不是手动锁定，也不保护已经失效的节点。验收时至少覆盖：

- 当前节点存活，最快候选只快不到容差：应保持当前节点。
- 当前节点存活，最快候选快于容差：允许切换。
- 当前节点失效：允许故障切换，不等待容差或自然周期。

截至 2026-09-01，Mihomo [#2945](https://github.com/MetaCubeX/mihomo/issues/2945) 报告 `url-test`
当前节点恰好位于候选列表首项时，`fastNotExist` 判断可能使容差失效。这个问题应记录为核心限制：

- 不承诺每次都严格执行容差。
- 记录发生时的候选顺序、原选中项、各项 delay、Mihomo 版本和 history 时间戳。
- 保持用户确认的周期与原生实现，不因为这个已知问题自动引入后台控制器。

候选卡片保持订阅或配置顺序很常见。`url-test` 决定实际 `now`，不承诺界面按延迟重新排列。

## 避免继承旧选择缓存

启用 `profile.store-selected` 时，同名组可能从 `cache.db` 恢复以前的 `now`。把同名 `fallback`、
`select` 或旧自动组改成 `url-test` 时，优先建立语义清楚的新组名，再把所有活动引用精确改到新名称。

1. 在持久化增强源中定义新组。
2. 扫描最终规则、外层组和后处理脚本，确认所有预期引用都已更新。
3. 只有确认旧组不再被任何规则或活动组引用后，才精确移除旧定义。
4. 不删除或重置全局 `cache.db`，因为它还保存其他组的选择和运行状态。

重新生成配置或刷新订阅可能同时更新 `profiles.yaml` 中的流量、到期时间或订阅名称等遥测字段。比较改动
时把这类订阅元数据与组结构、规则引用和增强文件绑定分开；字节变化不自动等于路由配置漂移。

## 外层 `fallback` 嵌套风险

截至 2026-09-01，Mihomo [#2588](https://github.com/MetaCubeX/mihomo/issues/2588) 报告父
`fallback` 会把嵌套策略组当成不透明候选：子 `url-test` 组级健康状态为失败时，父组可能直接跳到下一项，
即使子组内部仍有存活节点。

这种结构需要单独验收：

- 保存父组与子组各自的 `alive`、`now` 和 history，不只查看子节点。
- 普通外层若经用户确认允许裸节点降级，要明确最终出口可能因此暂时变化。
- AI 外层候选只放完整落地链组；不加入裸节点、普通降级组或 `DIRECT`，避免核心限制扩大成 AI 出口泄漏。
- 父组意外越过子组时，先记录为嵌套组健康判断问题，不误判成 `tolerance`、候选排序或界面自动测速。

## 验证与验收

### 静态与生成配置

1. 修改前备份 `profiles.yaml`、当前 profile 绑定的增强源、两份生成配置，并记录 SHA-256。
2. 检查增强脚本语法，随后让 Clash Verge GUI 重新生成配置；不把生成 YAML 当持久化源。
3. 对 `clash-verge-check.yaml` 和 `clash-verge.yaml` 分别运行 Mihomo 配置检查。
4. 用 YAML 解析器确认每个新组只出现一次、`type: url-test`、参数精确，候选集合与当前订阅解析结果
   双向相等且顺序稳定；运行态 `/proxies` 中对应类型应为 `URLTest`。
5. 扫描旧组名引用，并核对外层优先级、AI 分流、国内直连、局域网和认证门户规则没有改变。

### 运行态与容差

1. 通过命名管道查询 `/proxies`，不打印 controller secret 或完整代理对象。
2. 触发两轮受控健康检查，记录目标组的选中项、存活状态、history 和 delay；验证小于容差时保持、
   大于容差时允许切换、失效时允许故障切换。
3. 再观察一次自然 `interval` 周期。手动触发的两轮不能替代自然周期证据。
4. 自然周期前后核对服务日志和新建连接，确认运行态选择与实际 `using` 链一致。

### 持续连接

自动组切换通常影响新建连接；已建立连接是否继续沿用旧链取决于协议复用、客户端行为、核心版本和连接
关闭设置，不能只凭原理保证。使用真实持续连接跨越自然切换：

1. 在切换前建立可持续观测的 HTTP/2、WebSocket 或等价长连接，记录连接标识、请求成功数、重连数和错误数。
2. 保持同一连接跨过自然健康检查与实际自动切换，不主动重启 GUI、核心或客户端。
3. 切换后继续在旧连接上发送数据，确认是否中断或重连。
4. 另建一个新连接，通过同一时段服务日志或不泄露真实 IP 的出口一致性比较，确认它使用新选节点。
5. 报告“本次测试观察到的行为”，不要把一次无中断扩大为所有协议和应用的保证。

## 回滚

若增强脚本语法、配置生成、任一 Mihomo 检查、候选集合、规则引用或运行态路由核对失败，恢复批准范围内
的增强源备份并重新生成两份配置。恢复后重复静态与运行态检查；不通过清空全局缓存解决生成或路由错误。
