# Markdown 文档组织

## 适用范围

本参考用于整理、拆分、合并或持续维护相互关联的 Markdown 文档。它处理文档之间如何分工，不替代 README、AGENTS、SKILL、实验记录、技术文档和版本记录自身的专业要求。新建项目、目录迁移和文件搬迁由 `project-organizer` 负责。

开始前确认项目、目标读者、参与文档、主要维护位置、维护者、更新触发条件和本轮范围。只做检查或讨论时保持只读；需要写入时，先确定本轮文档和内容的归属。

## 盘点与职责

完整阅读受影响入口和必要引用，按实际段落或章节识别内容块。必要时用清单记录内容、权威落点、维护者、更新触发、读者和生命周期；清单用于判断，不作为默认交付物。

先看现有目录和文档能否承接内容。经常因同一事件或同一证据一起更新的内容适合放在一起；不要按部门名、学科名或固定栏目强行分类，也不为整齐创建空目录。

一份详细文档只承担一个主要维护任务。系统方案、器件选型、代码操作、仿真结果、实验记录和交付验收若因不同事件分别更新，应由各自合适的文档承接。不要建立跨主题的兜底文档。篇幅不是拆分依据：单主题长文可以保留，短文档承担多项独立维护任务时也可能需要拆分。

每项事实只保留一个权威落点。其他文档按读者需要保留摘要并链接到主记录；摘要、结论、模板栏目或面向不同读者的内容有独立功能时可以并存，但需明确它与主记录的关系。

## 内容与历史

项目入口可概括用途、用法、当前成果、限制、待办和专题链接；专题说明承接详细方法、参数和条件；实验记录保留批次、步骤、结果和证据；验收记录保留判定依据和结论；版本记录保留当时有效的状态。具体项目按现有结构取舍，不强行套用统一目录。

当前状态、历史事实、计划、实测、推测和待办分开表达。历史记录保留当时条件和结论，不改写成当前状态；日期用于实验批次、版本、验收时间或历史索引，不作为每次修改的流水账。

按事实、章节功能和证据判断重复。同一事实承担同一功能且没有新证据时可合并；入口摘要与专题详情、不同条件或不同批次有独立作用时保留。不要为了消除重复而轮换术语、削弱限制或改变结论强度，也不要按日期、版本号或文件年龄批量删除历史。

仍影响当前使用、兼容、排错、恢复、验收或责任判断的内容，保留在原处或归入能承接它的当前章节、专题记录或恢复材料，并更新引用。已解决且没有后续用途的普通试错和重复说明可以合并或删除。没有明确承接位置、唯一证据或恢复依据时，先保留并标为待核实，不以另建冗余历史副本代替内容归位。

## 引用与验收

引用使用读者可访问、可验证的路径或链接。迁移或合并内容时，按明确映射更新 Markdown 链接以及图片、代码、配置和其他工程资源路径，优先使用可用的相对路径；外部 URL、Zotero 标识和历史叙述不作机械替换。动态依赖通过适用工具和运行检查核实。

完成后回读完整文档及受影响引用，确认：

1. 读者能找到当前入口、状态、限制、下一步和详细材料；
2. 该类文档应保留的参数、条件、批次、结果、版本差异、证据、恢复位置和未验证边界仍可定位；
3. 规则、安全文件、配置、回滚、恢复和证据等关键入口没有因精简丢失；每项事实有明确的权威落点，迁出内容有承接位置，引用目标存在且指向正确对象；
4. 整理没有改变数字、版本、因果、范围、状态或结论强度，也没有把历史事实改写成当前事实。

可从项目中选取 3–5 个真实的后续更新事件，检查每项信息应改哪份文档；若同一信息出现多个同等权威落点，职责仍未理清。继续修改只剩同义替换或个人偏好时停止。缺少原始材料、外部证据或目标文件不可访问时，保留来源和未核验状态；路径存在不等于内容已验证。
