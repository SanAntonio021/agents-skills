# 页面制作、渲染与验证

总览确认后、生成前读取本文件；交付前执行末尾验证。命令均从技能根目录运行。流程授权以 [SKILL.md](../SKILL.md) 为准，本文件不增加确认关卡。

## 页面组织与样式

没有用户自定义模板时，页面沿用以下默认职责；自定义模板按原版式承载同样的工作与结果信息，不强加总结条或默认坐标：

- 首页设置“今日工作总览”，列出本次已确认入选的全部工作，包括后文展开的项目，不扩充筛选范围。每项用一至两句话连接项目总体目标、当天具体工作和已有结果或状态；前因不能只停在下一步操作的局部目的。不为缩成“动作＋工作对象”删掉关键因果关系，目标依据缺失时先回查，不编造背景。具体方法、参数、结果和后续安排放到对应页面。同一工作的多个分析页合并为一个总览条目。不设每项必须一行的限制，以讲清楚为准，不为压成一行缩小字号或省掉必要对象、原因和条件；按[总览页表达规则](chinese-style.md#总览页工作缘由与实际推进)检查，不强求以“完成、完善、明确”开头。沿用编号、22 pt、常规字重，不拆成加粗小标题与说明。汇报题目或文件名已有日期时，总览标题下不再重复日期。此页不套用进展页的项目双标题或结果总结条。
- 每个进展页的左上标题在同一行依次写“项目名称 + 三个 ASCII 空格 + 本页主题”。项目名称是大标题，保留标题字号并加粗；本页主题是小标题，按 PowerPoint 字号档缩小两次且不加粗，例如 36 → 32 → 28 pt，不按固定减 2 pt 处理。项目名称采用正在推进项目的真实名称，优先使用用户确认或修改后的名称，不能擅自用简称、会话标题或本页工作代替项目名；具体项目命名保存在项目记录中，不写入公开技能。
- 红色/粉色横条只写一句话，总结这一页实际完成了什么或得到什么结果。前面的进展页不写“还需实测”等下一步安排。
- 正文与图件交代当前工作、比较条件和实际进展；必要时补背景，不机械套用起因栏目。不显示右上日期/页码角标，不设置页底重复总结。
- 页底不默认补充文字，允许留白；删除重复图注、内部操作说明和过度解释。图中已有且清楚的信息不再复述，影响判断的实验条件、来源和仿真/实测区别仍需保留。
- 当前工作全部讲完后，以最后一页“下一步工作”收束。每项连接项目总体目标、当前待解决的问题、下一步行动及目的，写法与交付检查见[末页表达规则](chinese-style.md#页面检查与独立安装基础检查)。把当前已确定推进的后续行动写在一个原生文本框中，按 1、2、3 编号；沿用用户最新取舍，不自动恢复此前删去的事项，不为凑数量加入备选安排。总览确认后，末页随整套直接完成，不另设确认环节。

实验准备与方案按“要验证什么、怎么测、已准备什么、目前测到哪一步”组织，用现有系统图或接线图解释测量关系。操作顺序、按钮和逐条接线说明留在实验方案中，只有影响测量原理或结果判断时才进入汇报。尚无实测结果时如实展示方案与准备，不把软件离线检查当作硬件进展；不同项目分别组织，不固定每个项目的页数。

每组图回答一个具体问题：说明各组比较什么、结果支持什么判断。结果页须有对应数据或图件支撑本页结论；方案页的接线图仅说明方案，不能充当已完成实验的证据。单次扫描中的形状只作为本次观察，重复性结论需重复测量支持；拟合残差不能直接替代压缩点等有专门定义和测量条件的指标。当前完成程度与影响判断的限制可在进展页说明，未来行动统一末页表达。必要背景不能只放备注或依赖口头补充，也不为图大删掉理解所需的文字。

资料核对与页面表达分开：来源可信度、不能推出的其他结论和验证缺口用于决定能写什么，不直接搬成页面说明。页面先准确交代本次对象、条件、方法和结果；仿真、离线、实测或原型状态在对应结果处说明。其他信息按 [必要信息判断与全文检查](chinese-style.md#必要信息判断与全文检查) 取舍，不因“可能被误读”就增加免责声明。

在盘点完整输出后再选代表图。完整运行总览说明处理链路跑到哪一步，局部结果或多条件对比说明性能差异，二者不能自动互相替代。频谱分析、滤波调整等若构成独立且入选的科研进展，应有相应结果表达；同一结论的重复总览不必全放。总体图过密时另页展示关键区域并保留完整图来源，不能裁掉会改变判断的条件。

字号按每页内容密度、图件和可用空间调整；模板字号仅是起点，可逐页覆盖。保持标题、总结、正文和图注的层级与全稿协调，不为填满空白放大短句，也不为塞进内容不断缩字。调整后检查实际渲染，必要时改布局或拆页。

## 文件存放

文件归属与收尾遵循已加载的共享全局规则。正式汇报位置以用户本轮指定的目录为准；未指定时读取本机或当前项目已确认的每日汇报交付目录，均未配置时采用当前项目目录。个人绝对路径只记在本机或项目约定，不写入公开技能。过程材料放在 `过程文件/<任务>/`，续做及跨技能共用该目录；用户或项目另有文件约定时沿用。采集摘要、deck JSON、渲染 PDF、页面 PNG、HTML 和 manifest 均放任务过程目录，按需创建；实验原始数据和现有素材保持原位。渲染检查通过后，自动将 PPTX 无覆盖复制到约定的正式位置，复核可打开、大小及 SHA-256，并在过程 manifest 记录交付路径与摘要。PDF/HTML 仅在用户要求时作为成果交付；HTML 交付前确认自包含。正式位置同名时沿用下文版本规则，不覆盖旧成果。普通任务结束保留过程材料，清理须由用户明确提出。

## Deck JSON 与渲染

提纲按当前目标确定后，在任务过程目录写入一个小型 deck JSON 文件。渲染器要求以下结构：

```json
{
  "title": "今日工作汇报",
  "date": "20260715",
  "footer": "2026-07-15",
  "slides": [
    {
      "project": "光纤通信系统",
      "title": "链路测试",
      "summary": "完成 1 km 光纤链路测试，发现低频噪声峰。",
      "type": "result",
      "status": "已完成",
      "blocks": [
        {"type": "text", "heading": "观察", "text": "..."},
        {"type": "image", "path": "<IMAGE_PATH>", "caption": "频谱仪 CH2", "role": "result", "period": "current", "source": "<RUN_OR_DOCUMENT_REFERENCE>"}
      ]
    }
  ]
}
```

总览页使用 `type=overview`、`title=今日工作总览`、`font_sizes.body=22`，每项说明工作缘由与实际推进，作为文本块的一段正文，采用编号；不设置 `heading`、`project` 或 `summary`，以免生成加粗小标题、项目双标题或总结条。

使用以下命令渲染：

```text
python scripts/render_deck.py --deck "<project-root>/过程文件/<任务>/deck.json" --output-dir "<project-root>/过程文件/<任务>" --base-name <YYYYMMDD-or-YYYYMMDD组会>
```

依赖检查和生成均支持 `--config <配置绝对路径>`。未指定时，检查脚本只读取当前目录的 `lab-report.local.json`，生成脚本只读取 deck JSON 同目录的同名文件，不向上搜索。有效路径优先级为现有环境变量、项目配置、自动发现；明确配置无效时报错，不悄悄忽略。安装后用户级路径写入被拒绝时，由智能体按 [安装说明](../README.md#安装命令与配置参考) 保存项目配置，以后显式传入该绝对路径；不能把仅有本次会话路径写成已经持久保存。

配置中的 `work_root`、`diagnostics_root` 可指向项目过程目录，用于任务临时文件、独立 LibreOffice 用户配置和诊断。它们不会改变共享并发锁位置；不同项目仍共用两个槽位。共享锁访问被拒绝时不启动 LibreOffice，记录原因，在获准访问该锁的环境中重试，不把锁迁到各项目绕过限制。

`type=result/setup/comparison` 的页面必须有真实图片。每页支持一至六张图片，按可读性决定是否拆页。新制作的进展页必须提供 `project`（项目名称）和 `title`（本页主题），渲染成同一行的大小标题，中间三个 ASCII 空格；大标题加粗，小标题按 PowerPoint 字号档缩小两次且不加粗。旧稿只有 `title` 时保留单标题兼容（兼容旧 `section`/`kicker`），不得把这一兼容形式当作新稿默认。`summary` 是红条的一句当页结果总结；旧 `subtitle` 仅作红条兼容输入，不再生成页底结论。有图页的文字块进入独立正文区，不压入页底；`body_fraction` 可调正文占内容区的比例。`layout=wide-strip` 将首图放上方、其余图放下方；`layout=stacked-left` 将三张图排为左侧上下两图、右侧大图；其他情况使用单图或网格。

逐页用 `font_sizes` 覆盖 `title`、`summary`、`body`、`caption` 的起始字号；`title` 控制项目大标题的起始字号，本页小标题跟随其字号档缩小两次。`layout_overrides` 可覆盖各区域配置，先调整布局再决定是否拆页。拟合只用于避免溢出，不能代替逐页阅读和排版判断。最终页用 `type=next_steps`、`next_steps=["行动一", "行动二"]`，渲染成一个编号原生文本框；该类型不允许出现在中间页，统一标题“下一步工作”，不强套项目大小标题。日期、来源和状态保留在备注，不生成角标。历史示例仍须在可见文字中标明。

只有用户明确要求纯文字汇报时，才设置 `allow_text_only=true`；含真实图件的汇报允许最后一页为纯文字下一步。缺图和空材料会报错，不生成占位成品。

渲染器生成：

- `<name>.pptx`：文字为原生文本框，曲线图和照片为独立图片，可分别移动、缩放、替换。图片内部的数据和文字仍是像素，不宣称可编辑图表数据。
- `<name>.pdf`：由实际 PPTX 经隔离 LibreOffice 渲染。
- `<name>_01.png`、`<name>_02.png`、...：从该 PDF 生成的页面图片。
- `<name>.html`：使用这些页面图片的自包含预览，不另做一套版式。
- `<name>.manifest.json`：版本 3，保留输出路径、图片来源与哈希、幻灯片数量及可编辑对象说明，新增运行配置和 `pptx`、`structure`、`libreoffice`、`png`、`visual`、`powerpoint` 分阶段状态。脚本渲染完成为 `rendered_visual_pending`，不代表已做逐页视觉或 PowerPoint 原生检查。

每次执行使用独立输出名称，清单通过同目录临时文件刷新后原子替换。渲染失败返回非零状态，保留已生成 PPTX、阶段错误和完整 runner 诊断；明确报告“PPTX 已生成、渲染失败、视觉验收未完成”，不能仅称全部成功或全部没有生成。清单写入失败时报告该问题，保留旧清单；首次没有有效清单则不能声称可按清单恢复，诊断失败不遮蔽原始错误。

LibreOffice、PNG 或 HTML 阶段失败，修复环境后可运行 `python scripts/render_deck.py --resume-manifest <失败清单绝对路径> --config <配置绝对路径>`；没有项目配置时省略 `--config`。恢复入口检查原 PPTX 哈希与结构，在新尝试目录重新生成 PDF、PNG、HTML，不改原失败记录。PPTX 生成失败需重新生成；视觉或 PowerPoint 检查失败应修正具体问题后重做相应检查。PPTX 改动后不得沿用旧哈希、渲染或验收结果。

默认采用随附的简洁科研汇报样式：16:9、白底、微软雅黑、左上黑色大标题、深色分隔带、粉底居中一句结果总结、大面积图件及按需安排的正文。渲染器实际读取 `references/template-profile.json` 的尺寸、坐标、字体与颜色；deck 可用绝对 `profile_path` 选择其他配置。只复用样式参数，不需要原始样稿，也不包含私人实验图片。字体未安装时先在配置副本中选择已安装的中文字体，再检查渲染。manifest 记录样式来源及配置哈希。

文件命名：

- 日报：`YYYYMMDD`。
- 周组会：`YYYYMMDD组会`。
- 请求的 stem 已存在时，保留它并使用 `_v2`、`_v3` 等后缀。绝不能自动覆盖早期演示文稿。

## 验证

报告成功前：

1. 确认 HTML、PDF、PPTX、PNG 和 manifest 文件存在且非空。
2. 确认 PPTX 是有效的 ZIP/Office 包，并且幻灯片数量符合预期。
3. 确认 PNG 宽度为 1600 像素，高度随实际页面比例计算（默认 16:9 为 900）；每张引用图片均正常显示，缺图必须补齐或调整页面内容后再交付。
4. 对照覆盖清单，确认总览简短列出全部入选工作，同一工作的多页分析没有拆成多个总览条目，首页简述项未另建进展页，展开项的独立成果均已表达，未用少量局部图替代完整工作；核对各进展页真实项目名称、三个 ASCII 空格及同一行的小标题字号与非加粗样式，核对红条单句当前总结、按需背景及末页编号下一步；末页须讲清行动与项目总体目标、当前问题的关系，不能只剩动作清单，也不能把预期目的写成既有结果。按“必要信息判断”逐页检查标题、总结、正文、表头、括号、图注和表注，删除重复防御性补充，保留解释数据所需的条件、比较基准和假设。逐页检查实际 PPTX 的渲染：标题不换行、不溢出，图件够大、曲线和照片与文字对应、无裁切和重叠、无缺图占位符；页数符合本次要求。
5. 报告准确的输出路径和所有 `未验证` 项。
6. 用 `python-pptx` 读取文件，检查各页有非空原生文本框、预期数量的独立图片且图片不是整页截图。结合实际渲染确认对象与内容一致；安装了 `pptx` 技能时可复用它的检查工具。

原生 PowerPoint 验证是单独的验收项。有已安装的 `pptx` 守护程序或其他受控验证工具时，在隔离副本上验证，保留实际打开与导出结果；不能接管或关闭用户实例。没有工具或应用被占用时，交付已经检查的候选并标明“PowerPoint 原生打开与导出未验证”，不把 LibreOffice 渲染冒充原生验证。

修改已有 PPT 时先保留原文件，沿用用户指定的制作工具；使用 `python-pptx` 或 XML 编辑时检查有效 OOXML、重复格式节点及可编辑对象，并重新渲染。已安装 `pptx` 技能时可复用安全替换和结构检查工具；没有相应检查能力时明确报告未验证项，已知结构错误必须修复后再交付。
