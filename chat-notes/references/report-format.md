# 审查稿与汇报格式

## 审查稿写法

审查稿默认给用户看，不是给另一个 agent 看。

- 普通项目记录默认使用简版，通常不超过 10 行。存在 skill 升级候选时，改用下面的候选模板；每个候选都要足以让用户判断价值，不为守行数删掉理由、缺口或拟提取内容。
- 先说结论，再说理由。
- 用短句，不堆抽象词。
- 少用"沉淀、分层、入口、链路、治理、规范化"这类词；必须用时，后面补一句白话解释。
- 不写大段过程复盘，只写这次要不要改、准备改哪里、准备整理什么、为什么。
- 审查稿只列准备整理或准备修改的内容。不要列"不整理""不处理""不会去动"的清单；这些只作为内部过滤依据。
- 如果需要说明为什么某些内容不写进去，只写一句短理由，例如"其他材料与本次准备写入内容无关，暂不进入审查稿"。不要逐条列出被排除的文件、话题或旧讨论。
- 每条建议都要能直接回答"我接下来要不要让你写进去"。
- 准备新建 Markdown 时，必须先说明现有 README、规则文件或专题文档为什么不能承载；没有明确理由就改为复用现有文件。
- 如果审查稿或准备写进文件的正文里，有用户刚表示看不懂的词，换成更具体的话。
- 分流后不做 skill 时，审查稿只需写明结论、理由、写到哪里和内容摘要，不需要 skill 对比。
- 本地和外部 skill 检索默认由 AI 内部完成。只有候选会改变新建、修改或不改的选择时，才在审查稿里用一句话说明；用户要求详情时再给完整表格。
- 建议修改现有 skill 时，理由必须指出现有规则具体缺少什么。`没有规则`、`规则不完整`、`规则明确但没有执行` 的详细判断留在内部，不把分析过程堆给用户。
- 不把“候选补丁”当成审查稿。审查阶段先说明哪个 skill 值得升级、为什么、需要补强什么、准备从本轮提取什么以及放到哪里；用户批准后才生成正式内容。

## 审查稿简版模板

建议实际修改时使用这个结构：

```text
结论：整理成新 skill | 修改现有 skill | 写在当前项目里 | 这次不改
原因：<一句话>
准备改：
- <内容 1>
- <内容 2>
是否同意？
```

结论为`这次不改`时，只写：

```text
结论：这次不改
原因：<一句话>
```

只有存在真实取舍时才补一行本地或外部候选结论。不要为了证明做过检索而增加表格。

## Skill 升级候选模板

存在一个或多个 skill 候选时使用；没有证据的 skill 不列入：

```text
结论：修改现有 skill

候选 1：<skill 名称>（<源码目录>）
为什么值得升级：<本轮证据 + 可复用价值>
现有缺口：<没有规则或规则不完整的具体内容>
需要补强：<升级后应改变的行为或结果>
拟提取内容：<判断规则 / 检查表 / 参考内容 / 模板栏目 / 脚本能力 / 回归场景>
建议落点：<SKILL.md / references/... / assets/... / scripts/... / evals/evals.json>
外部借鉴：<只在实际影响候选时写来源、指标、可吸收内容和不吸收边界>

是否同意升级以上候选？也可以只批准其中一项。
```

有 2～3 个候选时重复候选区块，并按优先级排序。多个候选共同依赖同一段经验时分别写清各自职责，不复制同一句“需要补强”。审查稿只给内容轮廓，不给 diff、完整替换段落或完整新文件。

## 完成汇报与异常报告

### 默认短报

正式修改、项目记录更新、技能发布或清场完成后，用户可见汇报不固定行数，按实际发生的信息决定长度。按以下顺序写，缺失项直接省略：

1. **结果**：一句话说明做成了什么。
2. **状态**：只有状态影响当前使用或当前判断时才写。
3. **重要异常**：只有异常会改变完成判断时才写。
4. **用户动作**：只有确实需要用户处理时才写。

正常成功不展示逐文件变更、SHA-256、提交号、退出码、四层文件对照、完整测试过程或内部 `skill-creator` 对照。交付物路径可以显示。技术证据留在执行记录；触发中央异常报告时，聊天必须给出报告链接。

技能发布只显示实际达到的最高状态，不为“明确区分”而固定罗列多行：

- 仅本地修改且未要求发布：只写结果。
- 源码已推送但不涉及运行时同步：`源码已推送。`
- 源码已推送且运行时文件已同步：`源码已推送，运行时文件已同步。`
- 源码已推送但同步失败：`源码已推送，运行时未生效。`
- 推送失败：`技能已修改，但源码推送失败，运行时未更新。`
- 当前任务仍持有旧技能上下文且影响立即验证时，才追加：`当前任务仍使用旧规则，后续调用生效。`

### 清场预览例外

清场批准前不使用短报。必须完整展示：

- 归档批次：`archive/cleanup-YYYYMMDD/`；尚未移动任何文件；
- 保留集的用途、数量、总字节数和 `retained-manifest-before.csv`；
- 归档候选的数量、总字节数和 `archive-manifest-before.csv`；
- 每项候选的原相对路径、目标路径、用途和拒绝覆盖的恢复方式；
- 待判断或未归档项及保留理由；
- 空目录计划及重建方式；
- 报告后的再次明确批准要求。

用户最初说“做完后清理”等预授权只触发清场准备，不替代本次预览后的批准。清场批准只覆盖预览中的固化路径。出现遗漏清单、目标已存在、哈希不一致、文件进入回收站或保留集变化时，停止报告“完成”，先按清单恢复或重新核验。

### 中央异常报告

出现以下任一情形时，必须生成中央异常报告：必需验证失败或无法完成；提交、推送或运行时同步失败；部分完成；混入其他提交或范围漂移；路径、SHA-256、保留集或清场验收异常；需要人工恢复。

报告统一写入 `D:\BaiduSyncdisk\.agents\reports\chat-notes\`。开始写入前，按最终候选文件名运行：

```powershell
git -C "D:\BaiduSyncdisk\.agents" check-ignore -q -- "reports/chat-notes/<YYYYMMDD-HHMMSS>-<task-slug>.md"
git -C "D:\BaiduSyncdisk\.agents" status --short -- "reports/chat-notes"
```

第一条必须成功，第二条必须为空。任一条件不满足时，不创建报告目录、不修改 `.gitignore`，聊天直接说明报告未能保存的原因和用户动作，不得把任务写成完成。

报告文件名为 `<YYYYMMDD-HHMMSS>-<task-slug>.md`，采用拒绝覆盖创建；同名时顺序追加 `-01`、`-02`，直到取得未占用路径。报告是异常的统一人工阅读入口，至少汇总任务与仓库、实际变更、文件清单、验证与测试、提交/推送/同步证据、退出码、哈希差异、失败边界和恢复动作。清场批次内的 `archive-acceptance.json`、manifest 和日志仍保留为原始证据，由中央报告链接引用，不能替代中央报告。

聊天只显示直白异常结论、必要用户动作和中央报告链接。正常成功不生成中央报告；成功清场继续复用批次内 `archive-acceptance.json`。

- "待确认"只能放需要用户做决定的事项。不要放无关的旧背景、上一轮已讲清的状态、本任务范围外的事、或 AI 自己的操作说明。没有真正待用户拍板的事，就把整节删掉，不要写"无"也不要硬凑。
- 分流后不做 skill 时，省略"本地有没有类似 skill"和"外面有没有类似 skill"。
- 需要展开外部 skill 候选时，字段规则见 [external-skill-format.md](external-skill-format.md)。

## 不放进审查稿、由 AI 内部处理的内容

- **踩坑记录**：这轮遇到的操作层面错误和避免方法，只在用户授权且宿主允许时写入记忆。宿主生成的 `MEMORY.md`、`memory_summary.md` 和 rollout summary 保持只读；使用宿主规定的 correction input。没有合规写入入口时标为 `pending`，不要把未写入说成已完成。用户点名多个机器生成文件时，审查稿逐一说明这些文件只读，不能只举其中一个例子。
- **Git 状态详情**：正常时只在发布状态影响当前使用时写一句状态；不要把提交号、哈希或完整 Git 状态堆到聊天中。异常证据进入中央报告。
- **排除清单**：不准备整理的话题、文件、旧讨论和临时输出，只在内部用于避免误写，不向用户逐条列出。

## 自检清单

完成后过一遍：

- [ ] 结论属于四类之一，且理由清楚
- [ ] 普通项目审查稿默认不超过 10 行；skill 升级候选按候选模板给足判断信息；`这次不改`时只写结论和原因
- [ ] 存在 skill 升级价值时，已列出 1～3 个有证据的候选；每个候选都有价值、具体缺口、补强目标、拟提取内容和落点，且没有提前生成补丁
- [ ] 分流判断有依据，适用范围不确定时走了完整流程
- [ ] 建议修改现有 skill 时，已逐字核对现有规则，判断属于 `没有规则`、`规则不完整` 还是 `规则明确但没有执行`，并指出具体缺口；已明确覆盖时没有重复加规则
- [ ] （分流为"有可能做 skill"时）已搜索本地和外部类似 skill；只有候选会改变结论或用户要求详情时才展开表格，缺失字段没有编造
- [ ] 源码目录和同步产物没有混写，README/AGENTS/CLAUDE 职责没有混乱
- [ ] 建议新建 Markdown 前已检查现有文件，并说明现有文件不能承载的具体原因；否则已改为复用现有文件
- [ ] 规则文件保护到位，未把 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 当垃圾
- [ ] 项目会同时用 Codex 和 Claude 时，已同时检查 `AGENTS.md` 和 `CLAUDE.md`；没有明确 Claude 使用场景时，未主动新建 `CLAUDE.md`
- [ ] 没有相对时间遗留
- [ ] 清场前已按用途建立保留集、归档候选和待判断项；没有仅按 `qa`、`compact`、`_reference` 或版本前缀决定移动
- [ ] 已先冻结原有文件集合，再在批次根目录生成清单和验收记录；本批控制记录未进入候选集、保留集或自身哈希范围，也未覆盖项目中原有的旧清单
- [ ] 清场预览已展示归档位置、保留集、候选数量/字节数、归档前与保留集清单位置、逐项恢复方式和空目录计划，并取得报告后的再次明确批准；未获批准时文件保持不变
- [ ] 每个已批准候选都记录原/归档相对路径、用途、Git 状态、字节数、归档前 SHA-256 和拒绝覆盖的恢复命令；归档保持原目录层级，未平铺、覆盖、进回收站、硬删或自动改 `.gitignore`
- [ ] 每项移动后都已确认源离开、目标存在、字节数与 SHA-256 一致；归档后已复核文件数、总字节数、逐文件哈希和保留集哈希，并写入验收 JSON
- [ ] 空目录只在预览列明、用户批准且执行时确认为空后移除；已记录重建命令；README、record、handoff 等引用只在归档验收通过后检查和修正
- [ ] 正常最终汇报只保留结果、影响当前使用的状态、重要异常和必要用户动作；没有展开文件清单、哈希、提交号、退出码、四层对照或完整测试过程
- [ ] 触发验证、提交、推送、同步、范围、路径、哈希、保留集或清场异常时，已按中央报告规则留档并在聊天链接；报告目录不可安全写入时没有把任务写成完成
- [ ] 任一清单、路径、哈希或保留集异常时已停止下一项和完成结论，保留恢复信息；"待确认"只在有需要用户拍板的事项时才出现
