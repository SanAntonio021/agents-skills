# 实际评测、对照与结果检查

## 先确定验证问题

文字整理检查含义与引用；行为变化需要独立实际试跑；声称效果改善需要可比的新旧结果。选择覆盖此次变化的代表性成功、边界及失败任务，优先复用现有用例，不固定用例数、不默认扩大到全库。

用例沿用 [schemas.md](schemas.md) 的 `evals/evals.json`：
`skill_name`，以及每例的 `id`、`prompt`、`expected_output`、`files`、`expectations`。
评分内容供主智能体或评审者使用，不传给执行者。可自行从已经确认的目标编写测试，不逐例要求用户批准。

## 运行方式

- 在任务过程目录保存实际需要的输入副本与结果，修改前固定被测版本。源码不覆盖用户业务文件。
- 启动独立子智能体时使用新上下文；只提供任务、被测版本路径、必要材料及允许操作范围。每个执行者使用独立结果子目录，主智能体的验收记录另存，避免同名日志互相覆盖。不要继承修改讨论，不提供正确答案、评分条目或暗示应采取哪条路线。
- 执行者实际读取被测技能并完成任务。主智能体检查读取记录、使用的工具、文件变化及实际产物；没有执行记录时不得仅凭最终自述认定通过。
- 测试中使用临时文件、临时仓库或模拟服务。任务需要真实外部写入才能完成时，不能把技能维护授权扩展为真实业务授权。
- 子智能体数量按当前可用并发安排，可顺序运行。独立通道不可用时保留对应未验证项，仍可继续静态检查。
- 只做一项业务测试的执行者直接完成该任务，不递归建立维护或评测流程。

## 对照与盲评

修改已有技能比较旧版与新版；新建技能需要证明额外收益时比较有技能与无技能。各组使用相同模型、供应商、输入材料、工具、权限和参数，从独立新上下文开始，只改变被测技能。

先比较实际成果及完成过程，再决定是否重复或扩大样本。结果波动、差异不明或主观偏好可能干扰判断时，读取 [comparator.md](../agents/comparator.md) 做匿名 A/B 比较；隐藏版本身份但提供任务与评分依据。读取 [analyzer.md](../agents/analyzer.md) 分析差异原因，不把一次胜出写成稳定优势。

## 评分与记录

读取 [grader.md](../agents/grader.md) 评定实际输出；机器可核验的项运行检查，文风和视觉质量由内容判断。事实、原稿保护、范围与完成程度单独核对，不能用总体分数掩盖失败。

保留必要的输入版本、运行上下文、输出和检查结果即可。使用现有汇总工具时遵守原格式：
- `eval_metadata.json`：`eval_id`、`eval_name`、`prompt`、`assertions`。
- `grading.json` 的 expectations 条目使用 `text`、`passed`、`evidence`。
- 宿主提供实际耗时或 Token 数据时保存至 `timing.json`；缺失则省略并说明未知，不写成 0、不估算或当作节省量。
- `python -m scripts.aggregate_benchmark <iteration-dir> --skill-name <name>` 汇总可比记录。成本列必须回查原始 timing：现有脚本可能将缺失值填 0、把 `execution_metrics.output_chars` 作为 tokens，或在 grading 已有非零耗时时不读取 timing.json 的真实 tokens。字符数不是 Token；原始数据缺失则标为未知，不引用这类回填值声称成本或节省量。没有真实多组运行时不制作伪对照。

## 展示与后续

默认在对话中分点展示改动、关键样例与限制。需要逐件比较大量成果或用户指定时，使用原有查看器，勿另写一套：

```text
python <skill-root>/eval-viewer/generate_review.py <iteration-dir> --skill-name <name> --benchmark <benchmark.json> --static <review.html>
```

只在已有 benchmark 时传该参数；比较历史结果时可加 `--previous-workspace <previous-dir>`。静态 HTML 不启动浏览器或占用窗口。用户反馈文件仍沿用 `feedback.json` 的 `reviews`（`run_id`、`feedback`）及 `status` 字段；空反馈只表示未提供意见，不视为签字。

仅在用户明确要求反馈后再改或结果确需其判断时等待反馈；其他已授权工作继续。必要检查通过即可交付，存在新问题或用户新反馈才开启下一轮。
